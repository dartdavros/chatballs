# T-168: проверка подключения сервисов

Дата: 2026-10-23. Рабочая ветка: `skaro/T-168-podklyuchit-servisnye-adaptery`.
Результат ограничен подключениями, контрактом адаптеров и выдачей пресетов.
Редактор, копирование и исполнение сценария, делегирование действий, обмен и
весь этап SPEC-0037 этим отчётом завершёнными не объявляются.

## Источники и решения

- Личная приёмка обоих baseline зафиксирована в SPEC-0037 R-28 и
  `.skaro/docs/service-integrations-implementation-readiness.md` основной копии.
  Карточка плана не используется вместо приёмки макета.
- Источник UI — актуальный `Сервисы.dc.html` основной копии, только для чтения;
  дизайн-файлы и новое меню настроек в ветку не переносились.
- Владелец отдельно выбрал первый брендовый пакет Битрикс24 и предоставил
  реальный вебхук. Ссылка не записывалась в исходники или этот отчёт.
- Согласованные отличия: «Возобновить» и статус «Приостановлено»; скрытые до
  T-169 действия настройки/изменения/создания и списка сценариев.
- После проверки 1024 владелец отдельно выбрал две колонки каталога на узкой
  рабочей области; на 1440 сохраняются три. Внутреннее устройство карточки
  соответствует baseline; порог определяется шириной её контейнера.
- Для сетевых сбоев владелец согласовал существующий текст причины из API в
  том же баннере и строке состояния, без ложного сообщения об отзыве доступа.
  Авторизационные ошибки и кнопка восстановления остаются по baseline.

## Штатное окружение

Skaro: `skaro-chatballs-t-168`. Frontend `http://localhost:20004`, API
`http://localhost:20002`; proxy frontend направлен на `backend-app` того же
Compose-проекта. Readiness через frontend вернул
`status=ok`, `database=true`, `redis=true`. PostgreSQL/Redis и backend-app
имели healthy-состояние. Миграции штатного init выполнены без новых изменений.

Использована уже существующая демо-учётная запись администратора. Seed,
изменение паролей, ролей, TOTP, recovery-кодов и учётных доступов не выполнялись.
Браузерная проверка шла на настоящем backend и реальном портале; временных API
и демонстрационных сервисов не создавалось. Изолированные тестовые doubles
применяются только внутри штатных автоматизированных тестов.

## Автоматические проверки

Команды запускаются из корня checkout с переменными окружения Skaro.

```powershell
docker compose exec -T frontend npm --workspace @chatballs/internal-ui run build
docker compose exec -T frontend npm --workspace @chatballs/internal-ui run test -- src/features/integrations/services/connect/SchemaFields.test.tsx --testTimeout=30000
docker compose exec -T frontend npm --workspace @chatballs/internal-ui run test -- src/features/integrations/services/model.test.tsx src/features/integrations/services/connect/SchemaFields.test.tsx --testTimeout=30000
docker compose exec -T frontend npm --workspace @chatballs/internal-ui run test -- src/features/integrations/model.test.ts --testTimeout=30000
docker compose exec -T backend-admin python manage.py check
docker compose exec -T backend-admin python manage.py makemigrations --check --dry-run
docker compose exec -T backend-admin python -m ruff check chatballs/integrations/adapters chatballs/integrations/service_connections chatballs/ai/diagnostic_redaction.py
```

Сборка прошла (TypeScript + Vite); остаётся предупреждение о размере chunks.
Пять тестов формы и девять тестов прежней модели интеграций прошли. Последний
прогон формы и разделения сетевых/авторизационных ошибок карточки: 11 passed. Django check:
ошибок нет; makemigrations: изменений нет; Ruff: ошибок нет.

Адресные backend-прогоны, все с `--reuse-db -p no:cacheprovider -q`:

| Область | Проверенные результаты |
|---|---|
| adapters + service_connections и непосредственно затронутые старые HTTP/MCP/network/i18n/redaction | 123 passed, 1 skipped; один MCP-тест времени повторён отдельно после нагрузки сборки |
| OAuth + schema/registry + отдельный MCP timeout | 26 passed; таймаут повторно прошёл |
| OAuth после fencing запоздавшего отказа | 11 passed |
| HTTP/files + runtime RLS | 16 passed |
| schema/registry после сохранения типов числового enum | 16 passed |
| legacy bridge и runtime RLS в следующем адресном прогоне | все 10 прошли; единственная ошибка ожидания пути в новом schema-тесте исправлена и его файл повторно прошёл |
| API подключений после разделения ошибок CRM/user | 13 passed |

Автоматические проверки покрывают обязательные handlers, вложенные схемы,
nullable/enum/date/file, расширения и версии контролов, запись HTTP без ложного
read-only, мост старых HTTP/MCP без изменения секретов/подтверждений, OAuth
state/user/tenant/refresh, RLS и файлы под runtime-ролью, redaction вложенных
секретов, redirects/SSRF, бинарные ответы и неопределённый исход записи.

Пропуск в i18n — проверка frontend-файлов, не смонтированных в backend-контейнер;
совпадение frontend-каталогов дополнительно проверяет TypeScript. Полный набор
тестов проекта не запускался. Известные прежние сбои диагностики/миграционного
теста и web-without-channel воспроизведены предыдущим исполнителем на базовом
коммите; их результаты находятся в истории задачи и не выданы за успешные.

## Проверка браузером

Task-local Playwright, ширины 1440 и 1024, светлая и тёмная темы. Тема проверена
через штатный профиль; первоначальная тема администратора — светлая.

- Каталог содержит только установленный Битрикс24. Открываются карточка,
  определение пресета и применимая форма входящего вебхука.
- Проверены ошибка формата ссылки, ожидание проверки и блокировка повторной
  отправки, успешная замена доступа реальным вебхуком, пауза и возобновление.
- Создан второй временный экземпляр: оба видны в списке, счётчик равен 2,
  сценарии «Не включены». Временный экземпляр удалён через подтверждение;
  исходное подключение сохранилось, счётчик снова равен 1.
- Подключение вызывает проверку чтением; бизнес-записи портала не создавались.
  После сохранения карточка/API не возвращают секретную ссылку.
- На 1024 окно восстановления помещается в viewport, кнопки не переносятся и
  нет горизонтального overflow. В тёмной теме фон окна — `rgb(27, 28, 31)`.
  Снимки и DOM-проверки сохранены в истории Playwright этой задачи.
- Согласованное исправление каталога проверено: две колонки по 315px на 1024
  и три примерно по 291px на 1440, кнопка и счётчик помещаются в карточке.
  Светлая тема профиля восстановлена и подтверждена ответом сессии.
- Локальный baseline нельзя открыть через `file:` в task-browser: протокол
  заблокирован инструментом. Сверка структуры выполнялась с исходным HTML;
  фактическая компоновка проверялась в штатном приложении.

## Внешние ограничения проверки

Портал успешно вернул пять стадий лидов. `user.get` отказал из-за разрешений
вебхука. Это blocker только реальной проверки справочника сотрудников; его
успешное чтение на портале не заявляется. Путь успешного чтения и отказа
проверен API-тестами. Для подключения достаточно CRM; пресет отдельно объявляет
необходимость CRM и пользователей. Права портала ради проверки не расширялись.

Одна повторная проверка получила `address_unresolved`. Отказ сохранён и показан
карточкой; последующая штатная замена доступа тем же разрешённым вебхуком
завершилась успешно и вернула «Подключено». Это проверка отказа/восстановления,
а не заявление о стабильности внешнего DNS.
Следующий реальный check вновь получил DNS-отказ. На нём браузером проверен
согласованный текст «Сервис не отвечает» в баннере и строке карточки; сообщение
об отзыве/истечении доступа для этой причины больше не выводится.

Реальное создание/изменение/удаление CRM-записей, выполнение пресета и OAuth
Битрикс24 не проверялись и не входят в проверенный пользовательский результат
подключения. Общие OAuth/подписи/сертификаты/длительные handlers проверены как
контракт, а не выданы за установленные способы доступа этого брендового пакета.

## Структура и архитектура

Новые компоненты разделены на API/model/state/subviews; страницы собирают
подкомпоненты. Новые файлы реализации меньше 300 строк, React-компоненты
меньше 180 строк. Большие существующие словари и shell-файлы получают только
точечные подключения маршрутов/каталогов, а не новую ответственность фичи.
Семантическая C4-модель хранится только в Skaro; authored Markdown не содержит
её копии или сгенерированных блоков. Решение по пакету и review точного
changeHash фиксируются квитанциями Skaro, отдельно от этого отчёта.
