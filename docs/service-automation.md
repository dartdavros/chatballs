# Автоматизация и обмен данными

Технический контракт T-172 дополняет docs/service-execution.md и
docs/service-scenario-runtime.md. Работает один backend, штатный PostgreSQL/RLS,
worker и worker-events; дополнительных служб нет. Требования и planned-покрытие
хранит общая C4-модель Skaro. Приёмка обоих baseline зафиксирована 22.10.2026
в SPEC-0037 R-28. Текущий документ не объявляет проверенным внешний сервис.

## Запуск и полномочия

Сохранённый ScenarioAutomation ссылается на администратора, явно разрешившего
запуск без сотрудника. Disabled/delegated=false, блокировка membership, отзыв
роли и изменение scope проверяются при launch и перед новым эффектом.
Копирование выключает делегирование; миграции не выбирают пользователя.
ActionGrant не создаётся. Вложенные Run пересекают полномочия всех предков.

launch_automatic передаёт проверенный вид инициатора общему launch; сохранение
snapshot, Run и outbox атомарно. Интерпретатор и эффектный ledger прежние.
Идентичность Run — tenant/scenario/trigger; ревизия отсутствует в dedup.
Явно делегированный автоматический запуск может выполнять записывающие шаги;
настройка confirm=always сохраняет отдельное подтверждение.

Сервисный webhook проверяется адаптером над исходными байтами. VerifiedEvent
содержит стабильный ID, схему payload, aware occurred_at, sequence/correlation,
causal_chain и необязательные проверенные entity_kind/entity_id. Организация
выводится из серверного подключения. Внешний payload не выбирает actor/tenant
или произвольный conversation ID. Контекст определяется явной EntityLink;
неоднозначный контекст не выбирается автоматически. Данные контекста строятся
после авторизации делегата с сохранением RLS/видимости.

## Доставка, cursor и расписание

Receipt зашифрован; outbox хранит ссылки. Подходящая аудитория EventSubscription
фиксируется EventDelivery до ACK. Один сценарий получает один Run события даже
при нескольких совпавших триггерах. Поздняя подписка не получает старое событие.
Каждая доставка имеет отдельную транзакцию. Частичный fan-out переживает падение;
успешные доставки не повторяют эффекты. Ожидаемый отказ одного не теряет других.
Watchdog выбирает pending/due deliveries порциями и восстанавливает работу даже
после исчерпания попыток одного outbox. Пауза подключения переносит доставку;
отзыв делегирования или отключение даёт безопасный остановленный исход.

Доменные hooks публикуют отдельный integrations.native_fact в транзакции домена.
В outbox нет клиентских текстов/контактных значений. Существующие handlers и
четыре вида правил не регистрируются заново. Native clocks фиксируют реальные
изменения контакта/диалога; время изменения старой записи не выдумывается.

PollResult — не более 100 VerifiedEvent, opaque cursor и retry_after.
Проверка каждого конверта выполняется до фиксации. Cursor двигается только
в транзакции с receipts/outbox. UUID fence, lease и сравнение прежнего cursor
отклоняют устаревший poller. Внешний I/O — вне транзакции, deadline 30 секунд;
polling делит ограниченные два worker-слота с исполнителем. Due/backoff независимы
по подключению, очередь отсортирована по due; dispatcher сообщений не ждёт I/O.

Расписание использует сохранённый часовой пояс организации, выбранные дни/дату,
daily/weekdays/monthly и число 1–28/последний день. Fold — first/second;
gap — skip либо первое существующее локальное время. При misfire=once берётся
последний пропущенный slot; skip не воспроизводит пропущенные. Для обычного
опроса предусмотрено окно до 60 секунд после slot. Слот и следующий checkpoint
фиксируются с запуском атомарно; UTC-slot + trigger ID не включают ревизию.

## Внешний API

POST /api/v1/scenario-triggers/{public-key-id}/
принимает Authorization: Bearer и обязательный Idempotency-Key (1–100 символов).
Тело: {"parameters": {...}, "conversationId": 123}; conversationId необязателен
и допустим только в текущей организации/области делегата. Ключ ограничен одним
сохранённым сценарием/trigger. Пользовательский tenant/actor/grants запрещены.
202 содержит ID и текущее состояние Run. Повтор ключа возвращает прежний Run;
перевыпуск Bearer прекращает действие старого секрета. Новый секрет показывается
один раз; пример запроса в редакторе использует реальный адрес установки.

## Связи и обмен

EntityLink хранит tenant, connection, виды сущностей и устойчивые IDs. Создание
через native entity_link.create входит в общий runner; локальная мутация и
nativeResult сохраняются одной транзакцией. После сбоя между доменной записью
и checkpoint повтор возвращает receipt. Снимок связей активного Run не меняется
при замене; новые Run используют новую связь. Контакт по email/телефону не ищется
для автоматического слияния. Публичный поиск только показывает кандидатов.

EntityReferences объявляет read/search operation, аргументы и проекцию кандидатов.
Замена требует завершённый разрешённый search Run и явный выбор ID из его
результата; снятие/замена проверяют текущую видимость и ревизию. Запись сервиса
не меняется. Битрикс24 использует существующий crm.*.list, фильтр ID либо
подстроку NAME/TITLE и явный выбор первой страницы; правила фильтра описаны в
[официальном контракте](https://apidocs.bitrix24.ru/api-reference/crm/contacts/crm-contact-list.html).

SynchronizationBinding задаёт read operation/arguments и EntitySnapshot
(values, version, modified_at, deleted), а также поддерживаемые conditional
update/delete operations и построение их аргументов с expected version/causality.
Адаптер отвечает за атомарную проверку expected version во внешней системе.
Отсутствие такого контракта не заменяется безусловной записью.
Битрикс24 объявляет чтение для входящего обмена; события и условная исходящая
запись не объявлены поддерживаемыми. Недоступное направление блокируется при
включении. Отказ чтения/доступа не считается доказанным удалением.

Каждая включённая native↔service пара/явная связь имеет отдельный checkpoint.
Цикл — один immutable Run: read → plan → повторное чтение/проверка версий →
нужные условные изменения → проверочное чтение → фиксация обработанных значений.
Все операции используют обычные lease/fence/effect keys/recovery/unknown.
Native-обновление вызывает общий сервис карточки контакта и штатные операции
жизненного цикла. Закрытый диалог не переоткрывается: это запрещено ADR-0001/
SPEC-0018. Создание собственной CRM или произвольная запись в доменные таблицы
не вводятся. Неизвестный/частичный результат остаётся виден по шагам.

Mappings направлены; обратная таблица статусов не выводится из прямой.
Несопоставленное значение не меняет получателя. Source-of-truth/latest/manual,
keep/unlink/поддерживаемое propagate исполняются явно. Baseline отражает только
обработанные значения, не поглощает более новое конкурентное изменение.
Совпавшие обработанные поля не создают обратный эффект. Causal chain и бюджет
глубины останавливают самопорождающиеся события общего механизма.

При manual конфликте Run приостанавливается в decision. OWNER/ADMIN выбирает
каждое поле в принятой композиции журнала. Digest, версии сторон, ревизия связи,
настройка и актуальные права проверяются снова; сохранение выбора не является
записью. Более новое изменение отклоняет устаревшее применение. Внутренние
версии/служебные параметры native steps не выводятся в пользовательском UI.
Неактивный обмен очищает obsolete значения по сроку операционных данных;
активные/неразрешённые Run сохраняют необходимые данные.

Автоматические контрактные адаптеры живут только в изолированных тестах и не
устанавливаются в рабочий каталог. Mock API/fake backend, seed и изменение
учётных данных для демонстрации не используются. Реальные внешние проверки
учитываются отдельно от контрактных тестов и browser-проверки приложения.

Связанная запись открывается только по HTTPS-адресу, который формирует
установленный адаптер локально. Query/fragment и credentials в адресе
запрещены. Битрикс24 возвращает только origin портала и путь карточки;
секретный путь webhook не передаётся браузеру. Отсутствие адреса не
подменяется поиском или выдуманной ссылкой.
