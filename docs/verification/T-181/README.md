# Проверка T-181

Проверка выполнена 2026-11-05 в штатном окружении `skaro-chatballs-t-181`, на копии данных Skaro. Использованы существующая учётная запись администратора и обычные API/формы приложения. Seed, подмена API, временные серверы и изменения доступов не применялись.

Адреса: приложение `http://localhost:20016`, backend `http://localhost:20014`, web-chat `http://localhost:20017`. Loader подключался с `http://localhost:20017/chat-widget.js` к настоящей странице приложения. Готовность frontend → backend проверена по `/api/v1/health/ready/`: database и Redis доступны.

Основание UI — лично принятый [baseline](../../../design/baseline/widget-site-events/OWNER-ACCEPTANCE.md), версия `69c2d5f6`. Архитектурный пакет «T-181: зафиксировать принятую границу реализации события сайта» применён Skaro, revision 17. Реализация planned-элементов становится current только при подтверждённой публикации.

## Автоматические проверки

- Сборки `@chatballs/web-chat` и `@chatballs/internal-ui`: `tsc` и Vite прошли. У internal-ui остаётся обычное предупреждение о размере существующих chunks.
- Основной адресный backend-прогон: 62 теста прошли. Дополнительные 7 проверок конфигурации/проекции каталога прошли; 6 из них повторяются в основном прогоне.
- Заключительный прогон `test_proactive.py`, `test_site_event_policy.py`, `test_proactive_status.py`: 9 тестов прошли с `--reuse-db`, включая 3 новых проверки терминальных состояний. Всего проверено 66 различных backend-тестов; повторные проверки пересекаются с основным набором.
- Очередь loader + память виджета: 9 тестов прошли. Проверяются неверные ранние кандидаты, выбор первого подходящего, отдельность от полей, instance/widget routing, ограничение очереди, исходный TTL, очистка stub, reload, позднее согласие и явный retry.
- `makemigrations --check --dry-run`: изменений не обнаружено. `origin` добавлен отдельной миграцией 0012, поскольку 0011 уже применялась в данных задачи. Обе миграции проверены при пересоздании только тестовой БД.
- Ruff изменённых Python-файлов прошёл. Новые компоненты и модули проверены по ограничениям размера; новые локальные компоненты меньше 180 строк, модули меньше 300 строк. Крупные существующие каталоги i18n получают только импорт отдельных словарей.
- Примеры новой справки ru/en исполняются проверкой [check-help.mjs](check-help.mjs): оба примера проходят реальный loader; TTL stub удаляет данные, исходный массив очищается при загрузке.

Backend выполнялся с `--reuse-db`. `--create-db` использован один раз после изменения схемы, только для тестовой БД. Полный набор тестов проекта не запускался.

## Штатный браузер и реальный провайдер

Ключ владельца сохранён формой Custom-подключения только в окружении T-181. Использован OpenRouter, модель `qwen/qwen3-30b-a3b-instruct-2507`. В Git ключ отсутствует. DEMO-провайдер не использовался для подтверждения первого ответа.

В этот интервал widget API не запрашивался, payload не отправлялся, панель оставалась `display: none`, фокус не менялся, событий message/call activity не было. `sessionStorage` содержал только техническое значение `1`, с ключом origin/widget. Пустая обязательная форма блокировала начало; заполнение имени до submit также не отправляло payload.

Ранняя очередь из одного события была обработана с уже актуальным серверным согласием, без новой формы и клиентского текста. Панель оставалась закрытой до ручного открытия. В истории появился один настоящий AI-ответ, обычный ввод доступен:

- SiteEventLaunch 1: `sent`, Conversation 32, Message 146.
- Run 1: `completed`; журнал содержит `created`, `claimed`, `request_sent`, завершение шага и Run.
- В этом диалоге ровно одно AI-сообщение и ни одной CONTACT-реплики.
- LLMInvocation 591: `agent_chat`, `SUCCESS`, выбранная реальная модель, 2716 входных и 56 выходных токенов.
- Счётчик LLM-вызовов организации вырос с 586 до 587 — один вызов.

## Закрытие, reload и настоящий TTL

Два отдельных анонимных окна браузера использовали тот же настоящий backend и loader, без аккаунтов/данных-заглушек.

- Приглашение на ширине 320 px закрыто штатной кнопкой. Повтор события не показал его снова и не передал payload.
- После reload повторный ранний event также не показал приглашение. В iframe сохранилась только техническая отметка `1`.
- В другом окне выдержан реальный срок: через 344754 мс приглашение отсутствовало. Часы браузера не ускорялись.
- После истечения срока посетитель открыл чат, заполнил обязательную форму и дал согласие. Payload события не отправился, сообщений нет, обычный ввод доступен, показан текст об истечении приглашения.
- После этой проверки остаются один Run, один маркер запуска, 131 сообщение организации и 587 LLM-вызовов. Дополнительный контакт создан только штатным поздним согласием, без обращения или AI.

## Компоновка настроек

Проверены выбор общего сценария и сохранение правила через штатный UI со статусом «Сохранено». Краткая проекция каталога содержит `nativeEvents`/`accessScope`, без полного `definition`; соответствующая проверка добавлена в backend-тесты.

На 320 px общая боковая панель скрывается как в принятом baseline; поля формы не выходят за карточку. Только таблица имеет горизонтальную прокрутку. Селектор таблицы измерен: 30 px высоты, padding `0 9px`, как в baseline. Обычный чат сохраняет прежний DOM без дополнительной обёртки; область первого ответа включается только для связанного события.

Проверены также английский язык и тёмная тема на 320 px: ширина документа ровно 320 px; карточка занимает x=16–304, поля x=39–281. Числовой тип показывает два ограничения, логический — прочерк. Меню действий целиком внутри viewport (x=82, ширина 220), закрывается по Esc. Изменения типов не сохранены; исходное текстовое поле и настроенный сценарий сохранены. Личные предпочтения администратора после проверки восстановлены штатным API: LIGHT, #1677ff, язык организации.
