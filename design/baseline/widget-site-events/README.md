# Приглашение по событию сайта — принятый baseline

Открыть [settings.dc.html](settings.dc.html) и [visitor.dc.html](visitor.dc.html) в браузере. Это автономные дизайн-документы x-dc/canvas, без сервера. Соседние ресурсы должны оставаться рядом. README не заменяет макеты.

Статус: **версия 69c2d5f6 лично принята владельцем 2026-11-04, S01–S07 и V01–V17**, см. [OWNER-ACCEPTANCE.md](OWNER-ACCEPTANCE.md). Сопоставление исправленной композиции с действующими формами: [SETTINGS-REFERENCE.md](SETTINGS-REFERENCE.md). Продуктовый UI, доставка событий, хранение, AI и серверные проверки не реализованы. Ни backend, ни mock API, ни временный HTTP-сервер не запускаются. Сценарии, сообщения и данные формы — иллюстрации внутри документа; они не создают записи проекта. Текст об этом, выбор кадров и управление временем находятся за пределами продуктового кадра.

## Просмотр

1. Настройки: S01 — новое выключенное правило; заполнить имя и приглашение, выбрать сценарий, задать поля и ограничения. «Сохранить» показывает результат только внутри документа. Ссылка на общий каталог открывает существующий `service-integrations/editor.dc.html`; редактор шагов не дублируется.
2. Приглашение: V01 → «Начать чат» → исходное согласие → «Принять и начать чат» → «Ответ подготовлен» над кадром. Ответ появляется без клиентского сообщения. При настроенной обязательной форме вход проходит через V03: исходная форма уже содержит согласие и не пропускает пустое обязательное имя.
3. V04 показывает текущую редакцию для посетителя со старым согласием. V05 — уже актуальное согласие и заполненная форма: панель остаётся закрытой, открывается launcher; повторного согласия нет.
4. V06: отправить обычное сообщение или нажать «Сотрудник перехватил», затем «Ответ подготовлен». Запоздалый проактивный ответ не появляется.
5. V01: «Ещё одно событие» сохраняет первое приглашение. Закрытие или Esc убирает его и возвращает фокус launcher. «Прошло 5 минут» убирает приглашение; V16 показывает позднее согласие без запуска. «Обновить страницу» в панели просмотра выбирает иллюстрацию V14, а не перезагружает приложение.
6. В верхней панели переключить ru/en, светлую/тёмную тему, ширину 320/390/768/1024/1440. Встроенный виджет сохраняет исходную светлую палитру независимо от темы рабочего места.

Переходы между кадрами сбрасывают иллюстративное состояние. Документ намеренно не является реализацией TTL, sessionStorage, сетевой очереди или дедупликации. Их требуемые результаты представлены кадрами и справкой; проверка реального поведения относится к задачам реализации SPEC-0040.

## Источники и принятые решения

| Область | Источник |
|---|---|
| WEB-страница, разделы, поля | `Веб-чат · поля и оформление/Веб-чат · поля и оформление.dc.html`; IntegrationPageLayout, SectionMenu, WebIntegrationBasics, HttpToolForm; исходные FormField, TextAreaField, SelectField, SwitchButton |
| Навигация, тема, кнопки, ссылки | SidebarNavigation, OrganizationSwitcher, Button, `.link`; те же presentation imports, что в widget-speech и service-integrations |
| Выбор сценария и схема | Общий каталог из service-integrations; SelectField; компактная таблица по CustomFieldsTable, antd Dropdown с app-dropdown/row-menu-button. Здесь только настройка события, без шагов сценария |
| Статусы и ошибки настроек | ServerEnabled/ServerSaveActions, импортированные ServerErrors и ServiceAlert; стили исходных форм и подключений |
| Launcher | `apps/backend/chatballs/webchat/loader_assets/launcher.js`: SVG, размеры 56×56, отступы 24, исходные pop/blink/hover/focus; build извлекает исходные значения |
| Открытие/закрытие | Полный исходный `genie.js`, 300/240 мс. Обёртка подключает DOM кадра; сетевой loader и Audio не исполняются |
| Панель | Геометрия `loader_assets/runtime.js`: 440×720, развёрнутая 820, снизу 92; ≤480 — весь кадр, launcher скрыт. Внутри исходные ChatHeader, ChatComposer, Bubble |
| Согласие/форма | ChatBody с исходным ConsentText, StartChatFooter, PreChatForm; новая форма согласия не создана |
| Загрузка | Исходный LogoSpinner/Loader; отдельная устойчивая область |

Лично принятые композиции: раздел «События сайта», поля правила, ограниченная схема события, блок выбора из общего каталога, приглашение над launcher с текстом/закрытием/«Начать чат», нейтральные состояния недоступности и ошибки. Их новые ru/en тексты находятся только в `copy-ru.js`/`copy-en.js` и читаются через `t`. Пример `category` с длиной 120 — редактируемое значение макета, не новый лимит API. Никакие внутренние идентификаторы сценария, секреты, номера спецификаций или сырые ошибки в кадры не выведены.

Фон сайта в visitor — нейтральная поверхность холста, не новый экран сайта. Существующие положение/иконка/анимации не переопределяются приглашением. Здесь выбран стандартный правый launcher и акцент существующего кейса «Обед»; настройки оформления продукта остаются за пределами этой задачи. Разница относительно прежнего baseline — только перечисленные новые композиции по SPEC-0040 R-18.

## Граница этапа и архитектуры

Это baseline задачи T-180 по SPEC-0040/ADR-0040. Проверяемые визуальные требования: R-2, R-5–R-7, R-12–R-14, R-16–R-19 и визуальная часть R-20. R-4/R-6 показаны без передачи данных; реальная изоляция, consent gate, outbox, дедупликация и AI не объявляются проверенными.

`get_c4_context` классифицировал изменения как `artifacts`, concrete problems отсутствуют. Семантическая модель и документы `.skaro` не менялись; новый архитектурный пакет не предлагается. `widget-site-events`, `ui-widget-event-settings`, `code-widget-site-events`, `code-ui-event-settings` остаются planned. Решение владельца по baseline для `Q-WIDGET-SITE-EVENTS-DESIGN` зафиксировано в OWNER-ACCEPTANCE.md; семантическая модель здесь не изменяется.

## Повторить проверку

При Node и Git в PATH из корня checkout:

```powershell
node design/baseline/widget-site-events/build.mjs
node design/baseline/widget-site-events/check-browser.mjs
```

Первая команда собирает только автономные документы из presentation-компонентов и проверяет словари/синтаксис/размер authored-файлов. Вторая открывает настоящие file:// документы в отдельном Chrome и сохраняет измерения и кадры. Зависимости берутся из существующего node_modules проекта; при необходимости доступен `BASELINE_NODE_MODULES`.

Штатный task-local Playwright блокирует file://. Для него build создаёт ignored `generated/open-{settings,visitor}.playwright.js`, загружающий те же ресурсы через setContent в about:blank; затем исполняются `checks/*.playwright.js`. Это не HTTP-сервер и не подмена API.
