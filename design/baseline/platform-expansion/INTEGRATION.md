## Согласованное исключение: супервизор

Решение владельца от 10.10.2026: «Сохранить отдельную роль SUPERVISOR; зафиксировать исключение для противоречащих элементов макета, остальные макеты использовать».

Сохраняются ADR-0033, SPEC-0029 и действующий контракт отдельной роли. Утверждение README «супервизор — полномочие поверх роли», выбранная роль «Сотрудник» при включённом супервизоре и пояснение «не роль» в E2–E4 не переносятся в реализацию. Форма назначения должна сохранять и показывать фактическую роль SUPERVISOR; отдельный булев признак поверх EMPLOYEE/ADMIN/OWNER не вводится. Для управления ролью использовать существующий компонент выбора роли; блок подконтрольных групп сохраняется отдельно от обычного членства. Остальная структура, состояния, визуальный язык и отдельное разрешение управления общими шаблонами сохраняются.

В E1, K7–K9, ST13–ST14 тексты и ограничения доступа интерпретируются в терминах отдельной роли. Супервизор не получает настройки, учётные записи и секреты; пустая область не означает всю организацию. Исключение не разрешает другие отклонения.

## Согласованные исключения: базовая статистика T-113

Решение владельца в чате T-113 от 14.10.2026: «Согласовать эти подписи и источник графика» и «Согласовать эти исключения для штатного API». Сохраняются серверные формулы SPEC-0030, R-3–R-5. Для ожидания и обработки используется подпись «суммарное время за период» и seconds; для первого и последующих ответов — «среднее время от начала ожидания ответа» и meanSeconds. Среднее не называется медианой. График по дням получает отдельные штатные отчёты с теми же фильтрами и границами дней в выбранном часовом поясе.

В меню CSV подпись — «таблица, разделитель «,»». Подготовка синхронного экспорта показывает «Готовим файл…» без вымышленного процента. При ошибке — «Не удалось подготовить файл. Попробуйте ещё раз.», кнопка «Повторить» и сохранение параметров. Ограничение 92 дня не вводится. Остальная структура базового макета сохраняется; эти решения не меняют серверные формулы и API.

После предложения конкретных правок и пояснения оставшегося ограничения владелец 14.10.2026 указал: «доделыывай и закрывай». Для завершения согласованного экспорта применяется описанный вариант: штатный API выгружает обращения, нагрузку и статусы вместе, подпись окна — «Файл соберётся по текущим фильтрам», строка «Раздел» удалена. Остальные строки параметров, порядок и расположение окна сохраняются; выбранная вкладка не передаётся как несуществующий параметр API.

## Согласованные исключения: правила обработки T-151

Решение владельца в проектном чате от 14.10.2026: сохранить действующий backend и остальной макет N14–N15, убрав неподдерживаемое условие и обещание удаления и исправив текст о версии. Условие «Рабочее время организации» не выводится; доступные условия берутся только из штатного серверного каталога. Обещание удаления событий старше 90 дней не выводится. Вместо выполнения по прежней версии используется текст «Изменение правила создаёт новую версию; ожидающие действия по прежней версии отменяются». Уже отправленные сообщения не удаляются. Календарь, автоудаление и изменение исполнителя в задачу не добавляются.

Полное решение сохранено в `.skaro/docs/handling-rules-ui-agreement.md`. Остальные структура, порядок, компоненты, визуальный язык и состояния N14–N15 сохраняются; пользовательские строки проходят i18n.

## Границы реализации

- Визуальные размеры, порядок, компоненты, иконки, тексты и состояния воспроизводить по HTML с учётом только явно согласованных исключений выше.
- Заголовки холста, номера кадров, описания триггеров, пометки для разработчика не входят в продуктовый UI. Служебная лексика внутри продуктового кадра также не переносится — действует AGENTS.md.
- Данные переписки, контакты, даты, числа, настройки и выбранные переключатели — примеры референса. Они не разрешают seed, fixtures, новые начальные настройки, автоматическое включение функций или изменение учётных данных.
- Шкала 1–5 со звёздами показана в дизайне; реальные шкала, подписи, сроки и права читаются из API. Старые результаты используют сохранённую шкалу/версию; смешанные шкалы не усредняются.
- Выпадающие меню — существующий antd Dropdown; ссылки — общая .link; пользовательские строки — i18n; цвета — существующие токены. Не копировать HTML-референс целиком в React.
- Большие экспортированные макеты и support.js — ресурсы дизайна. Они не отменяют DRY/SRP/NO GOD FILES для реализуемых компонентов приложения.
- Новые вкладки и пункты навигации появляются вместе с соответствующим работающим результатом. Не показывать незавершённые функции как готовые.
- Сроки и состояния очереди, почтовой доставки, рабочих статусов, AI и доступа определяет принятый API. Макет не является разрешением поменять их семантику.
- Обязательное состояние вне этих макетов и действующего baseline — отдельный design gate; его нельзя придумать самостоятельно.

## Просмотр и проведённая проверка

Рантайм использует CDN React и Babel, поэтому для обычного просмотра требуется доступ к указанным в support.js ресурсам. Относительные файлы support.js, chat-model.js, вложенные .dc.html и assets/ должны оставаться вместе.

В обычном Chromium открытие через file:// отображает основные кадры, но fetch вложенных «Редактор ответа» и «Передача диалога» блокируется. Поэтому инструкция исходного README «любой файл открывается напрямую» недостаточна для полной проверки чата. При работающем штатном Vite проекта макеты можно открыть через его разрешённый /@fs/ путь до этого каталога. Отдельный временный HTTP-сервер ради просмотра не запускать без разрешения владельца.

При подключении выполнен просмотр оригинальных файлов в Chromium/Playwright: шесть основных холстов, вложенные компоненты, светлая и тёмная темы; изображения загрузились, ошибок исполнения и блоков ошибок рантайма не обнаружено. Для вложенных компонентов использован предусмотренный support.js механизм __resourceBlobs с точным текстом оригинальных HTML, прочитанным с диска, без замены API или изменения макетов. Проверка относится к дизайн-референсам, а не к работающему приложению. HTTP-серверы, mock API, seed и изменения аккаунтов не использовались.

Браузерная проверка реализации приложения остаётся обязательной в задачах со штатным бэкендом. Сборка и тесты приложения при импорте макетов не запускались: код приложения не менялся.
