# hub.edevs.tech — спецификация внутренних экранов Hub

## 1. Назначение

Документ предназначен для проектирования дизайна внутреннего интерфейса `hub.edevs.tech`.

Он определяет:

- визуальное направление;
- каркас приложения;
- навигацию;
- роли и доступ;
- карту экранов;
- состав и информационную иерархию каждого экрана;
- обязательные действия и состояния;
- единые UI-паттерны.

Документ не описывает конкретные значения изменяемой бизнес-конфигурации: цены, тексты промптов, лимиты, пороги, сроки и правила отдельных Offer. Они отображаются и редактируются через предусмотренные интерфейсы.

## 2. Границы

### 2.1. Входит

Внутренний интерфейс для ролей:

- `OWNER`;
- `OPERATOR`.

Функциональные области:

- авторизация и профиль;
- командный центр;
- отделы;
- сотрудники;
- продукты и Offer;
- AI-агенты, знания, промпты, releases и test chat;
- интеграции;
- настройки;
- рабочее пространство отдела продаж;
- диалоги;
- клиенты;
- заказы, платежи, возвраты, подписки и выдача продукта;
- уведомления и аудит.

### 2.2. Не входит

- публичный Web Chat;
- публичный checkout;
- страницы success, pending, cancel и payment error;
- email-шаблоны;
- мобильный кабинет внутреннего Hub;
- интерфейсы будущих отделов.

Публичный Web Chat определяется `SPEC-HUB-0003-Web-Chat.md`. Публичное оформление покупки определяется `SPEC-HUB-0007-Checkout-UI.md`.

### 2.3. Утверждённый baseline готовых страниц

Фактически готовые страницы дизайна и статической вёрстки фиксируются реестром `SPEC-HUB-0005-Implemented-Internal-UI-Baseline.md`. Канонические файлы внутреннего UI находятся в едином каталоге `code/hub.edevs.tech/design/baseline/` вместе с другими утверждёнными дизайн-файлами проекта и являются обязательной основой реализации.

Экраны, отсутствующие в реестре, остаются специфицированными настоящим документом, но не считаются визуально спроектированными или свёрстанными.

## 3. Дизайн-система

Используется:

- **Ant Design**;
- **Ant Design X** для AI-чатов;
- собственная тема **Edevs Hub Theme**.

Основание: `ADR-HUB-0013-Internal-UI-Design-System.md`.

## 4. Принципы интерфейса

### 4.1. Командный обзор

Главный экран должен давать владельцу картину компании одним взглядом. Пользователь не должен переходить в отдел, чтобы понять общее состояние.

Основной управленческий сценарий:

```text
Обзор → доклад → погружение
```

### 4.2. Разделение уровней

Интерфейс явно разделяет:

```text
Уровень компании
→ Рабочее пространство отдела продаж
```

Глобальные настройки и сущности компании не смешиваются с операционной работой отдела.

### 4.3. Минимум визуального шума

- без декоративных dashboard-блоков без действия;
- без дублирования одних показателей в нескольких местах;
- без длинных форм на одном экране;
- без скрытых важных статусов;
- без цветных карточек ради оформления.

### 4.4. Полная работоспособность состояний

Каждый экран проектируется для:

- данных;
- пустого состояния;
- загрузки;
- ошибки;
- отсутствия доступа;
- частичной недоступности интеграции;
- сохранения и несохранённых изменений.

## 5. Целевые устройства

- основной дизайн: `1440 px`;
- рабочий диапазон: `1024 px` и выше;
- desktop-first;
- мобильная версия внутреннего Hub отсутствует;
- таблицы и inbox не должны требовать горизонтального скролла при `1440 px`;
- при `1024–1279 px` допускается скрытие вторичных колонок и компактный sidebar.

## 6. Каркас приложения

### 6.1. Общая структура

```text
┌──────────────────────────────────────────────────────────────┐
│ Sidebar │ Top bar                                            │
│         ├────────────────────────────────────────────────────│
│         │ Page header                                        │
│         ├────────────────────────────────────────────────────│
│         │ Content                                            │
└──────────────────────────────────────────────────────────────┘
```

### 6.2. Sidebar

Полная ширина: ориентировочно `240–256 px`.

Компактный режим: ориентировочно `64–72 px`.

Sidebar содержит:

- логотип и `Edevs Hub`;
- навигацию текущего уровня;
- индикаторы непрочитанных и критических событий;
- ссылку на профиль в нижней части.

Иконки — Ant Design Icons. Emoji как системные иконки не используются.

### 6.3. Top bar

Содержит:

- breadcrumb или контекстный путь;
- название текущего уровня;
- центр уведомлений;
- индикатор состояния и внимания при наличии системной проблемы;
- меню профиля.

Глобальный поиск не входит в первую итерацию.

### 6.4. Page header

Содержит:

- заголовок;
- краткое пояснение только там, где оно необходимо;
- primary action;
- вторичные действия;
- фильтр периода или контекста при необходимости.

### 6.5. Переход между уровнями

При входе в отдел продаж:

- sidebar переключается на навигацию отдела;
- в верхней части остаётся явная кнопка `Назад в Hub`;
- отображается `Edevs / Продажи`;
- цветовая тема не меняется.

## 11. AUTH-01 — Вход

### Назначение

Безопасный вход владельца и оператора.

### Состав

- логотип;
- название `Edevs Hub`;
- email/login;
- пароль;
- `Войти`;
- восстановление доступа;
- сообщение об ошибке.

### Поведение

- без маркетингового контента;
- одна компактная форма;
- после входа OWNER переходит в командный центр;
- OPERATOR — в диалоги отдела продаж.

## 12. AUTH-02 — Смена временного пароля

### Состав

- текущий временный пароль;
- новый пароль;
- подтверждение;
- требования к паролю;
- сохранение.

Пользователь не может перейти в приложение до успешной смены.

## 13. AUTH-03 — TOTP владельца

### Состояния

- первичная настройка;
- ввод одноразового кода;
- повторная проверка при входе;
- восстановление через предусмотренный административный процесс.

Экран не используется оператором, если TOTP для него не включён.

## 13.1. AUTH-04 — Восстановление пароля

### Назначение

Самостоятельное восстановление доступа сотрудником по ссылке из письма.

### Состав (запрос)

- рабочий email;
- отправка ссылки;
- подтверждение отправки письма;
- повторная отправка с задержкой;
- смена адреса;
- возврат ко входу.

### Состав (новый пароль по ссылке)

- новый пароль и подтверждение;
- индикатор надёжности и требования к паролю;
- состояние недействительной/просроченной ссылки;
- состояние успешного сброса и переход ко входу.

### Поведение

- ответ на запрос одинаков независимо от наличия аккаунта (без раскрытия регистрации адреса);
- ссылка действует 30 минут и одноразова;
- шаг задания нового пароля отдельного прототипа не имеет и использует визуальный язык `AUTH-02`.

## 14. HUB-01 — Командный центр

### Задача экрана

Одним взглядом показать владельцу текущее состояние компании.

### Первый визуальный уровень

1. Заголовок `Командный центр`.
2. Общий статус компании.
3. Карточки существующих отделов.
4. Критические события и системные проблемы.

### Карточка отдела продаж

Обязательные элементы:

- иконка;
- название `Продажи`;
- `NORMAL | ATTENTION | CRITICAL`;
- краткая детерминированная сводка;
- открытые диалоги;
- активные за 15 минут;
- на AI;
- на операторах;
- ожидают оператора;
- незавершённые платежи;
- ошибки выдача продукта;
- продажи и чистая выручка за период;
- действие `Открыть отдел`.

Карточка не должна выглядеть как большая CRM-панель. Она должна быть готова к отображению рядом с карточками будущих отделов.

### Дополнительные блоки

- `Требует внимания` — список критичных событий;
- `Состояние интеграций` — только проблемы и деградации;
- `Расходы AI` — текущий период и предупреждение бюджета.

### Состояния

- нормальное;
- attention;
- critical;
- нет данных;
- частичная ошибка одного провайдера.

## 20. AI-01 — AI-агенты

AI-раздел управляет агентами как рабочими точками владельца. Технический `ProductAIRelease` используется как механизм безопасной публикации изменений, но не является отдельной конкурирующей точкой настройки.

Основание UX-модели: `ADR-HUB-0017-AI-Agent-Configuration-UX.md`.

### Таблица

- имя;
- продукт;
- модель;
- активный release;
- статус;
- диалоги сейчас;
- стоимость за период;
- действия.

### Действия

- открыть агента;
- создать агента для продукта без агента;

Показывает:

- технический stack trace пользователю не показывается.

Недоступные страницы отсутствуют в навигации. При прямом переходе показывается понятный `403` с возвратом в доступную область.

4. Командный центр читается без перехода в отдел.

6. ProductAIRelease можно собрать, протестировать и опубликовать.
7. Offer и новая Price version управляются без редактирования истории.
8. Карточка заказа показывает payment, receipt, выдача продукта и право доступа отдельно.
9. Для ключевых экранов показаны loading, empty, error и attention states.
10. Компоненты соответствуют Ant Design и Edevs Hub Theme.
11. Нет интерфейсов несуществующих отделов и функций вне первой итерации.
12. Документ не требует использования конкретного инструмента дизайна.
