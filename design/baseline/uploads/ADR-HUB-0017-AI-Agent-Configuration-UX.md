# ADR-HUB-0017 — UX-модель создания и настройки AI-агентов

- Статус: Принято
- Дата: 2026-06-25

## Контекст

В первой итерации Hub использует одного основного sales-агента на продукт и публикует рабочую AI-конфигурацию через атомарный `ProductAIRelease`.

Технически это корректно: опубликованный release исключает смешивание модели, prompts, знаний, retrieval index, инструментов и лимитов. Но в интерфейсе возникают несколько конкурирующих точек управления:

- интеграция OpenRouter хранит API-реквизиты, разрешённые модели и инфраструктурные лимиты;
- карточка AI-агента показывает модель, лимиты, инструкции, знания и состояние агента;
- ProductAIRelease показывает состав публикуемой runtime-конфигурации;
- продуктовая карточка показывает связь продукта с sales-agent.

Для владельца это выглядит как несколько источников истины. При этом создание нового агента не должно превращаться в свободную мультиагентность, потому что первая итерация сохраняет правило «один основной sales-agent на продукт».

## Решение

### Карточка AI-агента — рабочая точка владельца

Владелец настраивает поведение AI через карточку агента. Карточка агента является основным UI для:

- выбора модели из разрешённых моделей AI-провайдера;
- изменения параметров генерации;
- изменения лимитов и бюджета агента;
- управления разрешёнными инструментами;
- редактирования prompt-документов;
- управления обязательными знаниями;
- запуска тестового чата;
- подготовки черновика версии;
- публикации новой версии агента.

ProductAIRelease остаётся доменной runtime-сущностью, но в пользовательском UI подаётся как «черновик версии агента» и как шаг безопасной публикации изменений агента.

### Интеграции — инфраструктура, не настройка поведения агента

Раздел `Интеграции` отвечает за AI-провайдера как инфраструктуру:

- API-реквизиты OpenRouter;
- состояние подключения;
- healthcheck;
- разрешённые модели;
- модель по умолчанию для новых агентов и новых черновиков;
- инфраструктурные лимиты провайдера;
- ротация секрета и журнал ошибок.

Интеграция не является местом настройки конкретного поведения агента. Если OpenRouter не настроен или нужная модель не разрешена, карточка агента показывает blocker и переход в интеграцию.

### Создание агента

В первой итерации сохраняется ограничение: у продукта может быть не более одного основного sales-агента.

Новый агент создаётся только для продукта, у которого ещё нет sales-агента. Допустимые entry points:

- блок `AI-агент` в карточке продукта;
- действие `Создать агента` в списке AI-агентов с обязательным выбором продукта без агента.

Если у продукта уже есть агент, UI не предлагает создать второго агента и вместо этого даёт переход в существующую карточку агента.

Создание агента выполняет:

1. привязку агента к одному продукту;
2. создание стартовой конфигурации из разрешённой модели по умолчанию;
3. создание стартовых prompt-документов;
4. выбор или создание обязательных knowledge-документов;
5. создание первого черновика версии агента.

Созданный агент не становится рабочим runtime-агентом до публикации первой версии. До публикации он находится в состоянии настройки.

### Изменение агента

Изменения в карточке агента не меняют runtime напрямую. Они формируют неопубликованное состояние агента:

- изменены инструкции;
- изменены знания;
- изменены модель или параметры;
- изменены инструменты;
- изменены лимиты.

Из неопубликованных изменений владелец подготавливает черновик версии агента. Черновик версии:

- показывает состав изменений;
- сравнивается с опубликованной версией;
- проходит validation;
- проверяется в тестовом чате;
- публикуется атомарно.

Опубликованный release immutable. Откат создаёт новый черновик версии на основе старого опубликованного снимка.

## Последствия

Положительные:

- у владельца появляется одна понятная рабочая точка настройки агента;
- OpenRouter остаётся инфраструктурной интеграцией, а не конкурирующей настройкой агента;
- ProductAIRelease сохраняет безопасность и воспроизводимость runtime;
- создание агента не ломает правило «один sales-agent на продукт»;
- первый запуск агента проходит через тестирование и публикацию.

Ограничения:

- нужен явный UI для состояния «есть неопубликованные изменения»;
- нужен сценарий создания агента для продукта без агента;
- baseline AI-01 и AI-02 должен трактовать черновик версии агента как шаг публикации, а не как самостоятельный объект настройки;
- мультиагентность остаётся вне первой итерации.

## Отклонённые варианты

### Создавать произвольное число агентов вручную

Отклонено, потому что первая итерация не поддерживает мультиагентную маршрутизацию и фиксирует одного основного sales-агента на продукт.

### Настраивать поведение агента в разделе интеграций

Отклонено, потому что интеграции управляют внешними провайдерами и секретами, а не продуктовым поведением sales-agent.

### Публиковать изменения prompt/knowledge напрямую

Отклонено по `ADR-HUB-0005` и `ADR-HUB-0007`: это создаёт риск смешанной runtime-конфигурации.
