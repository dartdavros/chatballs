# Контракт внешнего агента v1 — предложение

Дата: 14.11.2026. Основной файл: `../external-agent-v1.openapi.yaml`.
Основание: SPEC-0041, ADR-0041 и документы интеграции GoCoStack в Skaro.
Все файлы этой папки образуют одно предложение; серверы и runtime не реализованы.
Изменения спецификации и C4 применяются только после принятия пакета владельцем.

## Структура и границы

Уточнение владельца от 15.11.2026: внешнее исполнение — редкая возможность,
исходно выключенная в настройках организации. OWNER/ADMIN включают её и там же
настраивают подключение исполнителя, параметры и сопоставление externalAgentId.
Только после включения в карточке агента выбирают подготовленное внешнее исполнение;
реквизиты и параметры там повторно не настраиваются. Каталог CRM и других
бизнес-интеграций не является местом подключения исполнителя. Внутреннее
переиспользование SERVICE/ADAPTER, credentials и защищённого транспорта сохраняется.

Действующее включение возможности проверяется сервером вместе с текущим
разрешением внешнего исполнения; скрытие выбора в UI не является защитой.
Выключение не удаляет настройки и не переключает агентов на builtin автоматически;
повторное включение не оживляет отозванные полномочия. Нормативные условия —
SPEC-0041/ADR-0041; JSON-форматы, HTTP-пути и версия протокола этим размещением
настроек не меняются.

OpenAPI 3.1.1 использует JSON Schema 2020-12 и локальные `$ref`.
`paths-*` описывают 12 операций двух сторон, остальные YAML — предметные схемы.
`examples.yaml` содержит положительные и отрицательные контрактные примеры.
`canonicalization.yaml` фиксирует точные байты канонизации и равенство повторов.
Для переноса нужно передавать основной файл вместе со всей папкой.
Основание формата: https://spec.openapis.org/oas/v3.1.1.html.

Адреса `.example.invalid` иллюстративны. `GoCoStackBearer` и `ChatballsBearer` —
разные ключи. Перед проверкой повторов проверяются ключ, подключение, tenant и
принадлежность объекта. Тела закрыты для неизвестных полей, кроме данных шаблона,
которые отдельно проверяет штатный `skill_templates/schema.py`.
`organizationId`, произвольные URL файлов, HTML, srcDoc, команды и patch контакта
не принимаются. Внешний режим не получает инструменты и native actions Chatballs.

Весь JSON в каждом направлении ограничен 262144 байтами UTF-8, включая ответы.
Лимит файла — не более 20971520 байт плюс штатные более узкие ограничения.
Лимит тела JSON не применяется к binary multipart, но остальные части и заголовки
ограничивает штатный upload handler. Сжатие не обходит ограничения после распаковки.
Дубликаты ключей JSON, невалидный Unicode, NaN/Infinity отклоняются до обработки.
Ничего не обрезается скрытно; неумещающийся trigger/полный блок полей — ошибка
подготовки и штатная передача сотруднику. Сетевые тела/значения не попадают в журнал.

## Обязательность, направления и файлы

`required` и `type: null` различаются: отсутствие обязательного поля — ошибка.
Все схемы задают это явно. `externalSessionId` передаётся и при null; первое
присвоение разрешено, после него изменение в той же привязке — конфликт.
`customer.id` может быть null только при фактическом отсутствии контакта;
тогда `fields`, `customFields.scope/items` пусты, чужой контакт не подставляется.
`language.requested` строка только при fixed, иначе null.
Стандартная карточка экспортирует выбранные `name`, `email`, `phone`.
Неизбранные ключи отсутствуют; выбранное пустое значение сохраняется как строка.

`capabilities.directions` задаёт два направления, `contentTypes` — их объединение.
Полный v1 требует всех описанных форматов в своих направлениях; фактический канал
сужает `deliveryConstraints.types`. Ограничение текста по символам, если объявлено,
считается в Unicode code points; дополнительно проверяется транспортное представление.
Контактное сообщение — сохранённый публичный текст, без придуманной vCard.
`contact_request` содержит только type: штатный текст берётся из словаря организации.
Шаблоны возвращают `dataSchema` в существующем формате CB (type object/list/...),
это не JSON Schema; ревизия целочисленная, монотонная и не переиспользуется.
WEB получает безопасный снимок, остальные каналы — штатный текст.
История formatted отдаёт сохранённый текст, не исполняемое представление.

Upload — multipart с uploadId, authorizationId, file, sha256; Idempotency-Key=uploadId.
Имя и MIME берутся из части file, проверяются; путь/CR/LF в имени запрещены.
Сервер проверяет реальные байты, digest, тип, размер, квоты и текущую связь.
201 — новый полный файл, 200 — его повтор. expiresAt исходно задаётся на 24 часа;
активные ссылки защищают нужный файл, повтор сам срок не продлевает.
Метаданные в результате сверяются с сохранённым файлом, не задают их заново.
GET file требует authorizationId в query и разрешённый fileId из trigger/снимка
истории/своего upload. Знание ID следующего клиентского файла не обходит FIFO.
Исходное голосовое недоступно. v1 не требует Range; полный ответ — 200.

## Снимок истории и порядок

История использует query `authorizationId`, `snapshotCursor`, необязательные
`pageCursor`, `pageSize` (1–200, по умолчанию 50). Это параметры, не секретные ключи;
query с разрешениями/курсорами не записывается в access log.
Курсоры непрозрачны, не более 4096 символов, криптографически защищены/проверены
сервером и связаны с подключением, диалогом, разрешением, политикой и снимком.
Срок snapshotCursor/pageCursor заканчивается не позже deadlineAt исходного request.
Истечение — 409 snapshot_expired; продление повтором или чтением не выполняется.

Пагинация идёт назад, каждая страница упорядочена вперёд. Первая страница без
pageCursor начинается от верхней границы снимка. Inline-окно — его хвост;
inline.nextCursor указывает страницу перед окном, без дублирования.
При inline=0 и наличии истории nextCursor указывает первую страницу.
hasMore/truncated равны наличию соответствующего nextCursor.
Страницы добавляются перед уже полученной историей; ID используются для дедупликации.
pageSize — максимум: JSON-лимит может уменьшить страницу, не сообщение.
Один неумещающийся элемент — 413, без бесконечных пустых страниц с тем же курсором.
Пустая страница из-за удалений допустима только с продвижением курсора.

Граница логическая: предыдущие обработанные ходы и публичные ответы включаются,
trigger и следующие необработанные клиентские сообщения исключаются даже при
несовпадении физического времени записи. Удалённые сведения не восстанавливаются.
Голосовое представляется только реальной сохранённой стенограммой + wasVoice/source;
при её отсутствии страница/контекст возвращает history_content_unavailable,
без выдуманного текста или молчаливого пропуска. Для текущего trigger штатная
подготовка выполняет STT; её сбой передаёт обращение сотруднику.
GET шаблонов и доставки тоже требуют authorizationId в query.
Отзыв закрывает чтение, в том числе по старым курсорам и fileId.

## Равенство повторов и канонизация

Для каждого вида операции ключ дедупликации scoped по подключению и виду операции:
requestId, (requestId,resultId), deliveryId, eventId, uploadId. Дополнительно один
request допускает только один неизменяемый terminal результат, независимо от resultId.
Область digest включает маршрут (связь/диалог/request), все поля тела и порядок массивов.
Сетевые заголовки/попытки, пробелы и порядок ключей JSON не включаются.
Отсутствующее поле отличается от null; bool отличается от числа.
Unicode не нормализуется, эквивалентные JSON escape-последовательности декодируются.
Числа сравниваются по точному десятичному значению, без округления через float/double.
Поэтому 1, 1.0 и 1e0 равны; 9007199254740992 и 9007199254740993 различаются.
Это сохраняет существующие типизированные number-поля CB, включая большие integer.

Нормативное каноническое дерево C(x):

| JSON | C(x) |
|---|---|
| null | `["null"]` |
| boolean | `["boolean", x]` |
| string | `["string", x]` |
| number | `["number", n]`, где n — строка нормализованного десятичного числа |
| array | `["array", [C(x0), C(x1), ...]]` |
| object | `["object", [[k0,C(v0)], [k1,C(v1)], ...]]` |

Ключи объекта сортируются по Unicode scalar values. n имеет вид `[-]ceE`:
коэффициент c без ведущих/хвостовых нулей, целый показатель E без плюса и ведущих
нулей; ноль всегда `0e0`. Примеры: 1200 → `12e2`, 1.20 → `12e-1`, -0 → `0e0`.
C(x) сериализуется компактным JSON в UTF-8; строки экранируются по RFC 8785 §3.2.2.2,
без нормализации. Полный JCS не применяется: его IEEE 754-модель чисел сузила бы CB.
Основание ограничения JCS: https://www.rfc-editor.org/rfc/rfc8785.html#section-3.2.2.3.
Chatballs хранит HMAC-SHA-256 канонических байтов с защищённым ключом дедупликации;
смена HTTP-credential не меняет этот ключ. Digest не является HTTP-подписью,
не передаётся в протоколе и не требует одинакового секрета у двух сторон.
Для multipart C включает uploadId, authorizationId, проверенные filename/mimeType,
size и sha256 реальных байтов; boundary/порядок частей не значимы.

## Терминальные итоги, ACK и отправка

Первый POST requests возвращает 200 TerminalResult либо 202 после durable записи.
Повтор зарегистрированного запроса возвращает 202 accepted/processing/unknown,
или 200 неизменяемый completed/failed/cancelled. unknown не запускает новую работу.
GET status возвращает состояние без дополнительной обёртки. Для cancel уже
сохранённый failed, как и completed, возвращается неизменным.
Callback принимает только completed/failed; unknown/cancelled читаются GET/status.
Локальная отмена не зависит от успешности cancel. Все сетевые повторы — те же ID.
Сроки и очередность SPEC-0041 сохраняются: HTTP 10с, обычный deadline 120с от trigger,
долгий срок настраивается (default максимум 24ч), retry 1/5/15с, poll 5/15/30с,
затем 30с; время не продлевается. Retry-After ограничен остатком deadline.

ACK callback сохраняется до HTTP-ответа: 202 только для нового queued набора;
200 для повтора, handed_off, failed и suppressed. failed результат передаёт диалог
в штатную очередь, квитанция имеет deliveryId:null/items:[], клиентского сообщения нет.
Для handoff reasonCode берётся из принятого события, для failed — безопасный code,
для suppressed — код из SuppressionCode. summary видит только сотрудник.
Поздний результат при действующем ключе получает безопасную suppressed-квитанцию;
противоречие ранее принятому terminal результату остаётся 409.

Произведённый самой операцией handoff отзыв не препятствует её точному повтору:
после проверки действующего ключа/tenant/принадлежности и прежнего digest возвращается
только её content-free квитанция. Это узкое исключение для своего eventId;
иной отзыв/смена настроек не разрешает повторное действие или чтение данных.
Повтор не выполняет handoff заново и не восстанавливает authorizationId.
Для прочих инициативных отправок текущая авторизация проверяется и при повторе.

Состав набора валидируется целиком до принятия, itemId уникальны. CB выделяет
deliveryId синхронному/callback reply, сервис задаёт его только для инициативы.
Одному item соответствует одно Message. Перед сохранением и передачей каждого
элемента проверяются срок, текущие версии, полномочия, очередь и канал.
Рендер и WEB-публикация считаются отправкой: проверка предшествует публичной записи.
Следующий набор не обгоняет предыдущий. При queued-элементах aggregate=queued;
если queued нет и все одинаковы — это состояние; иначе partial. Состояния items
первичны. unknown блокирует автоматическое продвижение доставки до достоверного
разрешения/штатной передачи сотруднику, не превращается в успех или новый ответ.
transport_accepted не означает прочтение; при unknown нет слепого повтора.

## Ошибки и дополнительные серверные проверки

| HTTP | Коды |
|---|---|
| 400 | invalid_request, unsupported_version |
| 401 | invalid_credentials |
| 403 | permission_denied, proactive_disabled |
| 404 | resource_not_found (также чужой объект) |
| 409 | idempotency_conflict, result_conflict, control_changed, conversation_busy, channel_restricted, template_revision_changed, snapshot_expired, history_content_unavailable |
| 413 | payload_too_large |
| 422 | unsupported_content |
| 429 | rate_limited |
| 503 | temporarily_unavailable |

retryable=true допустим для conversation_busy, rate_limited, temporarily_unavailable,
history_content_unavailable при сохранении полномочия/срока. Для остальных кодов
повтор без изменения условий не назначается. Это не разрешение нового requestId.
Причины handoff перечислены в common.yaml#/ReasonCode; новые причины требуют
согласования схемы. Произвольный текст summary не становится клиентским сообщением.

OpenAPI не доказывает транзакционные инварианты. Реализация отдельно проверяет:
ID URL/заголовка/тела, deadlineAt позже createdAt и в разрешённом сроке,
единственный terminal, совпадение пар scope/items,
allowlist/tenant/поколение схемы A→B→A, монотонный turnSequence, отсутствие отката
снимков, уникальность itemId, принадлежность файлов/шаблонов, enum/форматы полей,
актуальность полномочий и дедупликацию действий GoCoStack. Проверочные примеры
в YAML покрывают форму и отдельные нарушения; приёмка требует реального сервиса.
UI остаётся за отдельным design gate. Данный пакет не утверждает layout или тексты UI.

## Воспроизводимая проверка артефакта

Из корня репозитория: Python с `openapi-spec-validator==0.9.0`, `PyYAML==6.0.3`
и их зависимостями, затем `python packages/contracts/external-agent-v1/verify_contract.py`.
Зависимости проверки устанавливаются в отдельное окружение, не меняют зависимости
приложения. Проверяются OpenAPI, все локальные ссылки, 12 операций, допустимые/
недопустимые примеры и векторы канонизации. Скрипт не запускает сервисы, не обращается
к реальным API и не заменяет интеграционную приёмку. Сборка приложения для этого
документального изменения не выполняется.
