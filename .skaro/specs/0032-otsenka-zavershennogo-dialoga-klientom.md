# Оценка завершённого диалога клиентом

Предлагаемое расширение для этапа M17; источник — соответствующий пункт документа «Функциональные требования к расширению платформы» от 06.10.2026. Этот документ описывает планируемое поведение.

## Problem

После закрытия нет связанной с обращением оценки обслуживания. Запрос должен быть управляемым, адресованным клиенту и защищённым от повторных запусков и доступа к чужой истории.

## Scenarios

1. Завершение обращения запускает отложенный запрос согласно настройкам организации; клиент оценивает и оставляет комментарий.
2. Повтор обработки завершения не создаёт второй запрос; повтор отправки ответа на форму не создаёт вторую оценку.
3. Клиент открывает WEB-запрос спустя более 7 дней и после перезагрузки, оставляет оценку без ошибки просрочки; повтор возвращает прежний результат без второй записи.
4. Супервизор видит оценки подконтрольных обращений; публичная ссылка показывает только вопрос и форму, а не переписку.

## Requirements

- R-1. Организация хранит отдельное включение оценки, определение шкалы с допустимыми значениями и подписями, текст запроса и задержку после завершения. Управляют OWNER/ADMIN; исходно функция выключена, до настройки шкалы и текста запрос не отправляется. Форма пустой выключенной конфигурации предзаполняется значениями из утверждённого макета N10: шкала 1–5 с подписями, текст запроса и задержка 10 минут. Сервер предлагает их отдельно от сохранённых значений, на языке организации; чтение не записывает настройки и не включает опрос. Сохранение выполняется явным действием администратора; настроенные значения не заменяются предложениями.
- R-2. По событию завершения создаётся не более одного запроса для пары диалог и идентификатор завершения. Настройки и шкала фиксируются снимком на запрос; изменение будущей шкалы не переинтерпретирует старые оценки.
- R-3. Отправка выполняется штатным фоновым контуром не раньше заданного срока; перед отправкой проверяются включение, существование обращения и возможность доставки. Повторный запуск/ретрай не создаёт второй клиентский запрос.
- R-4. Поддерживаемые каналы задаются явно и документируются адаптерами. Универсальный вариант — связанная форма по ограниченной непредсказуемой ссылке, доставляемой поддерживаемым транспортом; нативная оценка допускается только после принятого контракта соответствующего канала.
- R-5. Публичный credential хранится хешем, ограничен конкретным запросом, не выдаётся в логах и не даёт доступа к истории, контакту, сотрудникам или иным запросам. WEB-запрос оценки и его credential не имеют срока действия: давность отправки не препятствует чтению вопроса и приёму оценки. Это относится к новым и уже отправленным запросам, включая ранее просроченные, если они не отменены и связанные данные существуют. Сохраняются непредсказуемость credential, штатные ограничения частоты, изоляция и неизменяемость единственного результата. Отмена и удаление данных остаются основаниями недоступности. Поведение остальных каналов этим исправлением не расширяется.
- R-6. Результат содержит допустимое значение шкалы, необязательный ограниченный комментарий, время и запрос. Приём атомарен; предлагается одна неизменяемая оценка по запросу, повтор той же операции возвращает результат, попытка заменить значение получает конфликт.
- R-7. Оценка связывается с диалогом и снимком фактически отвечавших сотрудников, а не просто добавленных участников. Для сводных отчётов одна оценка считается один раз; вклад каждого сотрудника не приписывается последнему ответственному автоматически.
- R-8. По результатам действуют текущие права: OWNER/ADMIN — организация, супервизор — область контроля. Доступ обычного оператора к оценкам требует отдельного решения; до этого сервер его не выдаёт.
- R-9. API настроек, планирование, получение публичного вопроса и приём оценки, защищённая выдача результатов и событийная интеграция отчётов реализуются отдельными задачами. Смешанные шкалы не усредняются как одинаковые числа без согласованной нормализации.
- R-10. Публичная форма, настройка и вывод в карточке/отчётах требуют baseline; клиентский текст задаётся настройкой на языке организации, штатные подписи и ошибки — словарями.

## Out of scope

Повторное редактирование оценки клиентом, опросы с несколькими вопросами, автоматическая оценка сотрудника по последнему назначению, незаявленные нативные кнопки каналов.

## Open questions

- Какие шкалы и каналы включить в первый выпуск, может ли обычный оператор видеть результат? Решения блокируют соответствующие настройки, доставку и выдачу, но не изолированное хранение и защиту API.
- Нужны макеты клиентской формы, настройки запроса и результата.

## Порядок реализации и проверки

Сначала реализуются небольшие серверные задачи: модели и миграции, сервисы, API и фоновые операции. У каждой задачи самостоятельные критерии, ссылка на эту спецификацию и зависимости от конкретных серверных функций. Приёмка бэкенда не требует нового интерфейса; проверка проводится в штатном контуре проекта, без самостоятельно созданных заглушек, seed и изменений учётных данных. Сборка и только относящиеся к изменениям тесты — по правилам проекта.

Фронтенд выделяется в отдельные задачи после соответствующих API и утверждения baseline с необходимыми состояниями. Спецификация задаёт поведение, а не макет: расположение, компоненты, иконки, цвета и тексты UI не изобретаются. При отсутствии макета конкретного состояния интерфейсная задача не запускается. UI проверяется в браузере с реальным бэкендом.

Организация и действующие права проверяются на сервере в HTTP, realtime и фоне; персональные данные и секреты не раскрываются другой организации. Пользовательские тексты проходят существующую i18n; все вызовы AI — действующую псевдонимизацию. Не требуется полный прогон тестов для каждой задачи.

## Исправление релиза — 05.11.2026

Решение владельца: WEB-оценка никогда не просрочивается по времени. Семидневный срок сейчас проверяют web_delivery.py/public_service.py и триггеры/защищённый directory PostgreSQL. Исправление охватывает весь путь, включая новые штатные миграции: прежние credential, снимки, результаты, привязки и отмены сохраняются. API достоверно передаёт отсутствие срока без фиктивной далёкой даты. Недоступность неизвестного/отменённого/удалённого запроса не называется временной просрочкой. Проверки — адресные backend-тесты с --reuse-db и браузер в штатном контуре. Изменения production в объём этой задачи не входят.
