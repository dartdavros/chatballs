# Подключение Битрикс24 входящим вебхуком

## Основание и границы
В T-168 владелец выбрал «Плюс первый брендовый адаптер» и предоставил реальный доступ для проверки. Это дополнение к SPEC-0037 оформлено отдельно согласно требованию документации SPEC-0037. ADR-0038 сохраняется. Источник UI — лично принятый «Сервисы.dc.html» основной копии, только для чтения; дизайн-файлы и новое меню настроек не переносятся в ветку.

T-168 поставляет пакет, подключение/карточку, схемы/справочники и определение пресета. Копия/редактор — T-169, запуск/связи/события — последующие задачи. Обработчик адаптера не является публичным разрешением выполнить действие.

## Требования
- R-7. Справочник ответственных Битрикс24 показывает полное доступное имя сотрудника из NAME/SECOND_NAME/LAST_NAME с удалением пустых частей и лишних пробелов. Если имя отсутствует, показывается EMAIL; ID используется только при отсутствии имени и email. Значением выбора остаётся ID Битрикс24, а не отображаемая подпись. Пустые и пробельные значения не скрывают доступный email. Ошибки доступа к справочнику остаются ошибками и не заменяются фиктивными сотрудниками.
- R-8. В прямом ручном создании лида/контакта Битрикс24 из диалога адаптер явно сопоставляет известное имя контакта с fields.NAME, телефон с fields.PHONE и email с fields.EMAIL. Телефон/email преобразуются в предусмотренные схемой массивы объектов VALUE с допустимым VALUE_TYPE через существующий типизированный механизм преобразований; сохраняются все известные значения, которые доступны в штатной модели контакта, без дублирования и выдуманных данных. Известная фамилия подставляется только при наличии отдельного достоверного источника; полное имя не делится эвристикой. Начальные значения видны до ручного ввода, редактируются и очищаются; точный preview и запуск используют отредактированное значение. OWNER/стадия/название не заполняются предположениями. Для сохранённых сценариев сохраняются их явные привязки и параметры. Доступ к текущему контакту и все штатные проверки исполнения сохраняются.
- R-1. bitrix24 версии 1 регистрируется общим реестром установленных модулей. Каталог содержит только установленные пакеты. Несколько именованных подключений изолированы организацией, не требуют Channel/AIAgent; enum бренда и ветвлений ядра нет.
- R-2. Доступ — HTTPS-ссылка входящего вебхука, хранится зашифрованно; наружу после сохранения выдаётся только хост. Проверка вызывает scope и требует crm; user дополнительно нужен справочнику ответственных/пресету. Проверка, пауза/возобновление, замена доступа и удаление подключения не создают и не меняют записи портала.
- R-3. Дескриптор описывает create/get/update/delete/list для lead/contact/deal, batch, чтение разрешений, пользователей и стадий лидов. Собственные схемы Битрикс24 сохраняют вложенные телефон/email и дополнительные vendor-поля; API выдаёт схемы входов/результатов. Доступность методов зависит от прав сотрудника, разрешений вебхука и возможностей портала.
- R-4. Пресет create_lead_from_conversation версии 1 содержит назначение, обязательные подключения/права crm/user, параметры ответственного/стадии, ручной запуск, условия контакта/отсутствия связи и упорядоченные шаги создания лида/сохранения связи. В T-168 выдаётся определение, без автокопирования/включения/запуска. Кнопки редактора и ссылки создания/списка сценариев скрыты до T-169 по решению владельца.
- R-5. Пакет использует общий защищённый транспорт, штатные tenant/RLS/шифрование/redaction. Запись не маркируется read-only. Потерянный или непригодный ответ после записи допускает неизвестный исход без слепого повтора. События явно не поддерживаются. crm.lead/contact/deal.* — документированные legacy-методы; универсальные CRM-сущности, OAuth Битрикс24 и длительные операции этим пакетом не заявляются.
- R-6. Приёмка включает адресные тесты контракта/схем/секретов/tenant/совместимости, сборку и browser-проверку штатного приложения на реальном разрешённом вебхуке. Бизнес-записи не создаются ради демонстрации подключения; реальные эффекты не объявляются проверенными. Документация контракта и справка ru/en поставляются вместе с кодом.

## Дизайн
Принятый baseline сохраняется. Согласованные владельцем отличия: «Возобновить» и серый статус «Приостановлено» после паузы; действия редактора скрыты до T-169. Новые состояния без решения владельца не придумываются.

## Архитектурное покрытие
Общая модель покрывает контекст, контейнеры, компоненты, код, deployment и упорядоченную настройку. Внешний портал — external-business; внутренние компоненты/код/deployment вне контроля Chatballs и имеют существующие доказанные исключения. Новых обязательных служб нет. Все элементы planned до проверенной публикации; готовность подключения не равна готовности всего этапа.

## Решение адаптивности каталога

После фактической проверки владелец выбрал две колонки на узкой рабочей области (1024), вместо сжатия трёх колонок с переносом кнопки. На 1440 сохраняются три колонки baseline. Внутренние структура/порядок/тексты/стили карточки не меняются; порог 868px контейнера соответствует трём карточкам по 280px и двум gap по 14px.

## Решение сетевых ошибок карточки

После реального DNS-отказа владелец выбрал существующие локализованные причины из API в том же баннере и строке состояния карточки. Сетевой сбой не описывается как отзыв или истечение доступа. Для авторизационных ошибок сохранены тексты baseline; компоновка и действие восстановления не меняются.
