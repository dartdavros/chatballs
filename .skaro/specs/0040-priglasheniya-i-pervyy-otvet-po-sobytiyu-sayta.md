Целевое поведение, ещё не реализовано. Этот файл применяется только после принятия единого пакета. Приёмка спецификации не означает приёмку макета или готовность кода.

## Проблема

Сайт обнаруживает событие, Chatballs показывает настроенное приглашение и после согласия запускает сценарий, в котором AI может написать первым. Нужны сохранение consent gate и общего runner. Основания: решения владельца 03.11.2026, SPEC-0001/0002/0019/0020/0037, ADR-0031/0038/0040.

## Сценарии

1. Сайт вызывает emitEvent до загрузки; отдельная очередь сохраняет событие.
2. До начала чата посетитель видит/закрывает локальное приглашение без обращения и вызовов провайдеров.
3. После принятия приглашения, согласия и формы сценарий инициирует первый ответ без фиктивного текста клиента.
4. С действующим согласием событие запускается без повторного приглашения и первой реплики.
5. Повторы/вкладки/падение не создают второй Run/ответ.
6. Клиент пишет сам или сотрудник перехватывает; запоздалый первый ответ подавляется.

## Требования

- R-1. Событие обнаруживает и передаёт сайт; Chatballs сопоставляет его с явной настройкой. Не добавляются встроенные DOM/scroll/таймеры/аналитический трекер.

- R-2. Правило WEB содержит стабильный ID, имя события, ограниченную типизированную схему data, текст приглашения, сценарий той же организации и включённость. Новое правило выключено. Публична лишь часть приглашения, не внутренний сценарий/IDs/шаги/полномочия. Сайт не выбирает агента, инструкции или произвольный сценарий.

- R-3. JS API: Chatballs.emitEvent({widgetKey,name,eventId,data}). widgetKey изолирует экземпляры, eventId устойчив для повторов одного события. Отдельная очередь работает до загрузки, сохраняет старые setFields/q/legacy. postMessage проверяет origin/source/instance. setFields сам не запускает сценарий; схема и ограничения опубликованы.

- R-4. До начала чата сопоставление с публичным правилом и показ приглашения локальны. Payload не отправляется backend/провайдерам, нет сценария/LLM/контакта/обращения. Для подавления повтора допустима лишь техническая отметка правила в sessionStorage с изоляцией origin/widgetKey без data/ПДн.

- R-5. Приглашение не открывает панель принудительно, не создаёт звук/unread/сообщение. Можно принять или закрыть. Принятие проходит действующие согласие и обязательную форму; актуальное согласие не переспрашивается без смены версии. Точное управление — по лично принятому baseline, текущий launcher/анимации сохраняются.

- R-6. До согласия одно первое подходящее событие в памяти не вытесняется следующими. Закрытие удаляет data и подавляет то же правило до конца сессии вкладки, включая reload. TTL 5 минут; истёкшее не запускается после позднего согласия. Payload не переживает reload, сайт может повторить eventId, но отметка подавляет повторное приглашение; это объяснено в справке.

- R-7. После актуального согласия и серверной проверки обязательной формы событие передаётся через WebSession. Общий сервис хранит принятую версию и проверяет её перед запуском/эффектом, старый токен/флаг не обходят gate. При уже действующем согласии допустимое событие запускает сценарий без повторного приглашения/первой реплики.

- R-8. Backend проверяет имя/активное правило/schema; неизвестные/невалидные поля отклоняются без значений в логах. Конверт ≤20 КиБ; число полей/длины ограничены схемой. Data недоверенны: не инструкции, доказательство личности или право на чужие данные.

- R-9. Организация/виджет/подключение/посетитель/сценарий разрешаются сервером по origin, публикации и WebSession. Нет browser scenario_id/organization_id/grants или секретного API-ключа. Rate limits и параллельность действуют и на повторы; изоляция и актуальное согласие проверяются заново.

- R-10. После согласия проверенный receipt+outbox фиксируются до ACK. Дедуп: организация/виджет/WebSession/стабильное правило/eventId; дополнительно атомарно не более одного Run правила на WebSession даже с новым ID/другой вкладкой. Retry/reload/гонка/падение не создают второго запуска или первого ответа.

- R-11. Источник webchat.site_event использует SPEC-0037/ADR-0038: subscriptions/ingress/fan-out, immutable snapshot, Run, журнал/восстановление и штатные права. Нет второго runner/службы/очереди/HTTP к себе. Реализация зависит от завершения T-172 и T-174, не подменяет их объём. Новый брендовый адаптер сайта не нужен.

- R-12. Первый автономный ответ требует активного подходящего агента/маршрута в режиме с AI, отсутствия начатой переписки и управления сотрудником. Проверки повторяются перед созданием диалога/эффектом/отправкой. Операторский режим/отключение/перехват/отзыв запрещают ответ; приглашение не создаёт фиктивного агента/очередь обращения.

- R-13. Сценарий инициирует штатный AI-ход без фиктивного клиентского сообщения; сохраняется обычный ответ. Доверенное задание сценария отдельно от недоверенного data с псевдонимизацией SPEC-0022. Без истории язык — язык организации с учётом явного answer_language.

- R-14. Первый клиентский текст, событие и перехват атомарно согласуются с состоянием диалога/поколением хода. Если клиент начал переписку до проактивной отправки, проактивный ответ подавляется и действует обычный ход; нет второго диалога/двойного ответа. Закрытый диалог не переоткрывается событием.

- R-15. Публичное событие не расширяет grants и не подтверждает внешние записи/удаления. Пересекаются права сценария и ограниченный контекст посетителя; внешнее изменение требует штатного подтверждения сотрудником. Нет обхода через технического администратора.

- R-16. Первый ответ доставляется через штатные сообщения/авторство/историю/unread. Ошибка отражается достоверно в общем журнале, не выдаёт ложную отправку; обычный ввод и путь обращения доступны. В виджете нет сырых provider errors/технических кодов/внутренних документов.

- R-17. Настройка/журнал/причины подавления используют общий каталог сценариев и существующие компоненты по baseline. Источник/первый ход публикуют event/action descriptors, новые API классифицируются для полноты SPEC-0037. Действие вызывает исходные domain services с RLS/AI-policy.

- R-18. Владелец лично принимает design/baseline/widget-site-events/*.dc.html до нового UI: правило/schema/приглашение/сценарий, desktop/mobile, принятие/закрытие/TTL, согласие/форма/первый ответ/ошибки. Нет служебной лексики и новых элементов вне baseline; геометрия устойчива, ru/en через t/tn/fmt. Приёмка плана не равна приёмке макета.

- R-19. По умолчанию правила выключены; существующие приветствие/setFields/сессии/формы/история/AI/правила не получают скрытых подписок. До согласия data только в памяти; после — минимальное защищённое операционное состояние по retention SPEC-0037 без токенов/секретов. Связи удаляются штатной политикой сессии.

- R-20. Приёмка охватывает очередь/локальный показ без payload-запроса/reload/dismiss/TTL, актуальное и старое согласие/форму, старт без текста, дубли/падение/гонки, ввод/перехват, выключенный AI, чужой сценарий/grants. Сборки и только относящиеся тесты (backend --reuse-db), browser в штатном контуре. Без заглушек/seed/смены аккаунтов; отсутствие контура фиксируется blocker. Справка содержит пример emitEvent и eventId/повторы.

## Вне объёма

Встроенный трекинг DOM/scroll; вызов AI/передача события до согласия; принудительное открытие; произвольный сценарий/API-key в браузере; маркетинговые сообщения в активную переписку; второй runner; замена объёма T-172/T-174.
