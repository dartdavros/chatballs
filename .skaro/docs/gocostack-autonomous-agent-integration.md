## 1. Краткое описание контракта

Chatballs принимает сообщения из подключённых каналов, сохраняет переписку и передаёт обращение автономному агенту GoCoStack по HTTPS. GoCoStack самостоятельно выбирает LLM, использует свои знания, память и инструменты и возвращает готовый результат.

Chatballs не вызывает промежуточную языковую модель для пересказа результата GoCoStack. Он проверяет полномочия и актуальность результата, подготавливает разрешённое представление сообщения, сохраняет его и доставляет клиенту штатным транспортом.

Ответ возможен сразу либо позже: GoCoStack устойчиво регистрирует запрос, отвечает `202 Accepted` и отправляет результат отдельным HTTP-запросом в Chatballs. Chatballs также может получить состояние исходного запроса через API GoCoStack.

Полный обмен поддерживает текст, файлы и изображения, контактные сообщения в поддерживаемых направлениях, оформленные ответы через разрешённые шаблоны Chatballs и упорядоченные наборы сообщений.

**Голос обрабатывается в Chatballs:** исходное аудио расшифровывает настроенный провайдер распознавания Chatballs. GoCoStack получает текст, `wasVoice: true`, исходный ID сообщения и длительность записи. Аудиофайл внешнему агенту не передаётся. Штатное прослушивание готового текста средствами Chatballs сохраняет собственные настройки.

GoCoStack может запросить сотрудника или отправить последующее сообщение по своей инициативе. Инициатива разрешается только в связанном открытом диалоге под управлением агента, при действующем разрешении и отсутствии активной или ожидающей клиентской очереди. После перехвата сотрудником автоматическая отправка прекращается. Вернуть управление может уполномоченный сотрудник штатным действием Chatballs.

## 2. Техническое устройство и ответственность сторон

### 2.1. Уровень интеграции

Интеграция работает на уровне прикладного HTTP API между backend Chatballs и сервисом GoCoStack. Это не подключение GoCoStack как OpenAI-совместимого провайдера и не вызов инструмента через промежуточную LLM.

В Chatballs внешний исполнитель выбирается у существующего агента. Сервисное подключение организации содержит адрес GoCoStack, способ доступа и защищённые секреты. Одно подключение может обслуживать несколько явно связанных агентов; конкретного агента GoCoStack выбирает поле `externalAgentId`.

| Область | Chatballs | GoCoStack |
|---|---|---|
| Каналы связи | Приём и доставка, токены каналов, ограничения транспорта | Не обращается к мессенджерам от имени Chatballs |
| Переписка | Основное хранилище диалогов и сообщений | Своя память с привязкой к диалогу Chatballs |
| Исполнение агента | Очередь обращения и контроль допуска | LLM, инструкции, знания, инструменты, бизнес-логика |
| Сотрудники | Рабочее место, очередь, перехват и явный возврат | Структурированный запрос передачи |
| Голос | Распознавание и сохранение стенограммы | Обработка полученного текста с признаком голосового |
| Файлы | Защищённое хранение, доступ, загрузка и доставка | Чтение разрешённых вложений, загрузка файлов ответа |
| Оформление | Каталог разрешённых шаблонов, безопасный рендер и снимок | Выбор шаблона, версии и типизированных данных |
| Надёжность | Устойчивые запросы, квитанции, восстановление и контроль доставки | Устойчивая регистрация запроса, защита своих действий от повторов |
| Данные и LLM | Передаёт согласованные исходные сведения | Отвечает за их хранение и передачу своим AI-провайдерам |

Внутреннее устройство, язык программирования и способ развёртывания GoCoStack контрактом не навязываются. Доступ к БД Chatballs и токенам его каналов сервису не предоставляется.

### 2.2. Что происходит внутри Chatballs

1. Backend сохраняет входящее сообщение и ставит работу в штатную устойчивую очередь.
2. Фоновый обработчик выбирает очередной ход диалога и проверяет актуальное управление.
3. При необходимости выполняется штатное распознавание голосового.
4. До HTTP-вызова сохраняются `requestId`, снимок передаваемых данных, срок и привязка полномочий.
5. Запрос выполняется вне длительной транзакции БД.
6. Результат проходит общий механизм приёма независимо от того, пришёл он синхронно или callback.
7. Разрешённые сообщения получают устойчивые квитанции; перед каждым элементом доставки управление проверяется повторно.

Состояние хранится в штатном PostgreSQL с изоляцией организаций. Используются существующие backend и фоновые процессы Chatballs; отдельная обязательная БД, брокер или новый сервис для этого обмена не нужны.

### 2.3. Схема обычного и отложенного обмена

| Шаг | Отправитель → получатель | Смысл |
|---|---|---|
| 1 | Клиент → Chatballs | Входящее сообщение сохраняется |
| 2 | Chatballs → GoCoStack | `POST /chatballs-agent/v1/requests` |
| 3а | GoCoStack → Chatballs | `200` с окончательным результатом |
| 3б | GoCoStack → Chatballs | `202`: запрос зарегистрирован, обработка продолжается |
| 4 | GoCoStack → Chatballs | Callback с окончательным результатом для варианта 3б |
| 5 | Chatballs → GoCoStack | При необходимости `GET` состояния того же запроса |
| 6 | Chatballs → канал клиента | Применение разрешённого результата и доставка |
| 7 | GoCoStack → Chatballs | Чтение квитанции доставки, если требуется |

Callback может прийти **раньше**, чем Chatballs получит ответ `202`. Обе стороны должны корректно обработать эту гонку.

## 3. Общие правила HTTP API

### 3.1. Адреса, кодировка и идентификаторы

В примерах используются обозначения:

| Обозначение | Значение |
|---|---|
| `<GCS_BASE>` | Согласованный HTTPS-адрес сервиса GoCoStack |
| `<CB_BASE>` | Публичный HTTPS-адрес установки Chatballs |
| `<CB_API>` | `<CB_BASE>/api/v1/external-agent/connections/{connectionId}` |
| `<requestId>`, `<uuid>` и другие угловые обозначения | Места для подстановки значений, не готовые значения запросов |

Обычные тела и ответы — JSON в UTF-8, `Content-Type: application/json`. Загрузка файлов — отдельный `multipart/form-data`. Даты — RFC 3339 в UTC. Версия в JSON — строка `"1"`.

| ID | Назначение |
|---|---|
| `connectionId` | Подключение сервиса к организации Chatballs |
| `agent.id` / `agentId` | Агент Chatballs |
| `externalAgentId` | Конкретный агент внутри GoCoStack |
| `conversationId` | Стабильный идентификатор диалога в протоколе |
| `externalSessionId` | Связь с памятью/сессией GoCoStack; первоначально может быть `null` |
| `authorizationId` | Текущее разрешение внешнего исполнения в данном диалоге |
| `requestId` | Один устойчивый запрос обработки входящего сообщения |
| `resultId` | Устойчивый идентификатор окончательного результата запроса |
| `deliveryId` | Набор сообщений, принятый Chatballs к доставке |
| `itemId` | Элемент набора, сохраняемый и доставляемый отдельно |
| `receiptId` | Квитанция приёма результата или операции |
| `uploadId` | Идемпотентная операция загрузки файла |
| `fileId` | Разрешённый файл в хранилище Chatballs |
| `eventId` | Инициативный запрос передачи сотруднику |

`requestId`, `resultId`, `deliveryId`, `authorizationId`, `itemId`, `uploadId`, `eventId` — UUID. Остальные ID рассматриваются как непрозрачные строки. Знание ID не даёт доступа к объекту.

### 3.2. Два независимых ключа доступа

| Направление | Заголовок | Кто предоставляет ключ |
|---|---|---|
| Chatballs → GoCoStack | `Authorization: Bearer <GCS_TOKEN>` | GoCoStack |
| GoCoStack → Chatballs | `Authorization: Bearer <CB_TOKEN>` | Chatballs при настройке подключения |

Ключ Chatballs ограничен одним подключением и назначенными ему правами. Это не сессия сотрудника и не универсальный токен API Chatballs.

Организация определяется по проверенному ключу. Поля `organizationId` в контракте нет. Отзыв ключа или отключение подключения прекращают новые обращения и применение ожидающих отправок. Проверка авторизации выполняется раньше проверки идемпотентного повтора.

### 3.3. Идемпотентность

| Операция | `Idempotency-Key` |
|---|---|
| Создать запрос в GoCoStack | `requestId` |
| Инициативно отправить сообщения | `deliveryId` |
| Инициативно запросить сотрудника | `eventId` |
| Загрузить файл | `uploadId` |

Для окончательного результата неизменность проверяется по `requestId`, `resultId` и содержимому результата. Он одинаков для синхронного ответа и callback.

Повтор с тем же ID и тем же значимым содержимым возвращает ранее созданное состояние. Под тем же ID нельзя передать другой текст, адресата, файл или результат: это конфликт `409`. Новый сетевой повтор не означает новый ход агента.

Точный алгоритм канонизации JSON и вычисления сопоставляемого содержимого следует закрепить в общей OpenAPI-схеме и тестовых примерах обеих сторон. В HTTP-контракт не вводится дополнительная обязательная подпись тела: принята схема HTTPS + независимые Bearer-ключи.

## 4. API, который реализует GoCoStack

Все пути этого раздела относятся к `<GCS_BASE>`.

| Метод | Путь | Результат |
|---|---|---|
| GET | `/chatballs-agent/v1/capabilities` | Поддерживаемые возможности без запуска агента |
| POST | `/chatballs-agent/v1/requests` | `200` с итогом или `202` с регистрацией |
| GET | `/chatballs-agent/v1/requests/{requestId}` | Текущее состояние того же запроса |
| POST | `/chatballs-agent/v1/requests/{requestId}/cancel` | Фактический результат попытки отмены |

### 4.1. Проверка возможностей

`GET /chatballs-agent/v1/capabilities`

Пример содержимого ответа:

```json
{
  "versions": ["1"],
  "contentTypes": [
    "text",
    "image",
    "file",
    "contact",
    "contact_request",
    "formatted"
  ],
  "durableIdempotency": true,
  "statusLookup": true,
  "callbacks": true,
  "cancel": true,
  "dedupRetentionSeconds": 2592000
}
```

Обязательны устойчивая идемпотентность, чтение статуса, callbacks и приём отмены. Срок дедупликации сервиса — не менее 30 дней. `cancel: true` означает способность принять уведомление об отмене; откат уже совершённых действий этим не обещается.

Поддержка конкретного формата зависит также от направления обмена и канала Chatballs. Проверка возможностей ничего не создаёт и не запускает LLM или бизнес-действия.

### 4.2. Запрос обработки сообщения — AgentRequest

`POST /chatballs-agent/v1/requests`

```http
Authorization: Bearer <GCS_TOKEN>
Content-Type: application/json
Idempotency-Key: <requestId>
```

```json
{
  "version": "1",
  "requestId": "<requestId>",
  "createdAt": "2026-11-10T12:00:00Z",
  "deadlineAt": "2026-11-10T12:02:00Z",
  "agent": {
    "id": "<agentId>",
    "externalAgentId": "<agent-in-gocostack>"
  },
  "conversation": {
    "id": "<conversationId>",
    "externalSessionId": null,
    "authorizationId": "<authorizationId>",
    "turnSequence": 1
  },
  "trigger": {
    "messageId": "<messageId>",
    "createdAt": "2026-11-10T12:00:00Z",
    "type": "text",
    "text": "Подскажите статус моего обращения",
    "wasVoice": false,
    "attachments": []
  },
  "context": {
    "history": {
      "mode": "window",
      "snapshotCursor": "<snapshotCursor>",
      "truncated": false,
      "messages": [],
      "historyUrl": "<CB_API>/conversations/<conversationId>/history/",
      "nextCursor": null
    },
    "customer": {
      "id": "<customerId>",
      "fields": {},
      "customFields": {
        "mode": "replace",
        "snapshotId": "<uuid>",
        "capturedAt": "2026-11-10T12:00:00Z",
        "scope": [],
        "items": []
      }
    },
    "dataPolicy": {
      "revision": 1,
      "mode": "agreed_original",
      "fields": [],
      "customFields": []
    },
    "language": {
      "mode": "mirror",
      "organization": "ru",
      "requested": null
    }
  },
  "permissions": {
    "reply": true,
    "handoff": true,
    "proactive": false
  },
  "deliveryConstraints": {
    "types": ["text", "file", "image", "formatted"],
    "maxFileBytes": 20971520
  },
  "callbacks": {
    "resultUrl": "<CB_API>/requests/<requestId>/result/"
  }
}
```

| Поле | Смысл |
|---|---|
| `version` | Версия протокола |
| `requestId` | Идентификатор, сохраняемый при всех повторах |
| `createdAt`, `deadlineAt` | Время регистрации и предельный срок применения результата |
| `agent` | Связь агента Chatballs с агентом GoCoStack |
| `conversation` | Диалог, внешняя сессия, текущее разрешение и номер хода |
| `trigger` | Текущее входящее сообщение; в историю повторно не добавляется |
| `context.history` | Краткий снимок публичной предыстории и доступ к страницам |
| `context.customer.fields` | Только разрешённые стандартные поля карточки контакта |
| `context.customer.customFields` | Полный типизированный снимок кастомных полей с источниками, ID и состояниями |
| `context.dataPolicy.customFields` | Явно разрешённые пары WEB-источник + fieldId; исходно список пуст |
| `context.dataPolicy` | Ревизия согласованной политики передачи исходных данных |
| `context.language` | Языковая директива для агента GoCoStack |
| `permissions` | Разрешённые виды взаимодействия; их актуальность сервер проверяет повторно |
| `deliveryConstraints` | Возможности и ограничения текущего канала |
| `callbacks.resultUrl` | Адрес приёма результата, сформированный Chatballs |

`language.mode`: `mirror` — отвечать на языке клиента; `organization` — язык организации; `fixed` — язык из `requested`. При других режимах `requested` не задаёт фиксированный язык. Chatballs не перегенерирует ответ, чтобы изменить язык: директиву исполняет GoCoStack.

`turnSequence` задаёт порядок ходов данного диалога. Повтор одного хода сохраняет ID и снимок. Смена `authorizationId` не означает, что старые запросы можно применить с новым разрешением.

### 4.3. Запрос принят, обработка продолжается — Accepted

Ответ `202 Accepted`:

```json
{
  "version": "1",
  "requestId": "<requestId>",
  "status": "accepted",
  "externalSessionId": "<session-in-gocostack>"
}
```

GoCoStack должен сохранить запрос и запись дедупликации **до выполнения действий и до ответа 202**. После перезапуска сервис должен продолжить ту же работу либо достоверно сообщить её состояние.

`externalSessionId` можно выдать при регистрации или позже, если ранее он был `null`. После присвоения значение внутри данной привязки не заменяется произвольно.

### 4.4. Готовый ответ — TerminalResult

Синхронный ответ `200 OK` и callback используют одинаковое тело:

```json
{
  "version": "1",
  "requestId": "<requestId>",
  "resultId": "<resultId>",
  "status": "completed",
  "externalSessionId": "<session-in-gocostack>",
  "outcome": {
    "type": "reply",
    "messages": [
      {
        "itemId": "<itemId>",
        "content": {
          "type": "text",
          "text": "Ваше обращение принято в работу."
        }
      }
    ]
  }
}
```

`messages` — упорядоченный набор. Каждый `itemId` постоянен при повторах результата. Допустимые варианты `content` описаны в разделе 5.

Окончательный результат не изменяется после принятия. Если callback был принят раньше синхронного ответа, одинаковый ответ считается повтором; отличающийся — конфликтом. Нельзя менять диалог или адресата через результат: Chatballs берёт их из исходного запроса.

### 4.5. Запрос сотрудника в результате обработки

```json
{
  "version": "1",
  "requestId": "<requestId>",
  "resultId": "<resultId>",
  "status": "completed",
  "externalSessionId": "<session-in-gocostack>",
  "outcome": {
    "type": "handoff",
    "reasonCode": "<agreed-reason-code>",
    "summary": "Краткое описание ситуации для сотрудника"
  }
}
```

`summary` предназначен сотруднику, не публикуется клиенту как текст агента. Chatballs использует текущую группу, штатную очередь и уведомления. GoCoStack не назначает произвольного сотрудника и не меняет права или группу.

`outcome` содержит один вариант: `reply` либо `handoff`. Управляющие токены в обычном тексте не заменяют структурированный запрос передачи.

### 4.6. Ошибка завершённого исполнения

```json
{
  "version": "1",
  "requestId": "<requestId>",
  "resultId": "<resultId>",
  "status": "failed",
  "error": {
    "code": "<safe-error-code>",
    "retryable": false
  }
}
```

Это итог уже принятой работы агента. Он не означает, что Chatballs должен автоматически заново запустить LLM или повторить внешние бизнес-действия.

Сбой HTTP до регистрации запроса и окончательная ошибка обработки — разные случаи. Если результат выполненного действия неизвестен, сервис сообщает `unknown` и выполняет сверку, не создаёт новый запрос под другим ID.

### 4.7. Статус запроса

`GET /chatballs-agent/v1/requests/{requestId}`

| `status` | Значение |
|---|---|
| `accepted` | Запрос устойчиво зарегистрирован |
| `processing` | Идёт обработка |
| `completed` | Готов окончательный `TerminalResult` |
| `failed` | Готов окончательный отказ обработки |
| `cancelled` | Сервис подтверждает отмену |
| `unknown` | Фактический исход пока не установлен |

Для `completed` и `failed` возвращается тот же окончательный результат, что доступен через основной обмен. Для промежуточного состояния возвращаются ID запроса и его состояние; промежуточное состояние не выдаётся за завершение.

После `202` Chatballs не создаёт новую работу вместо принятой: ожидает callback и читает статус исходного запроса.

### 4.8. Отмена

`POST /chatballs-agent/v1/requests/{requestId}/cancel`

```json
{
  "version": "1",
  "requestId": "<requestId>",
  "reason": "control_revoked"
}
```

| `reason` | Причина |
|---|---|
| `control_revoked` | Утрачено управление диалогом |
| `expired` | Истёк срок запроса |
| `configuration_changed` | Изменилась конфигурация или привязка |

GoCoStack возвращает фактическое состояние: `cancelled`, уже полученный `completed` либо `unknown`. Повтор отмены безопасен.

Локальный запрет Chatballs на отправку действует независимо от успешности этого запроса. Отмена не обещает отменить уже выполненное действие в системе GoCoStack или заказчика.


## 5. Форматы сообщений

### 5.1. Матрица поддержки

| Тип | Из Chatballs в GoCoStack | Из GoCoStack в Chatballs |
|---|---|---|
| `text` | Исходный текст | Готовый текст |
| Голосовое | Стенограмма как `text`, `wasVoice: true` | Исходящее аудио этим контрактом не предусмотрено |
| `file` / `image` | Метаданные и защищённый `fileId` | Ранее загруженный в Chatballs `fileId` |
| `contact` | Сохранённое контактное сообщение и разрешённые фактические сведения | Новая отправка контактной карточки не добавляется поверх возможностей платформы |
| `contact_request` | Публичное событие в доступной истории | Штатный запрос контакта там, где это умеет канал |
| `formatted` | Публичный текст и разрешённые метаданные снимка | Разрешённый шаблон + его ревизия + данные |

Наличие типа в общем протоколе не расширяет возможности конкретного канала. Chatballs возвращает их в `deliveryConstraints` и проверяет до принятия результата.

### 5.2. Обычный текст

```json
{
  "type": "text",
  "text": "Готовое сообщение клиенту"
}
```

Сервис не присылает исполняемые команды в тексте. Текст не обрезается и не разбивается на несколько сообщений скрытно.

### 5.3. Голосовое после распознавания

Пример `trigger` с голосовым происхождением:

```json
{
  "messageId": "<original-messageId>",
  "createdAt": "2026-11-10T12:00:00Z",
  "type": "text",
  "text": "Распознанное содержание голосового сообщения",
  "wasVoice": true,
  "source": {
    "kind": "voice",
    "durationSeconds": 18
  },
  "attachments": []
}
```

Chatballs сохраняет исходное голосовое внутри своей переписки, но не передаёт `audioUrl` или аудиофайл GoCoStack. Смена расширения или MIME не должна давать доступ к исходному аудио через API файлов.

Распознавание использует отдельно настроенный STT Chatballs и входит в общую очередность/срок обработки. Повтор отправки готового запроса не запускает STT заново при наличии сохранённой стенограммы. Ошибка или отсутствие распознавания переводят обращение сотруднику; пустая или выдуманная стенограмма не передаётся агенту.

WEB-диктовка, которая до отправки уже превратилась в текстовый черновик, остаётся обычным текстом. Если штатное входящее сообщение не содержит признака голосового происхождения, Chatballs его не выдумывает.

### 5.4. Файл или изображение

Пример содержимого исходящего элемента:

```json
{
  "type": "file",
  "fileId": "<fileId>",
  "filename": "document.pdf",
  "mimeType": "application/pdf",
  "size": 125000,
  "sha256": "<sha256>",
  "caption": "Документ по вашему обращению"
}
```

Для изображения используется `type: "image"` с метаданными фактического изображения. Входящий `trigger.attachments` содержит ссылки и метаданные разрешённых вложений.

Порядок отправки файла GoCoStack:

1. Загрузить файл в Chatballs через защищённый API.
2. Получить готовый `fileId`.
3. Включить этот `fileId` в элемент результата или инициативного набора.
4. Получить квитанцию приёма.
5. При необходимости проверить статус доставки.

Ссылка на внешний URL не заменяет загрузку: Chatballs не скачивает произвольный ресурс из результата. Binary не помещается в JSON/base64.

### 5.5. Контакт и запрос контакта

Входящий `contact` передаёт сохранённое содержание сообщения и только реально доступные, разрешённые поля. Chatballs не придумывает отсутствующие структурированные данные; сведения клиента не являются подтверждённой идентификацией.

Исходящий `contact_request` запрашивает штатную возможность канала: форму/кнопку, уже предусмотренную Chatballs и транспортом. Он не описывает произвольную форму и не меняет управление диалогом на сотрудника. Если канал не умеет такой запрос, Chatballs возвращает проверяемый отказ.

Каталог полей контактного сообщения `contact` (не кастомные поля карточки) и точное тело `contact_request` должны быть отражены в общей OpenAPI-схеме по существующим возможностям каналов; новые продуктовые формы этим документом не вводятся.

### 5.6. Оформленный ответ

```json
{
  "type": "formatted",
  "templateId": "<templateId>",
  "templateRevision": 3,
  "data": {
    "<field-from-template-schema>": "<value>"
  }
}
```

GoCoStack получает каталог **явно разрешённых** шаблонов и их схем. Сервер Chatballs проверяет данные, применяет существующий безопасный рендерер и сохраняет неизменяемый снимок ответа.

В WEB отображается штатный изолированный HTML-снимок. Для остальных каналов используется текстовое представление того же шаблона. Изменение или удаление шаблона не меняет уже опубликованное сообщение.

GoCoStack не присылает `srcDoc`, JavaScript или произвольный HTML/CSS. Неверная или отозванная ревизия — конфликт, а не разрешение самостоятельно построить другую карточку.

### 5.7. Составной ответ

```json
{
  "type": "reply",
  "messages": [
    {
      "itemId": "<text-itemId>",
      "content": {
        "type": "text",
        "text": "Направляю подготовленный документ."
      }
    },
    {
      "itemId": "<file-itemId>",
      "content": {
        "type": "file",
        "fileId": "<fileId>",
        "filename": "document.pdf",
        "mimeType": "application/pdf",
        "size": 125000,
        "sha256": "<sha256>",
        "caption": ""
      }
    }
  ]
}
```

Все элементы проверяются до принятия набора: типы, ссылки, размеры, шаблоны и разрешения. Невалидный второй элемент не должен приводить к публикации первого на этапе приёма.

После начала реальной доставки возможен частичный исход. Уже принятые каналом элементы не отправляются заново. Перед каждым следующим элементом проверяется текущее управление диалогом.

## 6. API, который реализует Chatballs

Все пути ниже добавляются к `<CB_API>`. Все методы требуют `Authorization: Bearer <CB_TOKEN>`.

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/requests/{requestId}/result/` | Результат исходного запроса |
| POST | `/conversations/{conversationId}/messages/` | Инициативный набор сообщений |
| POST | `/conversations/{conversationId}/handoff/` | Инициативный запрос сотрудника |
| GET | `/deliveries/{deliveryId}/` | Квитанция и состояния доставки |
| GET | `/conversations/{conversationId}/history/` | Публичная история в пределах снимка |
| GET | `/conversations/{conversationId}/reply-templates/` | Разрешённые шаблоны и схемы |
| POST | `/conversations/{conversationId}/files/` | Потоковая загрузка файла ответа |
| GET | `/conversations/{conversationId}/files/{fileId}/` | Защищённое чтение файла |

### 6.1. Callback с окончательным результатом

`POST <CB_API>/requests/{requestId}/result/`

Тело — `TerminalResult` из разделов 4.4–4.6. `requestId` в URL и теле совпадает. Другого диалога, адресата или организации в результате выбрать нельзя.

Chatballs подтверждает приём только после сохранения устойчивой квитанции и необходимых заданий продолжения. Повтор одинакового результата возвращает ту же квитанцию. Противоречащий окончательный результат — `409 result_conflict`.

Если срок или полномочие уже утрачены, корректно аутентифицированный поздний callback может получить квитанцию `suppressed`: результат зарегистрирован как неприменимый, сообщение клиенту не создано. После отзыва самого ключа вызов отклоняется на аутентификации.

### 6.2. Инициативное сообщение

`POST <CB_API>/conversations/{conversationId}/messages/`

```http
Idempotency-Key: <deliveryId>
```

```json
{
  "version": "1",
  "deliveryId": "<deliveryId>",
  "agentId": "<agentId>",
  "authorizationId": "<authorizationId>",
  "externalSessionId": "<session-in-gocostack>",
  "messages": [
    {
      "itemId": "<itemId>",
      "content": {
        "type": "text",
        "text": "Получен результат вашей проверки."
      }
    }
  ]
}
```

Условия применения проверяются совместно:

- Диалог принадлежит разрешённой связи сервиса и агента.
- Диалог открыт и находится под управлением агента.
- `authorizationId` актуален; подключение, агент и режим организации разрешают исполнение.
- Инициатива явно разрешена.
- Нет активного или ожидающего клиентского хода.
- Каждый элемент допустим для текущего канала.

При занятом диалоге — `409 conversation_busy`; при запрете инициативы — `403 proactive_disabled`. Предварительный отказ не создаёт сообщения. Тот же ещё не принятый запрос можно повторить позднее, пока разрешение действительно.

Метод не создаёт новые диалоги и не открывает закрытые. После принятия повтор с тем же `deliveryId` возвращает существующую квитанцию.

### 6.3. Инициативный запрос сотрудника

`POST <CB_API>/conversations/{conversationId}/handoff/`

```http
Idempotency-Key: <eventId>
```

```json
{
  "version": "1",
  "eventId": "<eventId>",
  "agentId": "<agentId>",
  "authorizationId": "<authorizationId>",
  "externalSessionId": "<session-in-gocostack>",
  "reasonCode": "<agreed-reason-code>",
  "summary": "Краткое описание ситуации для сотрудника"
}
```

Передача может прервать текущую обработку. Она использует штатную очередь Chatballs, отзывает разрешение дальнейшей автоматической отправки и не предоставляет GoCoStack права самостоятельно вернуть управление.

### 6.4. Квитанция приёма — DeliveryReceipt

При новом наборе, поставленном на доставку, Chatballs возвращает `202`:

```json
{
  "version": "1",
  "requestId": "<requestId>",
  "receiptId": "<receiptId>",
  "state": "queued",
  "deliveryId": "<deliveryId>",
  "items": [
    {
      "itemId": "<itemId>",
      "messageId": "<messageId>",
      "state": "queued"
    }
  ]
}
```

Для инициативы `requestId: null`. Для передачи сотруднику: `state: "handed_off"`, `deliveryId: null`, `items: []`. Для неприменимого позднего результата — `state: "suppressed"` с кодом причины и без созданных сообщений.

Идемпотентный повтор, передача или подавленный результат получают `200` с той же квитанцией и фактическим состоянием. **HTTP 202 не означает доставку в канал.**

### 6.5. Статус доставки

`GET <CB_API>/deliveries/{deliveryId}/`

Читаемая структура ответа:

```json
{
  "deliveryId": "<deliveryId>",
  "state": "queued",
  "reasonCode": null,
  "updatedAt": "2026-11-10T12:00:02Z",
  "items": [
    {
      "itemId": "<itemId>",
      "messageId": "<messageId>",
      "state": "queued",
      "reasonCode": null
    }
  ]
}
```

| Состояние | Значение |
|---|---|
| `queued` | Сохранено и ожидает разрешённой отправки |
| `transport_accepted` | Канал подтвердил приём либо WEB-сообщение опубликовано в клиентской истории |
| `failed` | Достоверно не принято, повтор не назначен |
| `unknown` | Канал мог принять сообщение, но подтверждение потеряно |
| `suppressed` | Отправка запрещена до передачи транспорту из-за срока или утраты полномочия |
| `partial` | Смешанный исход набора; необходимо прочитать состояния элементов |

`transport_accepted` не означает прочтение клиентом. При `unknown` нельзя повторять сообщение новым `deliveryId` в попытке «доставить наверняка».

### 6.6. История и восстановление памяти

`GET <CB_API>/conversations/{conversationId}/history/`

Логические параметры: `authorizationId`, `snapshotCursor`, `pageCursor`, `pageSize`. Точное размещение и ограничения GET-параметров фиксируются в общей OpenAPI-схеме.

| Поле ответа | Назначение |
|---|---|
| `items` | Публичные сообщения доступной страницы |
| `snapshotCursor` | Фиксированная граница чтения |
| `nextCursor` | Продолжение либо `null` |
| `hasMore` | Есть ли следующие страницы |
| `dataPolicyRevision` | Политика передачи данных данного снимка |

Сообщение истории содержит `id`, автора `customer | employee | agent`, `createdAt`, `content` и `wasVoice`. Для файлов выдаются разрешённые ссылки `fileId`, для оформленных сообщений — публичное представление и разрешённые метаданные.

Правила чтения:

1. Текущее входящее передаётся отдельно в `trigger`; не нужно повторно добавлять его из истории.
2. Последующие необработанные клиентские сообщения не попадают в текущий снимок.
3. Ответ предыдущего хода может быть включён, даже если физически сохранён после прихода текущего сообщения.
4. Внутренние комментарии, причины передач, назначения и технические события исключены.
5. Все страницы относятся к одному разрешённому снимку и политике.
6. Отзыв разрешения прекращает дальнейшее чтение.
7. Удалённые сведения не восстанавливаются из старого снимка.

Встроенное окно по умолчанию — 20 сообщений. Это удобная часть контекста, а не вся история. Для восстановления памяти GoCoStack читает доступные страницы и использует стабильные ID для дедупликации. Новые сведения после границы доступны следующим снимком.

### 6.7. Загрузка файла ответа

`POST <CB_API>/conversations/{conversationId}/files/`

```http
Authorization: Bearer <CB_TOKEN>
Content-Type: multipart/form-data; boundary=<boundary>
Idempotency-Key: <uploadId>
```

| Часть multipart | Значение |
|---|---|
| `uploadId` | Постоянный UUID загрузки |
| `authorizationId` | Текущее разрешение диалога |
| `file` | Фактическое бинарное содержимое |
| `sha256` | Контрольная сумма передаваемого файла |

После проверки ответ содержит `fileId`, `mimeType`, `size`, `filename`, `sha256`, `expiresAt`. Совпадающий повтор возвращает тот же файл; другие байты или метаданные под тем же ID — `409`.

Upload не создаёт клиентское сообщение и не доставляет файл. Незавершённый файл нельзя использовать в результате. Файл связан с текущими организацией, агентом, диалогом и разрешением.

Действующий общий лимит вложения Chatballs — **20 MiB**; применяются штатные запреты типов, безопасное имя, учёт хранилища и более узкие ограничения канала. Произвольный URL не принимается вместо binary.

### 6.8. Чтение файла

`GET <CB_API>/conversations/{conversationId}/files/{fileId}/`

Требуются ключ сервиса и текущее `authorizationId`. Способ передачи разрешения в GET фиксируется в общей OpenAPI-схеме.

Сервис получает бинарный поток только для разрешённого входящего файла публичной истории либо своего файла той же связи. Ссылка не является публичным URL. Исходное аудио голосового через этот метод недоступно.

Сервер применяет безопасный `Content-Disposition`, проверку принадлежности и штатную политику выдачи. Поддержка `Range`, если объявлена, использует штатные возможности хранилища.

Предлагаемый срок непривязанных загруженных файлов — 24 часа. Активные запросы и принятые сообщения защищают нужные файлы от очистки. Опубликованное вложение далее хранится по правилам переписки.

### 6.9. Разрешённые оформленные шаблоны

`GET <CB_API>/conversations/{conversationId}/reply-templates/`

Каталог выдаёт только явно разрешённые текущему агенту шаблоны:

| Поле | Смысл |
|---|---|
| `id` | Идентификатор шаблона |
| `revision` | Ревизия, на которую ссылается результат |
| `purpose` | Назначение |
| Схема данных | Типы и ограничения передаваемого `data` |
| Представления | Поддерживаемые способы отображения |

Внутренние инструкции навыка, инструменты, знания и исходники HTML/CSS автоматически не выдаются. Изменение или отзыв шаблона до принятия результата — `409 template_revision_changed`. Шаблон применяется сервером, а готовый снимок сохраняется неизменяемо.

### 6.10. Общие ошибки API

```json
{
  "version": "1",
  "error": {
    "code": "conversation_busy",
    "retryable": true,
    "traceId": "<traceId>"
  }
}
```

Пример показывает форму ошибки; возможность повтора определяется кодом, текущим разрешением и сроком, а не только HTTP-статусом.

| HTTP | Примеры кодов | Что означает |
|---|---|---|
| 400 | `invalid_request` | Нарушена структура запроса |
| 401 | `invalid_credentials` | Ключ недействителен или отозван |
| 403 | `permission_denied`, `proactive_disabled` | Операция не разрешена |
| 404 | `resource_not_found` | Объект отсутствует или недоступен этому подключению |
| 409 | `idempotency_conflict`, `result_conflict` | ID уже связан с другим содержимым |
| 409 | `control_changed`, `conversation_busy`, `channel_restricted` | Текущее состояние не позволяет применить запрос |
| 409 | `template_revision_changed` | Шаблон изменён или больше не разрешён |
| 413 | `payload_too_large` | Превышен размер |
| 422 | `unsupported_content` | Тип или содержимое не поддержаны |
| 429 | `rate_limited` | Необходимо отложить повтор |
| 503 | `temporarily_unavailable` | Временная недоступность |

Для `429/503` учитывается `Retry-After`, но повтор не продлевает срок запроса. В ошибках не возвращаются сырые ответы внешних API, stack trace, ключи и персональные сведения.


## 7. Порядок обработки, восстановление и доставка

### 7.1. Очередь диалога

Один входящий trigger получает один постоянный `requestId`. Сообщения одного диалога обрабатываются по порядку, без объединения в один запрос. Одновременно незавершённым остаётся не более одного внешнего запроса.

Ответ `202` освобождает HTTP-соединение и обработчик Chatballs, но не разрешает обогнать этот запрос следующим ходом. Ожидание хранится в БД. Окончательный контрольный результат позволяет продвинуть очередь.

Следующий снимок собирается с учётом уже обработанной предыстории. Последующие сообщения клиента, которые ещё стоят в очереди, не попадают в предыдущий запрос.

Порядок исходящей доставки также сохраняется: следующий набор не обгоняет незавершённый предыдущий. Если исход предыдущей отправки неизвестен, система не перескакивает через проблему молча.

### 7.2. Регистрация и защита действий GoCoStack

При первом `POST requests` GoCoStack должен:

1. Проверить ключ, схему и поддерживаемую версию.
2. Устойчиво зарегистрировать `requestId` и значимое содержимое.
3. При повторе вернуть существующую работу, не запуская новую.
4. Только после регистрации начинать действия агента.
5. Устойчиво сохранить окончательный результат до его отправки.
6. При повторной отправке результата сохранять прежние ID и содержимое.

Защита должна распространяться и на инструменты/бизнес-действия самого агента. Если действие во внешней системе могло выполниться, но ответ потерян, GoCoStack использует поддержанную идемпотентность или сверку. При невозможности установить исход сообщает `unknown`; новый `requestId` не является способом восстановить ту же операцию.

### 7.3. Сроки и повторы

Фактический срок конкретного запроса передаётся в `deadlineAt`. Параметры подключения настраиваются администратором.

| Параметр | Предлагаемое значение/действующее ограничение |
|---|---|
| Ожидание одного HTTP-вызова | До 10 секунд |
| Срок обычного ответа | По умолчанию 120 секунд от приёма trigger, включая STT и очередь |
| Долгая обработка | Отдельная настройка; предлагаемый максимальный срок по умолчанию 24 часа, не жёсткий предел функциональности |
| Повторы создания до регистрации | До трёх повторов через 1/5/15 секунд с тем же ID и снимком, внутри срока |
| Проверки статуса после 202 | Через 5/15/30 секунд, затем каждые 30 секунд до срока |
| JSON-тело | Не более 256 KiB; длинная история постранично, binary отдельно |
| Inline-история | По умолчанию 20 сообщений, настройка 0–200 |
| Файл | Текущий общий лимит Chatballs 20 MiB; канал может ограничивать сильнее |
| Дедупликация в GoCoStack | Не менее 30 дней |
| Непривязанные загрузки | Предлагаемый срок 24 часа |

Параметры времени приведены для согласования эксплуатации; значения конкретного подключения и переданный `deadlineAt` имеют практическое значение. Heartbeat, чтение статуса или сетевой повтор не продлевают срок автоматически.

После подтверждённой регистрации Chatballs ожидает результат или читает статус существующей работы. При истечении срока либо исчерпании возможностей восстановления диалог получает штатную очередь сотрудника, будущие автоматические отправки подавляются.

### 7.4. Две разные группы состояний

**Обработка GoCoStack:** `accepted → processing → completed / failed / cancelled`; `unknown` отражает неустановленный внешний исход.

**Применение и доставка Chatballs:** приём квитанции, `queued`, затем фактические состояния элементов `transport_accepted / failed / unknown / suppressed`; набор может иметь `partial`.

Успешно завершённое рассуждение агента ещё не означает доставленного клиенту ответа. Ошибка доставки не запускает повторное рассуждение или бизнес-действие агента.

### 7.5. Перехват сотрудником и возврат

`authorizationId` относится к конкретной действующей привязке агента и диалога. Chatballs проверяет не только текущее название режима, но и его версии.

| Событие | Последствие |
|---|---|
| Сотрудник перехватил диалог | Старое разрешение отозвано, будущие автоматические отправки прекращаются |
| Диалог закрыт или архивирован | Результат и инициатива не разрешают новую отправку |
| Сменился агент/подключение/режим/политика | Прежняя привязка становится непригодной |
| Подключение отключено или ключ отозван | Новые обращения и ожидающие отправки не обходят запрет |
| Сотрудник явно вернул управление | Создаётся новое разрешение; старые запросы не оживают |
| Режим выключили и быстро включили обратно | Версии различаются, старые результаты остаются непригодными |

Chatballs может уведомить GoCoStack отменой. Даже если уведомление не дошло, локальный запрет уже действует.

Перед сохранением и перед фактической передачей каждого элемента каналу полномочия проверяются повторно. После завершившегося перехвата нельзя начать новую отправку старого ответа. Уже переданное внешнему каналу сообщение автоматически отозвать не обещается.

### 7.6. Частичная и неизвестная доставка

Один `(deliveryId, itemId)` создаёт одно сообщение Chatballs. Это не универсальная гарантия доставки ровно один раз во внешнем мессенджере.

Если канал подтвердил приём — `transport_accepted`. Если достоверно отказал — соответствующий отказ. Если мог принять сообщение, а подтверждение потерялось — `unknown`.

При `unknown` автоматический повтор допускается только при наличии реальной поддержки идемпотентности или сверки данного канала. Отправка нового элемента или набора с другим ID может создать дубль и не является восстановлением.

В составном ответе уже принятые элементы не повторяются. Перехват подавляет оставшиеся. Квитанция сохраняет состояние каждого элемента, чтобы обе стороны и сотрудник видели фактический исход.

## 8. Данные, безопасность и хранение

### 8.1. Согласованные исходные данные

Для этой интеграции выбран доверенный сервис GoCoStack, которому передаются согласованные исходные тексты и явно разрешённые поля клиента. Это отдельная граница доверия; общие правила маскирования при вызове встроенных LLM Chatballs сохраняются.

- Стандартные поля карточки и кастомные поля имеют раздельные списки разрешений, исходно пустые. Кастомное поле разрешается по паре sourceConnectionId/fieldId, не только по key.
- Настройки доступа встроенной LLM не включают экспорт в GoCoStack автоматически.
- В сообщениях могут находиться персональные сведения; полного автоматического распознавания и удаления всех ПДн этот режим не обещает.
- Сведения, пришедшие с сайта, не являются подтверждением личности или прав клиента.
- GoCoStack отвечает за хранение полученных данных и их передачу своим LLM/внешним системам.
- Chatballs проверяет действующее согласие WEB и форму до передачи; если состав передачи требует новой версии согласия, она должна быть принята до включения.
- Комментарии сотрудников, причины передач из внутреннего журнала, секреты и технические настройки не экспортируются.

Политика данных имеет ревизию. Изменение политики аннулирует прежнее разрешение: старый курсор или ID не позволяет продолжить более широкий доступ.

### 8.2. Ограничение полномочий

Доступные операции: `result.submit`, `message.send`, `handoff.request`, `delivery.read`, `history.read`, `file.read`, `file.upload`, `template.read`. Каждая ограничена подключением, агентом, диалогом, текущим разрешением и соответствующим списком доступа.

Сервис не получает автоматически разрешений встроенных инструментов или действий Chatballs. Нельзя выбрать другую организацию в JSON, сменить получателя через callback, создать новый диалог, открыть закрытый или отменить решение сотрудника.

Чужой объект возвращает `404` без раскрытия его существования. Проверка ключа и текущего доступа действует также при идемпотентном повторе.

### 8.3. Сеть и секреты

Используется HTTPS. Исходящие обращения Chatballs идут через штатный защищённый HTTP-клиент: проверка адреса после DNS, проверка перенаправлений, запрет доступа к сервисам установки, управляемый допуск частных сетей.

Пути GoCoStack строятся из сохранённого проверенного адреса. Callback-адрес формирует Chatballs из своего настроенного публичного адреса, а не из произвольного входного заголовка.

Ключи не размещаются в URL, теле результата, истории, логах или заданиях очереди. В журналах — коды, ID, сроки и исходы; не полные HTTP-тела, промпты, ответы инструментов и секреты.

### 8.4. Хранение

| Данные | Правило Chatballs |
|---|---|
| Снимки запросов и необходимые результаты восстановления | Зашифрованы; по умолчанию 7 дней после завершения |
| Диагностические метаданные | По умолчанию 30 дней |
| Активные ожидания | Защищены от преждевременной очистки |
| Минимальные контрольные записи дедупликации | ID и защищённый digest без текста/секретов, на срок жизни подключения |
| Переписка и опубликованные вложения | Собственная действующая политика хранения переписки |
| Незавершённые/непривязанные загрузки | Очистка с учётом активных ссылок и согласованного срока staging |

Очистка восстановительного payload не разрешает повторно создать то же сообщение. Удаление диалога прекращает задания, отзывает связь и удаляет его операционные данные.

GoCoStack сохраняет записи дедупликации не менее 30 дней. Сроки его памяти, удаление внешних копий и работа с данными у его провайдеров фиксируются отдельно в соглашении сторон; Chatballs не объявляет внешние копии удалёнными без фактического выполнения на стороне GoCoStack.

## 9. Совместная проверка интеграции

Приёмка выполняется с реальным сервисом GoCoStack, штатным Chatballs и поддерживаемыми каналами. Автоматические контрактные тесты дополняют эту проверку, но не заменяют её.

| Сценарий | Проверяемый результат |
|---|---|
| Обычный синхронный ответ | Один применённый результат и корректная доставка |
| 202 + callback | Ожидание переживает завершение HTTP и перезапуск обработчика |
| Callback раньше ответа 202 | Результат принимается один раз |
| Повтор после сетевого сбоя | Нет повторного агента/бизнес-действия и лишнего сообщения |
| Изменённое тело под прежним ID | Проверяемый конфликт |
| Несколько сообщений клиента | FIFO, корректная история без будущих входящих |
| Восстановление памяти | Все разрешённые страницы истории доступны в одном снимке |
| Голосовое | Реальный STT, исходный messageId, текст и wasVoice; аудио в GoCoStack не уходит |
| Ошибка STT | Обращение сохранено и передано сотруднику |
| Файл/изображение в обе стороны | Защищённое чтение/загрузка, реальные ограничения, корректная доставка |
| Повтор/обрыв загрузки | Нет дублирования файла и публикации неполного содержимого |
| Оформленный ответ | Разрешённая ревизия, безопасный renderer и неизменяемый снимок |
| Контактные форматы | Только поддержанные направления и возможности канала |
| Составной ответ | Порядок элементов, достоверные partial/unknown, отсутствие слепого повтора |
| Инициатива | Только свой открытый диалог под агентом; busy и запреты учитываются |
| Передача/перехват | Будущая автоматическая отправка прекращается |
| Явный возврат | Новая авторизация, старый результат не оживает |
| Истечение срока/отмена | Поздний результат не публикуется |
| Отзыв/ротация доступа | Старый ключ и ожидающие отправки не обходят запрет |
| Изоляция организаций | Чужие диалоги, файлы, шаблоны, поля и квитанции недоступны |
| Кастомные поля | Составные ID, все типы, enum, пустая строка/0/false, unset/invalid и несколько WEB-источников |
| Обновление полей | Новый replace-снимок обновляет рабочий контекст; повтор сохраняет прежний снимок; отзыв/удаление не обходятся кешем |
| Нет обратной записи | Callback/AgentResult не изменяют значения или схему полей CB |
| Неизвестный исход канала | Нет ложного успеха и повторной отправки новым ID |

Функция не считается завершённой, если обязательные форматы или проверки оставлены на последующую поставку. UI Chatballs дополнительно проверяется в штатном приложении по отдельно утверждённому макету.

| Деталь | Что требуется зафиксировать |

| Эксплуатация | Реальные HTTPS-адреса, сетевой доступ, выдачу/ротацию ключей, сроки обычной/долгой работы, staging и хранения у GoCoStack |

Эти уточнения не сокращают функциональный объём и не разрешают менять принятые границы доступа. Изменения поведения согласуются обеими сторонами отдельно; параметры конкретного подключения передаются и проверяются сервером.

## 11. Кастомные поля клиента

### Разделение стандартных и кастомных полей

`context.customer.fields` содержит только явно разрешённые стандартные поля карточки контакта. Кастомные поля CB передаются отдельно в `context.customer.customFields`, чтобы одинаковые ключи разных WEB-подключений не сталкивались. Это не содержимое сообщения типа `contact` и не API записи в карточку.

Существующая модель CB хранит значение по связке «организация — контакт — WEB-подключение — ключ». Схема и устойчивый `fieldId` принадлежат WEB-подключению. Внешний контракт использует составную идентичность **`(sourceConnectionId, fieldId)`**, а `key` сохраняет как машинное имя. `fieldId` — непрозрачная строка из действующей схемы, не обязательно UUID. Новый после удаления объект с прежним `key` не наследует разрешение старого поля.

`sourceConnectionId` обозначает WEB-источник данных, а `connectionId` в префиксе внешнего API — сервисное подключение GoCoStack. Это разные идентификаторы и разные роли.

### Политика экспорта

Список `context.dataPolicy.customFields` содержит разрешённые пары `{sourceConnectionId, fieldId}`; исходно он пуст. `context.dataPolicy.fields` остаётся списком разрешённых стандартных полей. Выбор выполняется явно в настройке внешнего агента; данные другого контакта/организации или неразрешённого источника не выбираются по совпадению ключа.

`aiAccess` относится к встроенной LLM и не является разрешением передачи GoCoStack. Передача в этот доверенный сервис отдельно разрешает согласованные исходные значения; секретные служебные данные не экспортируются. Поля сайта остаются недоверенными данными, не инструкциями и не подтверждением личности.

Пример политики для одного кастомного поля (часть `context.dataPolicy`):

```json
{
  "revision": 2,
  "mode": "agreed_original",
  "fields": [],
  "customFields": [
    { "sourceConnectionId": "<web-A>", "fieldId": "<field-A>" }
  ]
}
```

### Полный снимок CustomFieldsSnapshot

Каждый AgentRequest содержит объект, даже когда полей нет:

```json
{
  "mode": "replace",
  "snapshotId": "<uuid>",
  "capturedAt": "2026-11-10T12:00:00Z",
  "scope": [],
  "items": []
}
```

| Поле | Тип | Правило |
|---|---|---|
| `mode` | Строка `replace` | Полный снимок разрешённых кастомных полей; не частичный patch |
| `snapshotId` | UUID | Идентификатор снимка текущего запроса |
| `capturedAt` | RFC 3339 UTC | Время формирования снимка Chatballs |
| `scope` | Массив ссылок | Все текущие экспортируемые пары `sourceConnectionId + fieldId` |
| `items` | Массив FieldValue | Ровно одна запись на каждую пару `scope`; дубликаты запрещены |

Снимок относится к контакту текущего разрешённого диалога и согласованным WEB-источникам. Его область не расширяется до всех данных контакта автоматически. Ключ, название и значения хранятся в исходном виде без локализованного превращения числа/boolean в текст.

`mode: replace` означает: GoCoStack заменяет **рабочий контекст кастомных полей** сессии целиком данным снимком, а не сливает его с прежним объектом. Отсутствующее в новом `scope` поле больше не используется из старого кеша. Это правило текущего контекста; оно не является ложным подтверждением физического удаления всех исторических копий GoCoStack. Их хранение регулируется соглашением сторон.

### Элемент FieldValue

| Поле | Тип | Обязательность и смысл |
|---|---|---|
| `sourceConnectionId` | Непрозрачная строка | Обязательно; разрешённый WEB-источник |
| `fieldId` | Непрозрачная строка | Обязательно; устойчивый ID текущего определения поля |
| `key` | Строка | Обязательно; машинный ключ из схемы источника |
| `label` | Строка | Обязательно; текущая подпись поля |
| `type` | Enum | Обязательно; один из типов таблицы ниже |
| `status` | `set \| unset \| invalid` | Обязательно; состояние текущего значения |
| `value` | JSON-значение или null | Обязательно; типизированное значение только при `set` |
| `updatedAt` | RFC 3339 UTC или null | Обязательно; фактическое время записи значения, если запись существует |
| `options` | Массив вариантов | Обязательно только для `enum`; у других типов отсутствует |
| `reasonCode` | Строка | Обязательно только для `invalid`, без невалидного исходного значения |

Вариант enum содержит `value`, `label` и, если задан в текущей схеме, `color`. Значение поля — именно код `value`, а не отображаемая подпись. Цвет — необязательные метаданные, не команда изменить продуктовый UI.

| `type` | JSON-тип `value` при `set` | Правило |
|---|---|---|
| `string` | string | Сохраняется фактическая строка, включая допустимую пустую |
| `number` | number | Число, не форматированная строка; boolean не является числом |
| `boolean` | boolean | `true` / `false`, не «Да/Нет» и не `0/1` |
| `datetime` | string | Валидированная исходная строка ISO 8601; отсутствующий часовой пояс не выдумывается |
| `enum` | string | Один из текущих кодов `options[].value` |
| `email` | string | Значение, прошедшее штатную проверку CB |
| `phone` | string | Сохранённое нормализованное значение CB |
| `url` | string | Значение, прошедшее штатную проверку CB |

Служебные `capturedAt` / `updatedAt` всегда передаются в UTC. Значение пользовательского `datetime` не переинтерпретируется при экспорте: существующая модель может содержать ISO 8601 без явного смещения.

### Значение отсутствует, пустое или некорректное

| Состояние в CB | Передача |
|---|---|
| Есть валидное значение | `status: set`, исходный типизированный `value`, реальный `updatedAt` |
| Валидные `""`, `0`, `false` | `status: set`; не заменяются на null и не пропускаются |
| Для действующего разрешённого определения нет сохранённой записи | `status: unset`, `value: null`, `updatedAt: null` |
| Значение очищено штатным `setFields(...null...)` | Следующий снимок содержит то же `unset`; старое значение удаляется из рабочего контекста GoCoStack |
| Сохранённая запись не соответствует текущему типу/вариантам/формату | `status: invalid`, `value: null`, фактический `updatedAt`, безопасный `reasonCode` |
| Поле удалено из схемы или больше не разрешено | Его нет в новом `scope/items`; старое разрешение не позволяет продолжить экспорт |

Коды `invalid`: `type`, `option`, `format`, `length`, `schema`. Это безопасная причина, не само невалидное значение. Нельзя сохранять прежнее значение в рабочем контексте только потому, что новое стало `invalid`.

**Ограничение существующей модели:** CB при очистке удаляет запись значения. Без дополнительной истории нельзя достоверно отличить первое отсутствие значения от прежней очистки или сообщить точный `clearedAt`. Контракт не вводит выдуманное состояние «когда-то было очищено». Для интеграции важен актуальный `unset`, который явно сбрасывает прежнее значение.

Удаление определения не гарантирует физическое удаление старой строки значения в CB. Такие строки без действующего определения не экспортируются. Если тип изменён, сохранённое значение повторно проверяется по текущей схеме до экспорта.

Для защиты от смены схемы «A → B → A» сервер хранит монотонную generation WEB-схемы: штатный путь сохранения определений повышает её в той же транзакции при действительном изменении. Generation входит в привязку авторизации/отпечаток вместе с ревизией allowlist и сохраняется в БД; один hash текущего содержимого или наблюдение только при dispatch недостаточны. Существующий runtime_revision источника сейчас обслуживает LLM/SPEECH и не объявляется уже готовой версией WEB-схемы. Реализация добавляет внутренний учёт generation без изменения публичного setFields и без пересоздания значений/ключей.

### Обновления, очередь и восстановление

1. Chatballs формирует снимок для очередного AgentRequest из текущих разрешённых определений и значений контакта. Порядок записей детерминирован: источник, порядок схемы, ID поля.
2. Снимок и состав разрешений замораживаются вместе с request до HTTP. Сетевой повтор сохраняет `snapshotId`, `capturedAt`, значения и общий digest.
3. Изменение только значения появляется в следующем допустимом запросе. Оно не переписывает уже принятый запрос и само не запускает новый автономный ход или webhook.
4. Обновление схемы экспортируемого поля либо состава разрешённых источников/полей изменяет контрольный отпечаток политики внешнего исполнения. Он проверяется до dispatch/применения/доставки вместе с версиями; удаление/отзыв не обходятся старым запросом, курсором или инициативой.
5. Повторное создание поля под прежним ключом получает новый ID и требует нового явного разрешения. Возврат настроек назад не оживляет старую авторизацию.
6. После сотрудника следующий допустимый запрос формирует свежий снимок. Повтор старого запроса не откатывает более новый контекст памяти; GoCoStack учитывает устойчивые ID и порядок ходов.
7. История сообщений не является историей всех изменений кастомных полей. Пагинация истории сохраняет свою границу; актуальный снимок полей передаётся отдельным блоком AgentRequest.
8. Если полный блок нарушает лимит запроса, CB не обрезает поля скрытно и не отправляет частичный `replace`: применяется проверяемая ошибка подготовки контекста и штатная передача сотруднику.
9. Снимки и приёмочные проверки используют тот же защищённый контур хранения и журнал без сырых значений, что и остальные данные запроса.

**Запись из GoCoStack в кастомные поля этим контрактом не разрешена.** AgentResult, callback и инициативное сообщение не принимают patch контакта или определений. Существующий сайт/штатные операции CB остаются источником изменений.
