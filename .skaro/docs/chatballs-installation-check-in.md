# Check-in установки Chatballs в Backoffice

Источники: `Chatballs Backoffice/.skaro/docs/chatballs-installation-check-in.md`, `docs/installations-api.md` и `docs/announcements-api.md` репозитория Backoffice. Требования к Chatballs — SPEC-0005 R-15…R-20 и ADR-0027.

## Обращение

`POST https://bo.chatballs.ru/public/v1/installations/check-in/` с `Content-Type: application/json`. Вызов только с сервера установки, с проверкой сертификата. Сессионные cookie, CSRF, токены и перенаправления не используются.

```json
{"installation_id":"68254058-03d8-4a51-9079-fbcb125698e3","version":"1.22.0","public_url":"https://chat.example.com"}
```

| Поле | Контракт |
| --- | --- |
| `installation_id` | Постоянный UUIDv4 с дефисами. Сгенерировать и сохранить до первого запроса. Перенос и восстановление той же установки сохраняют его. Независимая копия получает другой UUID. |
| `version` | Фактически запущенная версия `CHATBALLS_VERSION` без преобразования для semver, включая dev и prerelease. Строка длиной 1–255 символов без управляющих символов. |
| `public_url` | Необязательный настроенный внешний HTTP(S)-адрес с доменом или публичным IP. Если задан порт, он входит в адрес. Логин, пароль, параметры запроса и фрагмент исключаются. |

Тело запроса ограничено 4096 байтами. Для каждой разрешённой попытки берётся актуальный адрес из существующих настроек установки: явное переопределение `CHATBALLS_PUBLIC_BASE_URL` либо сохранённые схема, хост и порт. Встроенное значение для localhost, локальные имена, непубличные IP и адрес сетевого соединения не используются как внешний адрес. Без пригодного внешнего адреса запрос содержит только UUID и версию. Смена адреса сохраняет UUID. Данные организаций и пользователей, логи и секреты не передаются. Сетевой адрес соединения виден принимающей стороне как часть HTTPS-транспорта, публичный маршрут Backoffice учитывает лимит по адресу. В запрос GitHub UUID и внешний адрес не добавляются. Передача `public_url` включается после развёртывания поддержки поля по T-021 в проекте Backoffice.

## Расписание и настройка

Настройка «Получать обновления и сервисные сообщения. В Backoffice передаются идентификатор установки и внешний адрес, если он настроен.» по умолчанию включена. Для всех организаций действует одна настройка. Ею управляет пользователь с правом управления «Платформой» по ADR-0024. Выключение останавливает новые фоновые и ручные проверки GitHub и обращения за отметкой связи и публикациями. При отключении сервер также закрывает соединение доставки публикаций. Повторное включение использует прежний UUID. Проверка, начатая до отключения, не запускает повтор и не приводит к показу сообщений при выключенной настройке.

Плановая отметка связи выполняется раз в сутки. Это расписание не ограничивает синхронизацию публикаций. Сервер Chatballs держит открытое исходящее защищённое соединение с Backoffice. Сразу после успешного сохранения Backoffice отправляет подходящей подключённой установке новую публикацию или изменение. Если окно уже началось и ещё действует, сервер Chatballs сразу сообщает об изменении открытой рабочей оболочке. Баннер появляется без обновления страницы. При подключении или восстановлении связи установка получает полный актуальный список действующих и запланированных публикаций. Реализован отдельный POST /public/v1/installations/publications/stream/ с SSE-снимками расписания и heartbeat; точный контракт описан в docs/publication-stream.md проекта Backoffice. Суточный check-in сохраняет прежний ответ для старых клиентов. Штатный poller резервирует попытку в PostgreSQL и освобождает базу до HTTP. Выбор исполнителя не полагается на локальные переменные процесса. Первый цикл штатного воркера после смены версии `CHATBALLS_VERSION` резервирует check-in с прежним UUID, даже если суточный срок ещё не наступил. Перезапуск с той же версией соблюдает сохранённое расписание. Выключенная настройка, действующая резервация и срок ожидания после 429 имеют приоритет. Операция с ограниченным сетевым временем сохраняет результат только для актуальной попытки. Штатное клонирование базы для отдельно работающей копии выделяет свой UUID до разрешения внешних обращений и не переносит расписание или список сообщений от источника. Для проверки на изолированной копии исходящие обращения контролируются до запуска воркера; вызов реального Backoffice нужен только в согласованном контуре.

## Успех

Поток публикаций отвечает `200 OK` и передаёт SSE-события `snapshot` с `serverNow` и массивом `announcements`. Пустой массив — валидный результат. Это отдельный маршрут, суточный check-in сохраняет прежний ответ без границ окна.

```json
{"announcements":[{"id":42,"title":"Плановое обслуживание","text":"Вечером возможен короткий перерыв.\n\nПодробности на сайте.","link":"","starts_at":"2026-12-01T15:00:00Z","ends_at":"2026-12-01T20:00:00Z"}]}
```

Backoffice передаёт подходящие действующие и запланированные публикации. Завершённые публикации в целевой ответ не входят. Для стабильной `X.Y.Z` он добавляет сообщения общей аудитории и подходящих диапазонов с включёнными границами. Dev, prerelease и другие принятые строки получают только общие сообщения. Порядок — сначала более позднее начало, при равенстве ID по возрастанию. В ответе есть только поля публикации `id`, `title`, `text`, `link`, `starts_at`, `ends_at`. Обе отметки времени обязательны, передаются в ISO 8601 с явным часовым поясом и обозначают абсолютные моменты. `ends_at` должен быть позже `starts_at`. Заголовок и текст отображаются как текст с сохранением абзацев. Пустая ссылка скрывается. Непустая ссылка проверяется как абсолютный HTTP(S)-адрес без учётных данных и не загружается при приёме сообщения.

Первый суточный check-in создаёт запись без назначений. Повтор сохраняет первую связь, клиента, специалиста и ручные технические сведения, записывает версию и обновляет последнюю связь серверным временем. Сообщённый адрес позволяет администратору Backoffice найти карточку по домену или IP и вручную назначить клиента. Chatballs не вызывает служебный API Backoffice.

Каждый валидный снимок потока заменяет сохранённый список целиком, включая пустой. Сервер установки и открытая оболочка показывают каждое подходящее незакрытое сообщение только при `starts_at <= now < ends_at`. В момент начала и в момент окончания окна оболочка обновляет баннер без перезагрузки и без нового обращения к Backoffice. Когда текущее сообщение истекает, оболочка показывает следующее подходящее незакрытое сообщение по порядку Backoffice или скрывает полосу. Если окно уже началось при получении, сообщение доступно до исходного окончания. Если окно полностью прошло, сообщение пропускается. Ошибка связи не продлевает окно. При отключении баннер скрывается, после повторного включения нужен свежий результат. В Chatballs сообщения доступны пользователю с правом управления «Платформой» по ADR-0024 в верхней полосе рабочей оболочки. Она показывает полные заголовок и текст с абзацами по одному сообщению за раз. Крестик закрывает текущее сообщение и показывает следующее в порядке Backoffice. «Подробнее» открывает адрес из поля `link`. Общий переключатель остаётся в карточке «Обновления» в настройках платформы.

До развёртывания расширения действующий check-in возвращает только активные публикации без границ. Backoffice сохраняет этот ответ для старых клиентов. Запланированные сообщения выдаются только клиентам, которые поддерживают расписание.

## Ошибки и повторы

| Ситуация | Реакция Chatballs |
| --- | --- |
| `400` | Зафиксировать ошибку входных полей. Ускоренный повтор того же тела не запланирован. |
| `413`, `415` | Зафиксировать ошибку размера или формата. Ускоренный повтор того же тела не запланирован. |
| `429` | Отложить попытку как минимум на полученный `Retry-After` в секундах. При некорректном или отсутствующем заголовке применить обычную задержку временной ошибки. Не увеличивать частоту из-за нескольких установок за прокси. |
| Тайм-аут, сетевой сбой, `5xx` | Повторить с ограниченной частотой и прежним UUID. Идемпотентность по UUID предотвращает вторую карточку. |
| Некорректная выдача | Зафиксировать ошибку контракта, сохраняя исходные окна предыдущих валидных публикаций. |

Диагностика ограничивается видом сбоя и техническим статусом без журналирования исходящего тела. Ошибка check-in хранится отдельно от ошибки GitHub. Один сбой не прерывает выполнение другой проверки. `updater` применяет релизы по прежнему протоколу ADR-0027.

## Приёмка

1. На согласованной установке включить настройку, отметить связь и найти один UUID в Backoffice.
2. Перезапустить или обновить тот же экземпляр. Сверить UUID, актуальную версию, первую и последнюю отметки связи. Сверить сохранность назначений и ручных сведений.
3. На согласованном штатном контуре опубликовать сообщение с началом «сейчас» и окончанием вечером. Проверить, что подключённая установка показывает его сразу после получения, пока суточный check-in ещё не наступил. Проверить также восстановление связи, пустой список и публикацию с абзацами, полученную до начала окна. В открытой оболочке проверить появление в `starts_at` и исчезновение в `ends_at` без нового обращения. Отдельно проверить изменение окна, потерю связи перед окончанием, позднее получение и совместимость старого клиента.
4. Выключить настройку и проверить отсутствие фоновых и ручных запросов GitHub и новых check-in. Включить её и сверить прежний UUID. На независимой копии проверить новый UUID до разрешения исходящей связи.
5. На стороне Chatballs проверить отправку домена или публичного IP с портом, смену адреса с прежним UUID, отсутствие поля без настроенного внешнего адреса, очистку значения и подчинение общей настройке. Сверить подсказку существующего переключателя.
