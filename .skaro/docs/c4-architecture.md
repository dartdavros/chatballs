# C4-архитектура Chatballs

## Назначение и границы пакета

Пакет переносит существующую архитектуру в общую семантическую модель Skaro. Он не вводит новых функций, прав, экранов, сервисов или способов production-миграции. Исходные бриф, архитектура, 37 ADR, 36 спецификаций и проектные записки сохраняются. В пакет переданы полные тексты архитектуры и спецификаций без изменения требований, чтобы Skaro вычислил хеши и привязал требования к схеме.

Срез построен по коду основной рабочей копии на 17.10.2026, HEAD `38520b751931e4bd1940b995bba2e61ca458b4fe`, контексту Skaro и существующим изменениям документов. Проверка в этой работе статическая: чтение исходников и конфигурации, проверка наличия путей и целостности модели. Работа не запускает приложение, seed, тесты, сборку, обновление или миграцию. Наличие архитектурной трассировки не является заявлением о прохождении функциональных тестов.

## Как читать схему

Skaro формирует интерактивные схемы из модели и управляет их композицией. Здесь нет собственных Mermaid/SVG, координат или стилей.

| Вид | Что показывает |

| view-containers | Браузерные приложения, Django, данные, шлюзы, CLI и поставка |
| view-backend-core | Доступ, маршруты, коммуникации и фоновые роли |
| view-backend-ai | Знания, псевдонимизация, провайдеры, HTTP/MCP, навыки и помощь |
| view-backend-support | Совместная работа, доступность, метрики, оценки, анализ и правила |
| view-workbench | Состав интерфейса организации и публичного Help Center |
| view-widget | Веб-чат, наблюдения посетителя, оценка, P2P-клиент и снимки ответов |
| view-tooling-cli / updater / secrets | CLI, генератор секретов и updater |
| view-code-component-* | Код каждого серверного компонента с путями к исходникам; межкомпонентные зависимости показаны отдельно на компонентном уровне |

| view-planned / view-planned-cli / view-planned-backup | Будущая телефонная интеграция и отсутствующие команды резервирования/восстановления |

## Один backend и разные процессы

`container-backend` — логический контейнер единственного Django-приложения. Доменные компоненты внутри него не являются микросервисами. Тот же код и образ запускаются как отдельные deployment-экземпляры:

- `backend-app`: tenant/public API и WebSocket, роль app, без platform/schema credentials;
- `backend-platform`: отдельные URLConf, host и cookie, роль platform;
- `backend-admin`: техническая поверхность с migration credentials, только loopback;
- `worker`: один poller, app с platform alias для межорганизационного захвата/каталогов;
- `worker-events`: по умолчанию две реплики обработки outbox, tenant-операции в коротких транзакциях;
- `init`: одноразовые миграции под migration-ролью.

Так схема сохраняет общую кодовую базу и одновременно показывает разные границы привилегий. Вызовы между доменными компонентами — Python-вызовы/ORM внутри соответствующего процесса, а не сетевые запросы между сервисами.

`internal-ui` и `web-chat` исполняются в браузере, nginx только раздаёт сборки и проксирует backend. Публичный портал использует ту же internal-ui сборку с выбором по host. Лоадер `chat-widget.js` собирается backend из существующих loader_assets. Общие packages/ui, contracts и shared входят в frontend-сборки и не изображаются отдельными сетевыми сервисами.

## Данные и сетевые границы

PostgreSQL — единственная доменная БД: tenant-RLS, FTS/pgvector, inbox/outbox и факты диалогов. Redis служит кэшу, realtime и presence, не заменяет надёжную очередь. Контекст организации устанавливается через SET LOCAL в транзакции; внешнее organization_id не даёт права доступа.

Caddy принимает публичный HTTP/HTTPS, nginx направляет app API/WS в backend-app, а отдельный platform host ведёт в backend-platform. Django admin не публикуется через gateway. Coturn имеет собственную сетевую границу. P2P-медиа идёт между браузерами напрямую или через TURN; Django обслуживает signaling и жизненный цикл, не получает декодированное медиа и не сохраняет SDP/ICE.

Текстовые вызовы AI проходят псевдонимизацию; карта значений живёт только в памяти хода. Внешние HTTP/MCP-инструменты текущей версии только читают, используют явные разрешения и защищённый исходящий клиент. Собственная коммерческая мастер-база в Chatballs не появляется.

## Трассировка документов

Для каждой из 36 спецификаций сохранены существующие ID и путь. Каждое из 480 требований R-n связано с элементами, отношениями и соответствующими представлениями. Связи обозначены `uses`: описание поведения не меняется. В SPEC-0021 и SPEC-0022 только формат двух перекрёстных ссылок записан как «SPEC-xxxx, требование n», чтобы валидатор Skaro не считал упоминание требования другой спецификации новым местным R-n. Нумерация и содержание собственных требований сохранены. Skaro вычисляет bodyHash из переданного текста.

ADR связаны с элементами и отношениями, которыми управляют. ADR-0004 имеет статус superseded и не используется как действующее основание: его заменяет ADR-0031. Поздние ADR-0033–0037 и связанные спецификации учитываются вместе с существующим кодом. Исторические пути с именем sales отражают каталог компонентов контактов, а не возвращение продаж/CRM.

## Расхождения старого архитектурного текста и текущего среза

Старый текст architecture.md сохраняется целиком; схема не переписывает правила реализации. При чтении его ранних разделов учитываются следующие подтверждённые уточнения:

| Старое описание | Подтверждённый текущий срез и основания |
|---|---|
| §14: псевдонимизация не реализована, aiVisible | Есть ai/pseudonymization.py, invocation.py, маскирование вопроса эмбеддинга и aiAccess в webchat/field_schema.py. SPEC-0022, ADR-0031; задачи M06 завершены |
| §14: внешние инструменты не реализованы | Есть integrations/mcp_client.py, http_tool.py, tool_client.py, tool_network.py, ai/tool_loop.py и настройки UI. SPEC-0023, ADR-0032; задачи M07 завершены |
| §4: Channel–AIAgent строго 1:1, агент обязателен | ADR-0037/SPEC-0036 и identity/operation_modes.py, integrations/operator_routes.py задают Channel 1 — 0..1 AIAgent и независимые операторские подключения |
| §5: только OWNER/ADMIN/EMPLOYEE | Есть SUPERVISOR и отдельная область контроля: identity/supervision_models.py и policy.py, ADR-0033/SPEC-0029 |
| §7: новый диалог всегда ведёт AI | Общая политика autonomous_allowed учитывает режим организации, реального агента и состояние маршрута; операторский вход сразу создаёт ожидание человека |
| Ранний список модулей не раскрывает расширения поддержки и навыки | Текущие conversations/quality, conversations/rules, ratings, work_status, skills и соответствующие frontend-фичи показаны самостоятельными компонентами внутри прежнего монолита |

Эти уточнения относятся к архитектурному отображению уже существующего кода и принятых документов. Схема не объявляет всю реализацию повторно принятой и не меняет спецификации.

## Планируемое и неприменимые уровни

Будущая интеграция облачных телефонных AI-звонков оставлена planned по брифу и T-006. API-контракт и клиентская реализация не выдуманы. Текущий P2P-контур показан отдельно.

Команды CLI doctor/deploy/status/logs существуют. Backup/restore/install/update/rollback ещё отсутствуют в chatballs и deploy/cli/lib; SPEC-0005 R-13 и T-001/T-002 остаются планируемым контрактом. На схеме не выдаются за реализованные резервирование или восстановление.

Документ docs/service-integrations-c4.md сохраняется как записка о будущем механизме. У него нет принятой спецификации; пакет текущей схемы не разрешает запись во внешние системы и не отменяет ADR-0032. Вопрос о соответствующем будущем пакете оставлен явно.

Внутренности сторонних AI/почтовых/мессенджерных/S3/ACME/Docker-систем не принадлежат этому репозиторию: показаны только известные интерфейсы. Для nginx/Caddy/PostgreSQL/Redis/Coturn приводятся конфигурация и deployment, без выдуманного исходного кода сторонних проектов. Файловые тома не имеют прикладных классов/компонентов.

Обзорные code-виды раскрывают архитектурно значимые модули и общие browser-механизмы; полный перечень методов каждого UI-компонента не добавляется. Причины пропуска каждого такого scope/уровня записаны в exclusions модели с evidence. Dev/task overrides не трактуются как вторая production-топология. Kubernetes/multi-node HA исключены SPEC-0005.

Открытые вопросы модели относятся к уже обозначенным будущим работам: контракт телефонного сервиса, принятие отдельной спецификации сервисных сценариев и существующее расхождение CLOUD/SELF_HOSTED в скриптах запуска. Ни один из этих вопросов не разрешается молча принятием схемы.

## Планируемое расширение: интеграции сервисов

Исходный импорт выше сохраняет текущую архитектуру и её IDs. Отдельный планируемый слой SPEC-0037/ADR-0038 расширяет общую модель: адаптеры с готовыми сценариями, пользовательские сценарии и все публичные действия платформы; существующий модульный монолит/Compose сохраняется. Подробности и индекс всех новых представлений: [Интеграции сервисов](service-integrations-c4.md). Сроки по решению владельца: данные шагов — 7 дней, журнал — 30 дней после завершения запуска по умолчанию, активные ожидания защищены. Отметка planned снимается только после проверенной опубликованной реализации. Архитектурный пакет не создаёт задач и не означает личной приёмки будущего baseline.
