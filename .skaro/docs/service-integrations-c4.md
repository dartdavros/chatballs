# Интеграции сервисов: единое описание механизма и C4

## Суть решения

Реализуем общий расширяемый механизм интеграций. Затем добавляем адаптеры конкретных систем — CRM, Mindbox и других сервисов. Каждый адаптер сразу поставляется с полезными готовыми сценариями. Пользователь подключает сервис, выбирает сценарий, заполняет необходимые настройки и пользуется им. Если подходящего сценария нет — изменяет готовый или создаёт свой без программирования обычной бизнес-логики.

Поддерживаются одновременно чтение, создание, изменение, удаление и другие операции внешних систем; команды сотрудника и ИИ; события, расписания, внешний API и действия самого Chatballs. Заранее известные сценарии служат примерами и не ограничивают будущие интеграции.

В существующем разделе интеграций добавляется третья пользовательская группа — сервисы. Две существующие группы — точки входа диалогов и внешние серверы — сохраняются; AI-провайдеры имеют отдельное назначение. Название и оформление новой группы проходят личную приёмку владельца в baseline.

Механизм остаётся частью существующего Django-приложения и использует PostgreSQL, штатные worker/worker-events и inbox/outbox. Отдельные обязательные микросервисы, БД, брокер и внешняя платформа автоматизации не нужны.

Порядок работ: согласованная документация → задачи создания baseline в текущем формате .dc.html → личная приёмка владельца → реализация общего механизма и UI по принятому baseline → конкретные адаптеры с готовыми сценариями. Визуальные компоненты переиспользуются; новый переиспользуемый компонент создаётся, если подходящего нет.

Это проектная записка с конкретным устройством механизма. Нормативные требования находятся в [SPEC-0037](../specs/0037-rasshiryaemye-integratsii-servisov-i-sts.md), решения — в [ADR-0038](../adr/0038-servisnye-adaptery-i-ustoychivye-stsenarii.md). Текущая и планируемая архитектура разделены в общей C4-модели. Skaro строит все схемы и открывает их на интерактивном canvas; этот текст не задаёт оформление схем или baseline UI.

## Сценарии использования

1. Администратор добавляет сервисное подключение, выбирает установленный адаптер, настраивает доступ и получает его готовые сценарии. Заполняет необходимые поля и явно включает выбранный сценарий.
2. Сотрудник запускает доступный сценарий в контексте диалога/контакта. Операции CRM создают или изменяют связанные записи, а действия Chatballs добавляют метку, назначают ответственного и отправляют сообщение по настройке сценария.
3. ИИ вызывает разрешённую операцию или сценарий с записью во внешнюю систему. Режим действия определяет самостоятельное выполнение либо подтверждение сотрудником; общего запрета записи нет.
4. Пользователь создаёт свой сценарий: событие, условия, несколько шагов из Chatballs и разных сервисов, соответствия полей, ветвление, ожидание и обработка ошибки. Ядро не дорабатывается под этот бизнес-сценарий.
5. Событие CRM запускает несколько независимых сценариев. Один переводит диалог в группу, другой уведомляет сотрудника. Повтор webhook не повторяет эффекты.
6. Сотрудник запускает цепочку «операция компенсации во внешнем сервисе → задача в CRM → сообщение клиенту». Сообщение об успехе отправляется только после подтверждённой компенсации; частичный результат виден по шагам.
7. Воркер падает после выполнения внешней операции, но до сохранения результата. Следующий воркер использует прежний ключ эффекта и стратегию сверки адаптера; подтверждённые шаги не запускаются заново.
8. Если результат установить нельзя, пользователь видит неизвестный исход и предусмотренные действия разбора. Ошибка или неизвестность не выдаётся за успех.
9. Позднее разработчик добавляет адаптер другой системы с её собственными операциями, событиями и готовыми сценариями. Общий исполнитель и общие экраны не получают условий по названию этого сервиса.
10. Настроенная синхронизация сопоставляет записи и поля двух систем, разрешает конфликты по заданному правилу и предотвращает дубли/обратный цикл.

Примеры 2 и 6 поясняют поведение механизма; они не являются закрытым перечнем действий или реализацией конкретного брендового адаптера в рамках общего механизма.

## Функциональные требования

R-1–R-31 полностью перенесены в SPEC-0037 без ограничения возможностей; их архитектурные привязки входят в общий пакет. Сроки хранения теперь согласованы владельцем: данные шагов — 7 дней, журнал — 30 дней после завершения запуска по умолчанию. Остальная договорённость сохранена.

## Границы текущего механизма

- Реализация пакетов Mindbox/amoCRM/Битрикс24 именно в задачах общего механизма: они следуют после него на том же контракте и с готовыми сценариями.
- Собственная CRM/коммерческий учёт как мастер-база Chatballs.
- Обязательная внешняя workflow-платформа, дополнительная БД/брокер/микросервисы.
- Горячая установка недоверенного серверного кода/маркетплейс. Доверенные программные адаптеры входят в установленную версию приложения.

Этот раздел не исключает новые сервисы/сценарии, чтение/запись/удаление, действия Chatballs, сложные данные и какой-либо согласованный способ запуска.

## Что уточняется при дальнейшем проектировании

- Композиция редактора, вкладка «Сервисы», раздел «Сценарии», составные шаги/подтверждения и состояния приняты владельцем по третьему архиву 22.10.2026. Архитектура следует этому baseline и согласованному дополнению таблицы статусов.
- Конкретные операции/готовые сценарии каждого будущего брендового адаптера задаются его спецификацией; заранее закрытый перечень не требуется для расширяемости механизма.
- Сроки хранения согласованы: данные шагов — 7 дней, журнал — 30 дней после завершения запуска по умолчанию, с настройкой OWNER/ADMIN и защитой активных ожиданий.

## Предлагаемое решение

Пользователь видит подключённые сервисы и сценарии. Реализация состоит из реестра адаптеров/действий, определения сценария и одного устойчивого исполнителя. Доступ, внешние вызовы, прогресс и результаты общие для всех способов запуска.

Адаптер содержит описание операций, событий, авторизации, полей настройки и готовых сценариев, а также обработчики особенностей сервиса. Сценарий хранит условия, шаги и соответствия данных. Добавление сервиса не требует ветвлений по его имени в ядре.

Проектная третья группа — «Сервисы». Предлагаются Integration.kind=SERVICE и общий provider=ADAPTER; конкретный adapter_key хранится в отдельной записи настроек. Новому бренду не нужен новый enum. AI-провайдеры, мессенджеры и внешние серверы сохраняют типы. Сервисное подключение не требует Channel или AIAgent.

## C4 · уровень 1. Контекст системы

Кто пользуется Chatballs и с какими внешними системами взаимодействует механизм интеграций.


Сотрудник, ИИ, внешнее событие и автоматизация используют один механизм. ИИ выбирает разрешённое действие, а проверяет и выполняет его сервер. Chatballs взаимодействует с системами организации через их адаптеры.

## C4 · уровень 2. Контейнеры

Механизм использует существующие приложения, базу и воркеры. Контейнер C4 обозначает приложение или хранилище, а не отдельный новый микросервис.


PostgreSQL — источник истины о заданиях и прогрессе. Redis не становится второй очередью сценариев. worker планирует сроки и выполняет предусмотренный адаптером опрос. worker-events исполняет ограниченную порцию работы и сохраняет продолжение. Ожидание освобождает процесс.

Показан относящийся к интеграциям срез системы. Gateway, Redis, файловое хранилище и остальные поверхности проекта сохраняются; размещение показано отдельно.

## C4 · уровень 3. Управление и приём запросов

Компоненты внутри backend-app. API не исполняет длинный сценарий в пользовательском HTTP-запросе.


API выдаёт каталог реально установленных адаптеров, схемы полей/справочников, готовые сценарии и журнал. Готовый сценарий создаёт редактируемую копию организации; обновление адаптера не затирает её. Сохранение конфигурации не запускает сценарий и не выдаёт скрытых прав.

Сервис запуска атомарно создаёт снимок сценария, запуск и outbox-задание. Повтор запроса возвращает тот же логический запуск. Долгая работа не исполняется внутри HTTP-запроса. Предлагаемые ресурсы API: каталог адаптеров, сервисные подключения, сценарии, запуски/шаги и связи сущностей. Команды запуска, подтверждения, сверки и отмены проходят общую проверку.

Сценарии организации работают в её области. Административные действия установки/платформы используют соответствующую поверхность и действующие полномочия; tenant-подключение не получает административных прав установки.

## C4 · уровень 3. Исполнение

Компоненты внутри worker-events используют общий прикладной код с API. Ни реестр, ни исполнитель не содержат ветвлений по названию CRM.


Исполнитель сценария интерпретирует шаги. Исполнитель действия одинаково вызывает внешний адаптер и зарегистрированную обёртку доменного сервиса Chatballs. Встроенные действия не вызывают внутренний HTTP API и не пишут произвольно в таблицы.

Для всех публичных продуктовых действий Chatballs требуется проверяемое соответствие в реестре: диалоги/сообщения/контакты, сотрудники/группы, агенты/навыки/знания, порталы, файлы/звонки, уведомления, отчёты и настройки. Новая функция добавляет описание действия. Это полнота каталога, а не закрытый список бизнес-сценариев. Аутентификация и транспортные endpoints сохраняют штатные протоколы; автоматической публикации секретных endpoints нет.

Короткая транзакция захватывает шаг и сохраняет маркер попытки. Внешняя операция идёт без удержания БД; следующая транзакция фиксирует результат и продолжение. Для сценариев используются собственные типы заданий и ключи агрегатов, чтобы ожидание не блокировало весь диалог. Планировщик обеспечивает обслуживание сообщений/ИИ и других подключений.

## C4 · уровень 4. Контракт адаптера

Предлагаемые интерфейсы кода. Метаданные действий и готовых сценариев поступают в общий UI из адаптера.


Контракт включает идентификаторы и версию, схему настройки/авторизации, входы и выходы операций, события, готовые сценарии и стратегию восстановления. Имена интерфейсов на схеме предлагаемые.

Обязательны описание адаптера и его операций. connect/check/execute/resume/reconcile и обработчики событий реализуются по объявленным возможностям. Неподдерживаемая сервисом возможность фиксируется явно. OAuth, обновление токенов, подписи webhook, callbacks, опрос с cursor, сертификаты и нестандартные протоколы обслуживаются зарегистрированными обработчиками.

Поддерживаются чтение, создание, изменение, удаление, поиск, пакетные/длительные операции и файловые данные. Вложенные объекты, массивы, перечисления, справочники, даты и ссылки на файлы описываются схемой. Бинарные/большие данные идут через штатное файловое хранилище.

Общие HTTP/API- и MCP-адаптеры дают настраиваемый доступ к API; нестандартный протокол — доверенный программный адаптер. Пользовательский сценарий не исполняет Python/SQL/JavaScript. Авторизация, транспорт, преобразования и необходимые контролы расширяются по контракту.

Будущий пакет CRM содержит настройку доступа, операции, события и готовые сценарии. Названия Mindbox/amoCRM/Битрикс24 обозначают будущие адаптеры, а не уже работающие подключения.

## Модель данных и владение

Логическая модель целевого решения. Наличие этих блоков не означает существование таблиц в текущем коде. Владелец всех tenant-записей — организация.


Логическая модель показывает предлагаемые записи, а не уже существующие таблицы.

Integration сохраняет общие поля подключения. SERVICE_SETTINGS добавляет adapter_key, версию, настройки и зашифрованные credentials. Старые подключения доступны через мост без копирования секретов и автоматической выдачи прав.

SCENARIO хранит определение, техническую ревизию и разрешения. SCENARIO_RUN фиксирует снимок, инициатора, контекст и ключ запуска. STEP_EXECUTION сохраняет путь шага/итерации/ветви, ключ эффекта, состояние, lease и необходимые значения/ожидания/подтверждения. Отдельной публикации сценария нет.

EVENT_RECEIPT устойчиво хранит входящий конверт. В существующем InboxEvent есть hash, но нет тела: одного hash недостаточно для продолжения. OUTBOX_EVENT несёт идентификаторы, а не секретные payload.

ENTITY_LINK связывает произвольные виды сущностей конкретного подключения. Для синхронизации задаются поля, источник истины, конфликты, удаление и предотвращение обратного цикла. Телефон/email не доказывает личность и не вызывает скрытое слияние.

ACTION_GRANT делегирует доступ агенту/инициатору; разрешения сценария хранятся в его определении. Новая ролевая модель не вводится. Организация, RLS и проверки связей обязательны.

Для восстановления разрешено минимальное операционное состояние с шифрованием чувствительных значений. Секреты берутся из защищённых credentials, карта псевдонимов не сохраняется. Это не разрешение складывать сырые промпты/ответы старых инструментов в журнал. По решению владельца данные шагов удаляются через 7 дней, безопасный журнал — через 30 дней после завершения запуска по умолчанию. OWNER/ADMIN могут изменить сроки; активные ожидания защищены. Минимальные ключи дедупликации сохраняются на окно повторов/сверки без payload. Операционные копии файлов без независимого владельца очищаются с данными шагов; аудит сохраняет свою политику.

## Динамика. Запуск сотрудником или ИИ

Оба инициатора приходят в один сервис запуска. Runtime ИИ вызывает его напрямую, а не через HTTP к собственному приложению.


Все способы запуска поддерживаются совместно: сотрудник, ИИ, внутреннее/внешнее событие, расписание, аутентифицированный API и вложенный сценарий. Два первых показаны на схеме.

Для ИИ на операции/сценарии задаются запрет, самостоятельное выполнение или подтверждение сотрудником. Обязательного подтверждения всех записей нет. Подтверждение связано с точными параметрами/контекстом; изменение требует нового решения. Перед каждым эффектом проверяются актуальные права и отключение сценария/подключения.

Описания/значения/результаты перед моделью проходят действующую псевдонимизацию; значения восстанавливает сервер. Долгая операция возвращает фактическое состояние и идентификатор. Завершение не даёт отозванному ИИ права на позднюю отправку сообщения. Проверочный чат явно отделяет проверку конфигурации от реального изменяющего запуска.

## Динамика. Внешнее событие и несколько сценариев

Подтверждение webhook выдаётся только после устойчивой записи. Один сценарий не мешает другим подписчикам события.


Организация выводится из серверной привязки подключения, подпись/callback проверяется адаптером. После устойчивой записи ответ выдаётся быстро; обработка продолжается фоном. Если webhook нет, адаптер использует опрос и сохранённый cursor.

Отдельный интеграционный обработчик находит подписчиков и ставит независимые запуски. Уникальность — организация, сценарий и идентификатор срабатывания; правка ревизии не делает старое событие новым. Старые обработчики и четыре вида правил не регистрируются повторно.

Ожидание результата сохраняет корреляцию/срок и учитывает дубли/порядок. Callback, пришедший до ожидания, остаётся в durable-записи для сопоставления. Чужой/поддельный callback не завершает шаг.

## Состояния шага и восстановление

Состояние шага отдельно от состояния всего сценария. Неизвестный результат требует сверки; отмена не изображает откат уже сделанного.


Определение сценария поддерживает действия, условия/ветвления, перебор, независимые параллельные ветви, вложенные сценарии, ожидания времени/события/подтверждения и обработку ошибок. Это структуры одного определения и исполнителя. Путь шага различает итерации/ветви; ожидания освобождают воркер.

Отмена останавливает новые эффекты/ожидания. Уже отправленный запрос может завершиться позже; его результат нужно установить. Компенсация — явное поддерживаемое действие, успешные шаги не изображаются откатившимися.

Временные сбои повторяются с backoff/Retry-After; постоянные ошибки прав/параметров не повторяются бесконечно. Паузы/лимиты действуют по подключению. Рекурсия и самопорождающиеся события контролируются причинностью и техническими бюджетами с объяснимым завершением.

## Динамика. Падение после внешнего эффекта

Критическая граница: сервис уже выполнил действие, а локальный результат ещё не записан.


Внешняя система и PostgreSQL не образуют одну транзакцию. Универсальная exactly-once-гарантия без поддержки сервиса невозможна. Операция заранее объявляет безопасный повтор: идемпотентный ключ, сверка, повтор безопасного чтения или разбор неизвестного результата.

Ключ эффекта сохраняется до запроса и не меняется при повторе. Подтверждение шага и следующее задание фиксируются атомарно. После падения на опасной границе записывающее действие не повторяется вслепую.

Lease защищает локальные записи от конкурирующих воркеров, но сам по себе не предотвращает второй внешний эффект. За это отвечает стратегия адаптера.

## C4 · развёртывание

Фрагмент штатного Compose, относящийся к интеграциям. Другие существующие сервисы установки сохраняются.


Компоненты входят в существующий backend-образ. Миграции выполняет init; они не меняют учётные записи, не запускают seed и не включают новые сценарии. Новые обязательные брокеры, БД, микросервисы и тома не требуются.

HTTP-вызовы проходят единую сетевую политику с проверкой DNS и перенаправлений. Loopback и служебные адреса установки недоступны; частные адреса разрешаются политикой администратора установки. Другой транспорт соблюдает эквивалентные ограничения. Секреты не выдаются браузеру/ИИ/обычным логам/outbox.

Проверка продукта использует штатный контур; временный fake backend, mock API и seed для демонстрации не создаются. Проверка конкретного сервиса требует настоящего доступного окружения. Макет не объявляется работающей интеграцией.

## Пользовательский путь без программирования

Функциональная схема для будущего baseline; она не утверждает layout, новые иконки или продуктовые тексты.


Пользователь выбирает готовое решение и заполняет настройки. Если готового нет, создаёт свой сценарий в том же редакторе. Поля/справочники определяются схемами адаптеров, шаги могут использовать результаты предыдущих и несколько сервисов вместе.

Будущий baseline охватывает третью группу/каталог/подключение, карточку сервиса, готовые сценарии, редактор своего, запуск/доступ/связи/синхронизацию, действия в рабочем контексте, подтверждение, настройку агента, журнал и восстановление. Пустые/ошибочные/недоступные состояния, несохранённые и конкурентные правки проектируются сразу.

Используются shared/form-controls.tsx, shared/ui-controls.tsx, shared/ui.tsx, SectionMenu, Pagination, общие ссылки и antd Dropdown/Modal. Новый переиспользуемый компонент создаётся при отсутствии подходящего. Layout, тексты и иконки утверждает владелец в baseline; архитектурный flowchart не является разрешением на произвольный UI.

## Порядок документации, дизайна и реализации

Личная приёмка baseline владельцем — обязательная зависимость последующих работ, а не автоматический результат отчёта агента.


SPEC-0037 и ADR-0038 уже приняты. Обновление документации по третьему архиву проходит единым согласующим пакетом C4; его pending-состояние не принимается за применение. Действующий самостоятельный HTTP/MCP-контур сохраняет прежние разрешения.

После принятия спецификации оформляется полный план: сначала baseline, затем общий механизм и продуктовый UI. Формат: design/baseline/service-integrations/*.dc.html, canvas x-dc, support.js, модели кадров при необходимости, существующие токены/темы/компоненты и все состояния.

Результат каждой дизайн-задачи — личная приёмка владельца. Принятие карточки задачи или отчёт исполнителя не заменяет приёмку макета. Реализация зависит от неё. Пакеты конкретных сервисов следуют за механизмом и обязательно содержат готовые сценарии.

Документ не создаёт и не перепланирует задачи; граф оформляется инструментами Skaro после принятия спецификации.

## Проверяемые свойства решения

- Новый адаптер, его операции, события и готовые сценарии подключаются без правок исполнителя и общих экранов. Нестандартные транспорт, авторизация, преобразование или контрол используют зарегистрированную точку расширения.
- Пользователь создаёт отсутствующий сценарий без доработки ядра; обычный путь не требует кода или графового редактора.
- Все публичные продуктовые действия Chatballs имеют проверяемое соответствие в реестре с сохранением прав и бизнес-правил.
- Один путь исполнения обслуживает сотрудника, ИИ, событие, расписание и внешний API; полномочия проверяются сервером.
- Дубликат события, повтор команды, перезапуск и конкурентный захват не создают второй локальный логический запуск/шаг.
- Сбой после внешнего эффекта проверяется отдельно; неизвестный результат остаётся неизвестным до доказанной сверки.
- Ожидания переживают перезапуск; подтверждённые шаги не повторяются; чужие/устаревшие callbacks и права не позволяют продолжить действие.
- Проверяются типы/файлы, OAuth/секреты, RLS, ветви/итерации/расписания и совместимость существующих правил/инструментов.
- Выполняются только относящиеся к изменениям тесты, backend с --reuse-db. UI проходит браузерную проверку по лично принятому baseline. Полный прогон — только по явному указанию владельца.

## Правила и ограничения для реализации

1. Сохранять модульный монолит, штатные контексты/RLS, очередь и доменные сервисы.
2. Не хардкодить названия сервисов и список бизнес-сценариев в ядре.
3. Не выдавать частичные/неизвестные результаты за успех.
4. Не включать сценарии и не расширять полномочия миграцией.
5. Не создавать собственную CRM как мастер-базу: внешние сущности обслуживаются операциями, связями и необходимыми операционными снимками.
6. UI — после личной приёмки baseline; подходящие компоненты переиспользуются, недостающие проектируются до продуктового кода.
7. Соблюдать DRY, KISS, SRP и NO GOD FILES; API, схемы, политика, исполнение, адаптеры и представления разделяются по ответственности.
8. SPEC-0008/0015/0023, ADR-0008/0032, бриф и архитектура согласованно уточняются в этом же пакете; старые права/настройки не расширяются автоматически.

## Контракт кода и формат сценария

Модули находятся внутри существующего приложения integrations и одного backend-образа. Это разделение файлов и обязанностей, а не новые обязательные службы. Новые Django-модели экспортируются через штатный models-модуль приложения и получают миграции/RLS; новая независимая Django-служба не вводится.

| Граница | Планируемый путь от apps/backend/chatballs/integrations/ | Ответственность |
|---|---|---|
| Реестр | adapters/ | contracts, registry, HTTP/MCP/legacy, защищённый транспорт |
| Подключение | service_connections/ | настройки, credentials, OAuth, безопасная проверка/API |
| Определение | scenarios/ | definition, validation, bindings, presets, synchronization/API |
| Политика и запуск | execution/permissions.py, approvals.py, launch.py, views.py | актуальные права, точное подтверждение, снимок/идемпотентный запуск |
| Исполнение | execution/runner.py, checkpoints.py, blocks.py, actions.py, recovery.py, ai_bridge.py | ограниченные порции, шаги/ожидания, внешние эффекты/сверка и текущий AI-runtime |
| События | automation_events/ | ingress, fanout, handlers, scheduler, polling |
| Действия Chatballs | action_catalog/ | registry/coverage и отдельные обёртки доменов |
| Данные | scenario_state/ | разделённые модели connections/grants/definitions/subscriptions/runs/steps/receipts/entity_links, journal/retention |

AdapterDescriptor описывает key, contract_version, settings_schema, auth_schema, operations, events, lookups и scenario_templates. OperationDescriptor содержит key, input/output_schema, effect, permission_scope, retry_strategy, таймаут/лимиты и объявленные execute/resume/reconcile/cancel. Пресет имеет стабильные key/version, назначение, параметры и definition; runtime получает снимок совместимых контрактов. Обновление пакета не переинтерпретирует активный запуск другой версией.

OperationContext формируется сервером: tenant/scope, principal/grants, connection, run/step/path, effect_key, deadline и causal-chain. Браузер/модель не назначают tenant, credentials или подтверждённую связь сущностей. Результат операции содержит state (completed/pending/failed/unknown), типизированные данные или ссылку на файл, external_reference, continuation/correlation и safe_error/retry_after. Pending означает сохранённое продолжение, а не занятый поток.

ScenarioDefinition содержит triggers, условия, параметры, steps и настройки доступа/обработки ошибок; блоки action, if, foreach, parallel, call, wait, try принадлежат одному интерпретатору. Каждый блок имеет устойчивый ID; составной путь дополняется идентификатором итерации/ветви, а не зависящей от конкурентного исполнения позицией. Значение задаётся константой или типизированной ссылкой на input/context/event/steps/item с зарегистрированными преобразованиями. Определение проверяется до эффекта, выход шага — перед следующей зависимой операцией. Сбой одной parallel-ветви не стирает результат другой; политика ошибки явно определяет остановку новых эффектов/обработку, join учитывает результаты всех запущенных ветвей.

Техническая ревизия обеспечивает optimistic concurrency редактора и snapshot запуска; отдельный релиз/публикация сценария не требуются. Бюджеты вложенности/итераций/параллелизма/времени/объёма защищают работу установки и завершаются объяснимо, без скрытого отбрасывания ветвей. Увеличение настраиваемых технических пределов не меняет бизнес-модель и не требует другого движка.

Общие схемные контролы покрывают обычные параметры. Нестандартный контрол регистрируется доверенным пакетом UI по стабильному ключу с доступным схемным представлением; существующие подходящие компоненты переиспользуются. Это возможность расширения, а не требование писать UI для каждого сценария.

## Уникальности, приём событий и жизненный цикл

ServiceConnectionSettings связан с существующим Integration один-к-одному. Scenario, ScenarioRun, StepExecution, EventReceipt, EntityLink и ActionGrant принадлежат организации. Проверяется принадлежность каждой ссылки. Run уникален по organization/scenario/trigger_key; step — по run/step_path, effect_key сохраняется до внешнего запроса. Редакция определения не делает старый trigger новым. Намеренный повтор получает отдельную аудируемую команду.

Webhook сохраняет EventReceipt и outbox атомарно; InboxEvent.hash не заменяет конверт. Fan-out создаёт отдельные задания/Run каждому подписчику; чекпойнт распределения не теряет оставшихся подписчиков после сбоя. Callback сопоставляется по проверенной серверной корреляции/подключению/организации; сохранённый ранний callback доступен после появления ожидания. Подписка и cursor опроса сохраняются с результатами обработки, чтобы падение не сдвигало курсор без durable события. Где источник не даёт sequence/version, нельзя выдумывать порядок: применяется контракт адаптера/сверка и настроенная политика конфликта.

Для расписания хранятся timezone организации, локальное правило, next_due и UTC-идентификатор срабатывания. Нужен явный параметр обработки пропуска: пропустить, одно догоняющее выполнение либо ограниченное догоняющее выполнение. Переход часов определяется явно: несуществующее локальное время пропускается, повторяющееся исполняется один раз с фиксированным выбором первого UTC-момента; это описывается в справке/настройке до запуска. Ключ срабатывания не зависит от момента пробуждения poller.

| Состояние шага | Допустимое продолжение |
|---|---|
| Готов | Проверка прав, затем claim; при требуемом подтверждении — ожидание решения |
| Ожидает подтверждения | Действительное подтверждение точных параметров → готов; отказ/истечение → отмена до эффекта |
| Выполняется | Подтверждённый успех → выполнен; подтверждённый отказ → ошибка; pending → ожидание сервиса; потеря доказательств → неизвестный результат |
| Ожидает время/событие | Проверенный callback/срок → готов; отмена останавливает ожидание |
| Ожидает сервис | Подтверждённый исход → выполнен/ошибка; невозможность установить → неизвестный результат |
| Ожидает безопасный повтор | После due_at → готов; исчерпание → ошибка; отмена прекращает новую попытку |
| Результат неизвестен / сверка | Доказанный результат фиксируется; доказанное отсутствие эффекта и безопасность допускают повтор; недостаток доказательств сохраняет неизвестность |
| Выполнен / ошибка / отменён до эффекта | Терминальный факт не перезаписывается фиктивным откатом; последующее действие/компенсация имеет собственный шаг |

Суммарный статус Run выводится из подтверждённых фактов шагов и сохраняет частичный результат. Команда отмены не означает, что отправленный сетевой запрос исчез: такой шаг остаётся на сверке до установления исхода. После удаления содержимого по retention повтор/продолжение не восстанавливают старые параметры из логов: требуется новое явное заполнение/запуск с текущими правами, а неизвестный внешний исход не объявляется отсутствующим.

## Совместимость решений

## Журнал после удаления данных

В 30-дневном безопасном журнале остаются названия/версии сценария и операций, инициатор, время, статусы, разрешённые ссылки и очищенная структура исполнения. Прямой вызов одной операции сотрудником или ИИ оформляется одношаговым запуском того же исполнителя: не требуется создавать отдельный пользовательский сценарий и не появляется второй механизм выполнения.

## T-176: собственные полномочия установки и полнота API — 05.11.2026

Планируемая детализация описана в docs/service-native-installation-runtime.md.
Один executable registry дополняется явной границей существующего инициатора:
tenant/personal/instance/platform/bootstrap. Это не новые роли; штатные
permissions, credential protocols, подтверждения и процедуры восстановления
сохраняются. Tenant editor/grants/snapshot/runner не получают глобальные
полномочия даже через администратора-делегата. API и разделённые обёртки
вызывают общие доменные службы без HTTP к себе и APIView dispatch.

whitelist доменных префиксов, учитывает surface/route/method/handler и
проверяемую классификацию технических входов. Профиль, создание организаций,
настройки установки, обновления и хранение остаются продуктовой функциональностью.
