## Что именно спроектировано

Навык — общая инструкция организации с названием, кратким условием применения и подробными правилами. Может не иметь шаблонов. Один навык подключается нескольким агентам, общая правка влияет на будущие ответы всех этих агентов. Отключение в карточке касается только одного агента.

Оформление сообщения — необязательная возможность шаблонов внутри навыка. В макете конкретный пример называется «Работа с заказами», а не «Оформление сообщений». Внутри — «Карточка заказа» и «Статус заказа». Это иллюстрация данных внешней системы, а не собственная модель заказов Chatballs.

## Сценарий «Работа с заказами»

Инструкция: искать заказ по сообщённому номеру, при отсутствии номера уточнять; для состава/суммы выбирать «Карточка заказа», для этапа/срока — «Статус заказа». Не угадывать сроки и не изменять/отменять заказ; запрос изменения передавать сотруднику.

| Шаблон | Поля |
|---|---|
| Карточка заказа | order_no: строка; items: список объектов с title: строка, qty/price/sum: числа; total: число; все обязательны |
| Статус заказа | order_no и status: обязательные строки; eta: необязательная строка |

Синтаксис в макете: `{{ поле }}`, `{{#each список}}…{{/each}}`, `{{#if поле}}…{{/if}}`. Внутри each поля относятся к элементу списка. Ни бизнес-вычислений, ни вызовов кода этот синтаксис не предоставляет.

Данные заказа 4512: две позиции, 1 × 18 400 и 2 × 900, итог 20 200. Длинный пример — семь позиций. По решению владельца готовый навык поставляется как доступная для явной установки основа новой конфигурации. Указанные данные служат примерами редактора; они не становятся seed-данными или ответами рабочего backend. Рабочие значения агент получает только от разрешённых инструментов.

В примерах других навыков есть «подтверждает выбранный слот» и «перед изменением доставки». Это не разрешает изменять внешние данные: ADR-0032/0036 оставляют инструменты только читающими. Полноценная запись в календарь и изменение доставки вне объёма.

Макет форматирует суммы собственным `ru-RU` и демонстрирует статический код карточки. В продукте системные подписи используют i18n, числа — существующий fmt; пользовательский текст шаблона не переводится автоматически. Нельзя копировать демо-функцию форматирования или зашивать карточку заказа вместо универсального рендера.

## Пробелы исходного дизайна и их закрытие

1. Нет самостоятельных кадров нового навыка/шаблона и их первоначальной валидации. Существующий редактор показывает заполненные данные.
2. Кнопка «Поле» показана, но форма добавления/редактирования/удаления входного поля, вложенного объекта и элементов списка не показана.
3. CSS-вкладка названа, но активного кадра с CSS и его ошибками нет. Исходники полного HTML/CSS и текстовой версии карточки заказа как пользовательского шаблона не приложены: показан фрагмент и вручную нарисованный результат.
4. Не определены ошибки загрузки, объект не найден, конкурентное изменение, ошибки подключения/отключения и удаления, пустой поиск.
5. Не показан раскрытый результат действия «Текстовая версия» и оформленный ответ внутри существующей панели «Проверить агента».
6. Не показана несовместимость модели с навыками: ADR требует явной проверки поддержки вызовов инструментов.
7. В T4 есть сохранение шаблона, в K5 — общая панель сохранения навыка; граница сохранения и поведение при несохранённом родительском навыке требуют явного контракта.
8. Общая карточка агента в A1–A3 сокращена: в коде уже есть знания, помощь сотрудникам, подключения и инструменты. Эти блоки нельзя молча убрать ради воспроизведения сокращённого кадра.
9. Точные размеры и поведение административного редактора при 1024 px не показаны; мобильная версия административных разделов не требуется по SPEC-0015.

Владелец разрешил закрыть перечисленные пробелы существующими компонентами. Каждому из них соответствует конкретное решение в docs/agent-skills-ui-agreement.md: создание, схема полей, CSS, ошибки, сохранение, совместимость, просмотр текста и сохранение остальных блоков агента. Это закрывает известные пробелы для планирования. Новые неописанные состояния по-прежнему требуют решения в проектном чате; задач на подготовку спецификаций или дизайн-решений не создаётся.

Причины разделения: инструкционный навык полезен без оформления; библиотека предоставляет самостоятельный административный API; обработчик шаблонов требует отдельной проверки безопасности и может выполняться параллельно с runtime; доставка снимка является целостным жизненным циклом сообщения. UI управления и редактор кода — разные законченные сценарии; показ сообщений вынесен для общей проверки клиента и сотрудника и последовательно использует renderer из редактора, не создавая второй стандарт. ## Проверка реализации

Только относящиеся к изменениям тесты: tenant/RLS и права; модель без tool calling; загрузка только подключённых навыков; один снимок конфигурации на ход; общий срок и раунды; неизвестные/искажённые псевдонимы; HTML/CSS и ссылки; несовпадение схемы; длинные списки; неизменность истории после изменения/удаления; перехват человеком и повтор доставки; отсутствие исходных данных в диагностике; сохранение существующей входящей почты.

Для UI обязательна проверка в браузере на штатном backend с существующими учётными данными и установленным набором; seed/сброс аккаунтов/подмена API запрещены. Темы, ширины 300/340/360 и длинные названия сверяются с кадрами. Сборка — для изменений кода по правилам владельца; полного прогона тестов текущий запрос не разрешает. Изменённые компоненты проверяются на разделение ответственностей и NO GOD FILES.
