# Каталог действий установки и полнота API — T-176

## Статус и основание

Планируемая детализация принятой SPEC-0037/ADR-0038. Это контракт реализации,
не отчёт о готовности. Оба baseline лично приняты владельцем 22.10.2026,
как явно записано в R-28. Новая приёмка тех же макетов не требуется.
Новые экраны и изменение дизайна этим пакетом не предлагаются.

Исходный checkout T-176: 314252be. T-175 поставил 275 действий и 316 записей
своего inventory; coverage.py ограничивает resolver выбранными ROOTS/API_MODULES.
Auth boundary отдельно оставляет восемь глобальных продуктовых входов профиля.
Read-only resolver-проверка 05.11.2026 обнаружила 349 HTTP method/handler входов
app и 4 platform; health function views отдельно требуют точного method-contract.
Вне прежней описи — 47 app и 4 platform записи, включая технические протоколы.
Это результаты инвентаризации, не заявление об их реализации.
Полнота всего API этим срезом не доказана. Источники: action_catalog/coverage.py,
auth_boundary_inventory.json, urls_app.py, urls_platform.py и
docs/verification/T-175/main-merge.md.

## Один каталог, собственные полномочия

Полный executable registry сохраняет стабильные ключи, версию, TypeSpec входов
и выходов, effect, execution/retry и точные ссылки на исходные API. Descriptor
дополнительно отличает существующую область инициатора: tenant, personal,
instance, platform или bootstrap. Это граница исполнения, а не новая роль.

- Tenant: прежний TenantContext, grants, scope, делегат и runner.
- Personal: текущий активный HumanUser; цель всегда сам пользователь.
  Для списка и отзыва остальных сессий требуется его настоящая текущая сессия.
  TenantContext или ID пользователя из аргументов не заменяют её.
- Instance: штатные is_instance_admin и can_view_instance_settings. Сохранить
  различие чтения общих настроек менеджером организации и изменения только
  администратором установки; tools-network читает только администратор установки.
- Platform: действующие PlatformOperator и PlatformToken с исходной capability.
  Provisioning остаётся на backend-platform, со штатным Idempotency-Key,
  tenant-транзакцией и результатом существующей provisioning service.
- Bootstrap: только штатный открытый мастер до первой организации, с прежней
  проверкой закрытия и ограничением БД. Создание установки остаётся продуктовой
  операцией. Выдача сессии и credential challenge остаются исходным протоколом.

Серверный контекст получается на существующем защищённом входе. Его нельзя
создать из аргументов сценария, JSON, service connection или grant. Tenant-
каталог редактора, выдача разрешений, подготовка snapshot и runtime допускают
только tenant authority; сервер повторяет проверку перед эффектом, включая
старые snapshots, nested run, автоматический и ИИ-запуск. Даже личный глобальный
статус делегата не повышает authority tenant-сценария.

Полный каталог не означает новый универсальный административный endpoint,
новый сценарный движок или новые полномочия ИИ. Глобальные обёртки доступны
существующим уполномоченным инициаторам через их штатные входы и общий контракт.
API и descriptor вызывают один application service; логика, находящаяся
сегодня в APIView, выносится в разделённые доменные модули. Не допускаются
HTTP к себе, APIView dispatch, fake Request, произвольные ORM/SQL-команды
или дублирование проверок в отдельной модели ролей.

## Обязательные группы

Instance/settings: адрес, язык установки, SMTP, TURN, проверка почты и
tools-network. Сохраняются прежние validators, право чтения/изменения, смысл
пустого секрета «оставить прежний» и аудируемое включение локальной сети.

Storage: состояние, настройки, проверка S3, запрос переноса. Проверка S3
действительно пишет и удаляет проверочный объект; она не объявляется read-only.
Сохраняются проверки конфигурации, instance-аудит, outbox и штатный worker
миграции. Одновременные команды не должны создавать повторную миграцию.
Пароли, S3 credentials и необработанные ошибки провайдера не становятся
обычным результатом каталога.

Updates: состояние, проверка канала и явная установка. Сохраняются
sync_install_status, check_for_updates, request_install, heartbeat,
ограничения допустимой версии/состояния и штатный файловый обмен с updater.
Транспортный сбой не разрешает слепо повторять установку.

Platform и создание организации: исходные can_create_organization,
provision_organization и complete_setup, их валидация, транзакции и аудит.
Обёртка не bootstrap-ит закрытую установку и не предоставляет platform DB role
процессу приложения или tenant worker.

Чтение предустановленного demo-media также получает точное покрытие: собственное
действие чтения штатного ресурса, без запуска seed и без выдачи credentials.

Personal: изменение профиля, языка и оформления, чтение/загрузка/удаление
аватара, просмотр сессий и отзыв остальных сессий. Это продуктовые действия,
а не исключения auth. Credential операции пароля/TOTP/login/invitation
сохраняют собственную точную протокольную классификацию и проверки.
Каталог не создаёт обхода подтверждений и не возвращает credentials в журнал.

Модули action_catalog/instance.py, platform.py, updates.py, storage.py,
profile.py, setup.py разделены по доменам; settings.py сохраняет
организационные настройки. Общие конструкции находятся в contracts.py,
registry.py и authority.py. Изменённые крупные API-модули разделяются по
ответственности; новые/увеличенные файлы удерживаются в правилах AGENTS.md.

## Полный inventory

Coverage проходит все публичные маршруты urls_app и urls_platform, включая
унаследованные HTTP methods, и реальные WebSocket lifecycle/frame handlers.
Ключ записи включает поверхность, route, method и handler, чтобы одинаковый
путь на разных host не смешивал полномочия. Нет whitelist доменных префиксов,
скрывающего новую группу API. Каждая запись указывает executable action либо
конкретную техническую классификацию с проверяемой причиной и code evidence.

Auth/health/schema/gateway/transport/callback endpoints классифицируются
по действительной ответственности. Самостоятельная бизнес-операция не
становится технической только из-за пути auth или сложной авторизации.
Служебный Django admin имеет явно указанную границу относительно публичного
продуктового API; это не способ исключить app/platform операции.
Проверяются незарегистрированные/устаревшие/дублирующиеся записи, несовпадение
handler, action references и authority. Нулевое число проблем требуется
по фактическому множеству, а не по фиксированному количеству действий.
До получения этого результата coverage не объявляется полным.

## Эффекты, секреты и восстановление

Локальные доменные изменения сохраняют прежние транзакции и аудит.
Tenant receipt/checkpoint остаются в общем runner; глобальные операции
не получают фиктивную организацию или tenant Run. Их подтверждение и
восстановление используют собственную штатную административную процедуру:
provisioning idempotency record, update state/exchange, storage migration
state/outbox и фактическую сессию пользователя.

I/O и неоднозначный исход описываются честно; общий каталог не обещает
exactly-once и не повторяет запись без доменной стратегии восстановления.
Секретные входы не попадают в обычные результаты/логи. Проверки permissions
и redaction обязательны также при прямом вызове executable wrapper.
Наличие зарегистрированного действия не разрешает реальное изменение
production, аккаунтов, хранилища или установки ради теста.

## Проверка всей функции

После реализации: штатная сборка, только адресные тесты с --reuse-db,
browser-проверка в окружении Skaro с readiness БД/Redis и frontend proxy
на backend задачи. Не запускать полный прогон, seed, временные серверы
или fake backend. Контрактный unit-тест не выдаётся за реальный внешний доступ.

Итоговый журнал связывает R-1–R-31 с проверенными результатами прежних задач
и адресными проверками взаимодействия: permissions/RLS, секреты/OAuth/файлы,
дубли/гонки, падение между эффектом и фиксацией, ветви/ожидания/ранний callback,
отмена/unknown, синхронизация, 7/30 retention, прежние инструменты/правила.
Отдельно требуется путь подключение → готовый/свой сценарий → сотрудник/ИИ/
автоматический запуск → внутренние/внешние шаги → журнал/восстановление,
а также независимый адаптер и новый сценарий без изменения ядра/общих экранов.

Ранее принятые ограничения T-172/T-173 не являются доказательством выполненной
агентом внешней проверки. Недоступный реальный сервис или незакрытая проверка
остаются blocker соответствующего критерия. Общий механизм не объявляет
готовыми CRM/Mindbox или неподтверждённые операции конкретного адаптера.
Справка RU/EN и примеры описывают фактическую реализацию после проверки.

## Покрытие архитектуры

Все уровни применимы и сохраняются: context (сотрудник, администратор установки,
оператор платформы), containers (прежний backend и поверхности gateway),
components (native/policy/identity/platform/storage/updates), code
(registry/authority/wrappers/coverage), deployment (прежние роли процессов,
PostgreSQL, worker/worker-events, outbox, volumes и updater), ordered dynamics
установки, provisioning, хранения и обновлений. Новых обязательных служб нет.
Существующие динамики tenant runner, ИИ, автоматизации и восстановления
сохраняются. Исключённых уровней нет.

ADR-0038 управляет общим каталогом и восстановлением; ADR-0024 — правами
установки, ADR-0026 — ролями процессов, ADR-0013 — поверхностями,
ADR-0027 — обновлением. Стабильные ID и все R-1–R-33 сохраняются в единой
модели Skaro; Markdown содержит только авторский текст. Planned не переводится
в current этим предложением. Итоговый review нужен для точного changeHash
после кода/документации и до submit_result.
