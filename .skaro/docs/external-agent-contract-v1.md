# Контракт внешнего автономного агента: полный функциональный объём

Предложение от 10.11.2026 к SPEC-0041/ADR-0041. Ни один метод пока не заявляется реализованным. Объём единый, без MVP. Версия 1 означает совместимость HTTP-схемы. Числа ниже — предлагаемые эксплуатационные настройки. Источник требований — PDF от 09.11.2026 и решения владельца: новый контракт, согласованные исходные данные доверенному сервису, инициатива только в открытых диалогах под ИИ.

## 1. Граница и формат

Chatballs владеет перепиской, tenant-доступом, согласием, управлением и доставкой. Сервис владеет своим агентом, LLM, инструментами и памятью. Готовый текст не проходит другую LLM. Сервис не получает токены каналов, пользовательскую сессию, общие API-права или БД.

HTTPS; UTF-8; Content-Type: application/json; JSON-тело не более 256 KiB (binary uploads отдельно по штатному лимиту); version: "1"; даты RFC 3339 в UTC; requestId/resultId/deliveryId/authorizationId — UUID; остальные ID — непрозрачные строки, не основания доступа. Поддержаны text, image/file, входящий contact, исходящий contact_request в доступных каналах, formatted через явно разрешённый шаблон и упорядоченные составные ответы. Каждый элемент проходит реальные ограничения канала/общего контракта; текст не обрезается/делится скрытно. Исходный voice Chatballs расшифровывает и передаёт как text+wasVoice:true. Сервис не получает/генерирует аудио. Нельзя отправлять произвольный JS/srcDoc или создавать новые UI-формы; оформленные сообщения использует общий безопасный renderer. Штатное TTS сохранённого текста Chatballs сохраняется независимо.

Машиночитаемый артефакт реализации: packages/contracts/external-agent-v1.openapi.yaml с request/response schemas и примерами. Документ задаёт его предметную структуру; генерация файла и серверов не выполняется этим предложением.

## 2. Доступ и привязка

Два независимых Bearer credential:
- Chatballs → сервис: credential заказчика в encrypted ServiceConnectionSettings.
- Сервис → Chatballs: отдельный credential подключения, созданный Chatballs при явной настройке; выдаётся один раз, в БД хранится проверочный hash. Это не изменение существующих аккаунтов.

Credential разрешает только конкретное подключение. При запросе Chatballs сначала определяет организацию по проверенному credential, затем устанавливает tenant context/RLS и проверяет agent/session/authorization. organizationId из тела не используется; в v1 его нет. Ответы на чужие ID — 404 без раскрытия существования. Ни URL, ни externalSessionId не дают полномочий сами по себе.

ExternalAgentSession имеет стабильный conversationId протокола, ссылку на свой Conversation, agentId, connectionId, externalAgentId, optional externalSessionId и актуальное authorizationId. Последнее связывает версии режима организации, управления диалогом, агента, подключения и монотонную ревизию внешней настройки. Перехват/закрытие/архив/смена/отзыв аннулируют его. Явный возврат сотрудником и следующий допустимый dispatch выдают новое authorizationId, сохраняя прежнюю сессию только для той же привязки. Старые результаты не оживают. Изменение режима туда-обратно повышает ревизию.

Разрешения: result.submit, message.send, handoff.request, delivery.read, history.read, file.read, file.upload, template.read; каждое ограничено своим подключением/агентом/диалогом, типами и отдельными allowlist. message.send дополнительно требует включённой инициативы агента. Новая внешняя привязка не получает native actions, tools или grants встроенного агента. Секреты отсутствуют в JSON, URL, истории, outbox и журнале. HTTP не следует произвольным URL от сервиса; все пути составляются из сохранённого проверенного baseUrl. Callback URL строит Chatballs из штатного публичного адреса, не из входного Host/JSON.

## 3. Методы сервиса заказчика

| Метод | Путь относительно его baseUrl | Назначение |
|---|---|---|
| GET | /chatballs-agent/v1/capabilities | Read-only проверка версии и обязательных возможностей |
| POST | /chatballs-agent/v1/requests | Устойчивая регистрация запроса; 200 terminal либо 202 accepted |
| GET | /chatballs-agent/v1/requests/{requestId} | Текущее состояние исходного запроса без повторного запуска |
| POST | /chatballs-agent/v1/requests/{requestId}/cancel | Идемпотентное best-effort прекращение будущей работы |

Capabilities содержит versions: ["1"], contentTypes: ["text", "image", "file", "contact", "contact_request", "formatted"], durableIdempotency: true, statusLookup: true, callbacks: true, cancel: true, dedupRetentionSeconds >= 2592000. cancel означает способность принять уведомление, а не гарантировать откат. Отсутствие обязательной возможности не позволяет включить внешнее исполнение. Health/capabilities не запускает агента.

POST requests получает Idempotency-Key: requestId. Request body:

```json
{
  "version": "1",
  "requestId": "<uuid>",
  "createdAt": "<UTC>",
  "deadlineAt": "<UTC>",
  "agent": { "id": "<agentId>", "externalAgentId": "<customer-agent-id>" },
  "conversation": {
    "id": "<conversationId>",
    "externalSessionId": null,
    "authorizationId": "<uuid>",
    "turnSequence": 1
  },
  "trigger": {
    "messageId": "<messageId>",
    "createdAt": "<UTC>",
    "type": "text",
    "text": "<исходный текст или стенограмма>",
    "wasVoice": false,
    "attachments": []
  },
  "context": {
    "history": {
      "mode": "window",
      "snapshotCursor": "<opaque>",
      "truncated": false,
      "messages": [],
      "historyUrl": "<scoped history endpoint>",
      "nextCursor": null
    },
    "customer": {
      "id": "<opaque>",
      "fields": {},
      "customFields": {
        "mode": "replace",
        "snapshotId": "<uuid>",
        "capturedAt": "2026-11-10T12:00:00Z",
        "scope": [],
        "items": []
      }
    },
    "dataPolicy": { "revision": 1, "mode": "agreed_original", "fields": [], "customFields": [] },
    "language": { "mode": "mirror", "organization": "ru", "requested": null }
  },
  "permissions": { "reply": true, "handoff": true, "proactive": false },
  "deliveryConstraints": { "types": ["text", "file", "image", "formatted"], "maxFileBytes": 20971520 },
  "callbacks": { "resultUrl": "<server-generated HTTPS URL>" }
}
```

history.messages: [{id, author: customer|employee|agent, createdAt, content, wasVoice}]. Краткое inline-окно по умолчанию содержит последние 20 сообщений, настройка 0–200; остальная согласованная публичная история доступна через historyUrl и cursor. Отбираются публичные сообщения предыдущих обработанных входящих и сохранённых ответов всех форматов, ограниченные текущим снимком. Текущее сообщение передаётся только trigger; ожидающие последующие сообщения исключаются. Если ответ предыдущего хода сохранён после прихода текущего trigger, он всё равно включается: порядок определяется ходами, а не простым timestamp cutoff. Внутренние комментарии, назначения, причины передач и технические события не передаются.

Снимок замораживается при первом dispatch головы очереди; повтор — те же данные и digest. snapshotCursor обозначает границу, не разрешает произвольное чтение истории. truncated означает неполное окно, а не пропажу данных. Сервис не считает присланное окно полной историей и не дописывает его повторно в память только из-за retry: использует стабильные ID. Полная доступная история того же диалога читается постранично с тем же snapshot/authorization; можно восстановить память с нуля и продолжить после сотрудника. Курсор связан с tenant/диалогом/политикой/версией управления и границей очереди; будущие входящие не просачиваются через pagination. Отзыв закрывает и продолжение чтения; удалённое сообщение не восстанавливается из устаревшего snapshot. Разрешённая память сервиса может быть шире окна, но источник переписки — Chatballs.

customer.fields — только явно разрешённые стандартные поля контакта; кастомные поля WEB-источников передаются отдельно в customer.customFields полным типизированным replace-снимком. dataPolicy.customFields содержит разрешённые пары sourceConnectionId/fieldId, исходно пустые; dataPolicy.fields относится к стандартным полям. Текст и выбранные поля идут в исходном виде; сервис отвечает за свой экспорт в LLM. Не включаются credentials, внутренние заметки и системные настройки. Переданные сайтом сведения недоверенные, их нельзя считать подтверждённой идентификацией. dataPolicy.revision фиксирует выбранную администратором политику; смена политики отзывает старое разрешение. Наличие ПДн в свободном тексте не обещает NER/полного выявления; это согласованная исходная передача.

language.mode: mirror|organization|fixed; requested задан только для fixed. Это указание сервису, не повод Chatballs перегенерировать готовый ответ. Встроенные инструкции/skills/knowledge/tools не передаются автоматически. Разрешённые шаблоны выдаются отдельным каталогом схем. Binary и длинная история передаются через scoped file/history API, а не обрезаются в JSON. При настоящем нарушении ограничения/ошибке STT запрос не подменяется пустым текстом: штатная передача сотруднику.

Ответ 202:
```json
{
  "version": "1",
  "requestId": "<uuid>",
  "status": "accepted",
  "externalSessionId": "<opaque-or-null>"
}
```

202 означает durable registration до любого side effect. Результат приходит callback либо GET status. Повтор с тем же requestId не создаёт нового задания; другой semantic digest — 409 idempotency_conflict. Входящие авторизационные заголовки/сетевые попытки не часть semantic digest. Сервис может впоследствии выдать externalSessionId, если не выдал сразу; присвоенное значение внутри привязки неизменно.

Синхронный 200 и callback используют одинаковый TerminalResult:
```json
{
  "version": "1",
  "requestId": "<uuid>",
  "resultId": "<uuid>",
  "status": "completed",
  "externalSessionId": "<opaque-or-null>",
  "outcome": { "type": "reply", "messages": [{ "itemId": "<uuid>", "content": { "type": "text", "text": "<готовый текст>" } }] }
}
```

outcome — строго один вариант: reply {messages:[{itemId,content}]} либо handoff {reasonCode, summary}. Reply — полностью проверенный упорядоченный набор поддержанных сообщений. Handoff summary адресован сотруднику, не клиенту. Нельзя совместить text с исполняемыми действиями, выбрать другого получателя или прислать произвольный control token. Внешний текст не обрабатывается как HANDOFF_TOKEN встроенной LLM.

Terminal failure: version, requestId, resultId, status: failed, error: {code, retryable:false}. Ошибка агента завершает запрос, не запускает заново его side effects; автоматические повторы предназначены для транспорта, а не повторного рассуждения/действий. Неопределённый внешний исход отображается status: unknown с безопасным code, сверяется до deadline без нового requestId.

GET status возвращает accepted|processing без результата либо тот же terminal результат, cancelled или unknown. Принятый terminal результат не меняется. POST cancel: {version, requestId, reason: control_revoked|expired|configuration_changed}; ответ cancelled либо completed/unknown с фактическим состоянием. Успешный HTTP cancel не обещает отменить уже выполненное действие.

## 4. Методы Chatballs

Общий префикс /api/v1/external-agent/connections/{connectionId}. Все методы требуют отдельный Bearer credential этого подключения.

| Метод | Суффикс | Назначение |
|---|---|---|
| POST | /requests/{requestId}/result/ | TerminalResult исходного запроса |
| POST | /conversations/{conversationId}/messages/ | Инициативная отправка |
| POST | /conversations/{conversationId}/handoff/ | Инициативный запрос сотрудника |
| GET | /deliveries/{deliveryId}/ | Квитанция набора и каждого элемента |
| GET | /conversations/{conversationId}/history/ | Постраничная публичная история своего snapshot |
| GET | /conversations/{conversationId}/reply-templates/ | Схемы/версии разрешённых оформленных шаблонов |
| POST | /conversations/{conversationId}/files/ | Потоковая загрузка файла ответа |
| GET | /conversations/{conversationId}/files/{fileId}/ | Защищённое потоковое чтение разрешённого файла |

При результате requestId в URL/body совпадает. Agent/conversation/организацию/транспорт Chatballs берёт из замороженного request, не принимает как смену адресата. Запись request предшествует HTTP dispatch, поэтому ранний callback допустим. Синхронный ответ после callback обрабатывается как повтор.

Пример инициативы:
```json
{
  "version": "1",
  "deliveryId": "<uuid>",
  "agentId": "<agentId>",
  "authorizationId": "<uuid>",
  "externalSessionId": "<opaque-or-null>",
  "messages": [{ "itemId": "<uuid>", "content": { "type": "text", "text": "<готовый текст>" } }]
}
```

Header Idempotency-Key совпадает с deliveryId. Разрешена только текущая привязка: открытый диалог под агентом, без сотрудника и без активной/ожидающей клиентской очереди, с proactive=true и соблюдением ограничений канала. Иначе 409 conversation_busy/control_changed/channel_restricted либо 403 proactive_disabled. Новые/закрытые диалоги не создаются и не открываются. Предварительный отказ не создаёт Message; тот же непринятый запрос можно повторить позже, если полномочие осталось актуальным. После durable acceptance повтор возвращает прежнюю квитанцию.

Инициативный handoff: version, eventId UUID, agentId, authorizationId, externalSessionId, reasonCode, summary. Idempotency-Key=eventId. Тот же принцип одной квитанции и текущего полномочия; активная работа может быть прервана передачей. Нет groupId/employeeId/role и иных полномочий. Используются существующая очередь и группа диалога, уведомления и локализованные доменные события.

TerminalResult reply создаёт одну квитанцию набора и по одной Message/delivery на itemId. Инициатива использует ту же batch delivery-службу; повтор набора или элемента не добавляет сообщений. Тело accepted receipt:
```json
{
  "version": "1",
  "requestId": "<uuid-or-null>",
  "receiptId": "<uuid>",
  "state": "queued",
  "deliveryId": "<uuid>",
  "items": [{ "itemId": "<uuid>", "messageId": "<messageId>", "state": "queued" }]
}
```

Для результата requestId задан; для инициативы null. Для handoff state: handed_off, deliveryId:null, items:[]; фиктивного клиентского сообщения нет. Повтор получает ту же receiptId и текущий фактический state. HTTP 202 при новой queued отправке; 200 для идемпотентного повтора/handed_off/suppressed. ACK только после commit receipt/state/outbox; 202 не означает доставку. Callback позднего/отменённого request получает state:suppressed, reasonCode и без Message. Противоречащий уже принятому terminal результат получает 409 result_conflict; не переводится обратно в processing.

GET delivery возвращает deliveryId, state, reasonCode, updatedAt и items:[{itemId,messageId,state,reasonCode}]. Набор может иметь state:partial при смешанном исходе; состояние каждого элемента первично. State:
- queued — сохранён и ожидает проверяемую отправку;
- transport_accepted — внешний канал подтвердил приём либо WEB-сообщение опубликовано клиентской истории;
- failed — достоверно не принято и повтор не назначен;
- unknown — запрос мог быть принят каналом, подтверждение потеряно;
- suppressed — актуальное полномочие/срок утрачены до отправки.

transport_accepted не обещает прочтение/фактическое отображение внешним мессенджером. unknown не повторяется автоматически без поддержанной идемпотентности/сверки канала. Один (deliveryId,itemId) — одно Message; delivery не использует one-to-one ai_reply_to как единственный ключ, поскольку у инициативы нет входящего, а составной ответ содержит несколько элементов. Каждый элемент проверяет текущее управление. При unknown порядок не перескакивает молча к следующим элементам; остаток ждёт поддержанной сверки/штатного решения, без повторного запуска агента. Ошибки доставки не перезапускают агента.

## 5. Ошибки

Общий error envelope: {version:"1", error:{code, retryable, traceId}}. Сырой ответ чужого API, stack trace, credential и ПДн в envelope не возвращаются. Сервис получает стабильный код; UI переводит его в понятную фразу.

400 invalid_request; 401 invalid_credentials; 403 permission_denied/proactive_disabled; 404 resource_not_found; 409 idempotency_conflict/result_conflict/control_changed/conversation_busy/channel_restricted; 413 payload_too_large; 422 unsupported_content; 429 rate_limited; 503 temporarily_unavailable. Для 429/503 Retry-After ограничивается локальным deadline. HTTP-ошибку до регистрации не следует путать с terminal failure уже принятого агента. Аутентификация и tenant-допуск проверяются прежде dedup lookup; отзыв не обходится повтором прежнего ID.

## 6. Время, повторы, порядок и гонки

Предлагаемые defaults: HTTP 10 секунд; срок обычного ответа по умолчанию 120 секунд от приёма сообщения, включая STT/FIFO. Администратор явно задаёт также долгую обработку и максимально допустимый срок (предлагаемый default 24 часа, не жёсткий предел). deadlineAt выбирается политикой до dispatch. До трёх повторов создания с тем же ID и замороженным body после 1/5/15 секунд только до срока. Обязательная durable idempotency сервиса делает такой повтор допустимым. После 202 — callback и read-only status через 5/15/30 секунд, далее каждые 30 секунд до срока. Полученный processing не продлевает deadline. При неустановленном исходе статус unknown; нет нового requestId и повторного запуска бизнеса под видом восстановления.

Сервис сохраняет idempotency ledger минимум 30 дней, включая side effects. До подтверждения 202 atomic registration обязателен; потеря своей ledger не даёт права выполнить известный requestId заново. Действия внешнего агента должны иметь собственные effect keys/сверку либо unknown. Chatballs сохраняет контрольные ID/digest на весь срок существования подключения и не переотправляет истёкшие запросы.

Внутри диалога один активный внешний request. HTTP 202 не освобождает очередь для следующего хода; освобождается только worker/job. Сохранённый terminal checkpoint разрешает следующий request. Ошибка/истечение переводят диалог сотруднику и подавляют последующие queued-запросы. Нет debounce/объединения сообщений в v1. Снимок следующего запроса собирается после фиксации предыдущего результата с исключением ещё не обработанных сообщений.

Перехват/смена режима/приём результата/инициатива/закрытие согласованы общими блокировками в установленном порядке organization → conversation → request/receipt. Lease/fencing не допускают применения позднего worker. Проверка перед сетевой отправкой должна сохранять существующую гарантию: после завершения перехвата нельзя начать новую отправку старого ответа. Уже начатая и принятая каналом отправка не отзывается.

Срок/отзыв подавляют локальную отправку независимо от cancel сервиса. Поздний callback может быть квитирован без применения. Отдельная LLM Chatballs для сверки/пересказа/возобновления не вызывается. Внешние вызовы сервиса не держат DB-транзакцию; короткая критическая секция фактической передачи транспорту сохраняет штатную гарантию управления.

## 7. Хранение и эксплуатация

Целевые модели: ExternalAgentConfig, ExternalAgentAccessKey, ExternalAgentSession, ExternalAgentRequest, ExternalAgentReceipt и ExternalAgentDelivery. Ссылки проверяют organization и RLS/tenant constraints. В request — зашифрованный immutable snapshot, deadline, очередь, версии, claim/fencing, remote state и код исхода. В receipt/delivery — ID и соответствие digest/Message, полномочие и фактическая доставка. Outbox содержит только ID.

Payload для восстановления — 7 дней после terminal, метаданные — 30 дней по действующей политике. Активные ожидания не чистятся. Минимальные ID/keyed digest tombstones живут до удаления подключения без raw текста и credential; очистка payload не разрешает дубль. Переписка хранится по прежним правилам. Удаление диалога отзывает authorization, прекращает jobs и удаляет его операционный payload. Удаление в памяти заказчика и сроки его хранения — явная обязанность интеграционного соглашения; Chatballs не объявляет внешние копии удалёнными.

Настройка/отключение/ротация требуют прав существующей организации и аудита. Read API не возвращает секреты. Политика исходящих запросов берётся из существующего защищённого транспорта, включая DNS/IP/redirect, запрет сервисов установки и управляемый допуск частных сетей. Диагностика — только коды/ID/сроки/исходы. Нового обязательного контейнера, брокера или базы нет.

## 8. Приёмка и дизайн

Реальный сервис заказчика, штатное приложение и каналы: sync, async, callback до 202, повтор после потери HTTP, противоречащий дубль, FIFO и history snapshot, восстановление после рестарта, истечение/unknown, инициатива/busy, передача/перехват/возврат, отзыв и ротация, запрет чужих организаций/диалогов, channel unknown без дублирования. Автоматические тесты — только затронутые сценарии; не заменяют внешний end-to-end. Нельзя запускать mock API, seed или менять аккаунты ради демонстрации.

UI не спроектирован визуально этим документом. До реализации требуется отдельный лично принятый baseline карточки, интеграции, данных/согласия, проверочного чата и диагностики. Проверочный чат не вызывает сервис втихую: capabilities — без side effects; настоящий запрос может запускать действия заказчика и требует явного продуктового режима, принятого в baseline. Отсутствие endpoint/credential реального сервиса блокирует интеграционную приёмку, а не подменяется заглушкой.


## 9. Полный контракт содержимого, файлов, истории и STT

Content — discriminated union. Неизвестный type отклоняется, не превращается в text.

| Тип | Направление | Поля и обработка |
|---|---|---|
| text | Оба | text; wasVoice:true только после реального STT; source:{kind:voice,durationSeconds} без audio URL |
| file / image | Оба | fileId, filename, mimeType, size, sha256, caption; binary только через scoped API |
| contact | В сервис | Исходный сохранённый текст и фактически доступные разрешённые поля; нет выдуманной структуры или подтверждения личности |
| contact_request | Из сервиса | Штатный запрос контакта, только где transport capabilities его поддерживают; без произвольной формы |
| formatted | Из сервиса | templateId, templateRevision, data; общий schema→render→sanitize→immutable snapshot; история содержит text и разрешённые метаданные снимка |

Нативный voice в messenger сохраняется в Chatballs, штатный prepare/run/store STT выполняется перед dispatch и внутри общей очереди/срока с проверкой управления. Результат — исходный messageId, transcript, wasVoice:true, durationSeconds. Повтор dispatch не запускает STT заново при готовой сохранённой стенограмме; восстановление STT не теряет порядок. STT credential выбирается явно у внешнего агента и не требует провайдера LLM ответов. Ошибка STT — штатная операторская очередь. Диктовка WEB до отправки остаётся обычным текстом; если клиент не передал происхождение штатным контрактом, wasVoice не выдумывается.

Каждая сторона объявляет direction/type capabilities; Chatballs добавляет возможности текущего канала, лимиты файла, доступность contact_request и способ отображения formatted. Несовместимость не скрывается: точный 422/409 либо штатная передача сотруднику. WEB показывает разрешённый HTML snapshot общим iframe renderer, другие каналы — текст штатного шаблона; пользовательские интерактивные коммерческие кнопки/новые UI-компоненты этим не вводятся.

Files: POST multipart/form-data с uploadId UUID, authorizationId, file и sha256; Idempotency-Key=uploadId. Файл загружается потоково в tenant storage через текущие валидаторы/учёт хранилища, default max 20 MiB как в attachment_policy.py. После проверки возвращаются fileId, mimeType, size, filename, sha256 и expiresAt. Повтор тех же байтов/метаданных возвращает тот же fileId, конфликт — 409. Незавершённый upload нельзя сослать в результате. Успешный upload ещё не Message и не отправка; файл привязывается к текущей организации, агенту, диалогу и authorization. При принятии delivery ссылки фиксируются до очистки staging.

GET file требует текущий Bearer и authorizationId: выдаются только входящие файлы разрешённой публичной истории либо уже загруженные этим сервисом файлы той же связи. Никаких общих S3 URL, чужих ID, SSRF fetching или доступа к исходному voice даже под видом .bin. MIME/происхождение проверяются сервером; имя файла не определяет право. Ответ стримится с безопасным Content-Disposition и штатной политикой изображения/скачивания. Поддерживается повтор загрузки/скачивания; Range объявляется в capabilities и реализуется штатным storage helper при наличии. Истечение staging (предлагаемый default 24 часа) чистит только непривязанные файлы, не активные request/delivery; отмена/отзыв и удаление закрывают чтение. Опубликованные вложения живут по правилам переписки.

Templates: GET reply-templates возвращает только явно выбранные OWNER/ADMIN шаблоны этого агента: id, revision, purpose, typed data schema, поддержанные представления. Skill instructions, knowledge, HTML/CSS исходники и внутренние примеры автоматически не экспортируются. Ответ formatted обязан сослаться на разрешённые id/revision; изменение/отзыв до принятия — 409 template_revision_changed. Общий renderer проверяет данные и сохраняет snapshot один раз. Готовый snapshot не меняется вместе с шаблоном. Сервис не присылает srcDoc, скрипты или другой визуальный стандарт.

History: GET history принимает authorizationId, optional snapshotCursor и pageCursor, pageSize в технических пределах. Первый запрос открывает фиксированный согласованный snapshot, возвращает items, snapshotCursor, nextCursor, hasMore, dataPolicyRevision. Последующие страницы сохраняют границу: собственный диалог, публичная аудитория, обработанные ходы, исключение queued будущих входящих. message.id и itemId устойчивы; повторы безопасны для dedup памяти. Каждый pageCursor проверяет tenant, связь, snapshot, версии и срок; чужой/изменённый — 404/409. При отзыве авторизации чтение прекращается, при изменении политики нужен новый snapshot. Удалённые данные не воскрешаются ради resync. Обновления после snapshot доступны следующим снимком; контракт не объявляет полную двустороннюю репликацию.

Составной reply: messages:[{itemId,content}] в заявленном порядке. Проверка всех типов, ссылок, размеров, шаблонов и прав предшествует acceptance; частично невалидный batch не публикует первые элементы. У каждого принятого item собственные Message и transport receipt. После начала доставки возможен partial; обработанные элементы не повторяются, unknown не считается failed или успехом. Перехват подавляет остаток. Следующая клиентская доставка не обгоняет незавершённый batch; если доставка упёрлась в unknown, диалог переходит в штатное разрешение проблемы/сотруднику, а не запускает повторный бизнес-запрос. Объём batch ограничивается техническими лимитами JSON и текущими ограничениями канала, которые возвращаются в capabilities.

В приёмке обязательны все перечисленные форматы, STT→wasVoice без экспорта audio, файлы/очистка/отзыв, пагинация/resync, шаблоны и их ревизии, batch/partial/unknown. Нельзя принять сокращённый текстовый контур как завершённую реализацию.

## 10. Кастомные поля клиента

### Разделение стандартных и кастомных полей

`context.customer.fields` содержит только явно разрешённые стандартные поля карточки контакта. Кастомные поля CB передаются отдельно в `context.customer.customFields`, чтобы одинаковые ключи разных WEB-подключений не сталкивались. Это не содержимое сообщения типа `contact` и не API записи в карточку.

Существующая модель CB хранит значение по связке «организация — контакт — WEB-подключение — ключ». Схема и устойчивый `fieldId` принадлежат WEB-подключению. Внешний контракт использует составную идентичность **`(sourceConnectionId, fieldId)`**, а `key` сохраняет как машинное имя. `fieldId` — непрозрачная строка из действующей схемы, не обязательно UUID. Новый после удаления объект с прежним `key` не наследует разрешение старого поля.

`sourceConnectionId` обозначает WEB-источник данных, а `connectionId` в префиксе внешнего API — сервисное подключение GoCoStack. Это разные идентификаторы и разные роли.

### Политика экспорта

Список `context.dataPolicy.customFields` содержит разрешённые пары `{sourceConnectionId, fieldId}`; исходно он пуст. `context.dataPolicy.fields` остаётся списком разрешённых стандартных полей. Выбор выполняется явно в настройке внешнего агента; данные другого контакта/организации или неразрешённого источника не выбираются по совпадению ключа.

`aiAccess` относится к встроенной LLM и не является разрешением передачи GoCoStack. Передача в этот доверенный сервис отдельно разрешает согласованные исходные значения; секретные служебные данные не экспортируются. Поля сайта остаются недоверенными данными, не инструкциями и не подтверждением личности.

Пример политики для одного кастомного поля (часть `context.dataPolicy`):

```json
{
  "revision": 2,
  "mode": "agreed_original",
  "fields": [],
  "customFields": [
    { "sourceConnectionId": "<web-A>", "fieldId": "<field-A>" }
  ]
}
```

### Полный снимок CustomFieldsSnapshot

Каждый AgentRequest содержит объект, даже когда полей нет:

```json
{
  "mode": "replace",
  "snapshotId": "<uuid>",
  "capturedAt": "2026-11-10T12:00:00Z",
  "scope": [],
  "items": []
}
```

| Поле | Тип | Правило |
|---|---|---|
| `mode` | Строка `replace` | Полный снимок разрешённых кастомных полей; не частичный patch |
| `snapshotId` | UUID | Идентификатор снимка текущего запроса |
| `capturedAt` | RFC 3339 UTC | Время формирования снимка Chatballs |
| `scope` | Массив ссылок | Все текущие экспортируемые пары `sourceConnectionId + fieldId` |
| `items` | Массив FieldValue | Ровно одна запись на каждую пару `scope`; дубликаты запрещены |

Снимок относится к контакту текущего разрешённого диалога и согласованным WEB-источникам. Его область не расширяется до всех данных контакта автоматически. Ключ, название и значения хранятся в исходном виде без локализованного превращения числа/boolean в текст.

`mode: replace` означает: GoCoStack заменяет **рабочий контекст кастомных полей** сессии целиком данным снимком, а не сливает его с прежним объектом. Отсутствующее в новом `scope` поле больше не используется из старого кеша. Это правило текущего контекста; оно не является ложным подтверждением физического удаления всех исторических копий GoCoStack. Их хранение регулируется соглашением сторон.

### Элемент FieldValue

| Поле | Тип | Обязательность и смысл |
|---|---|---|
| `sourceConnectionId` | Непрозрачная строка | Обязательно; разрешённый WEB-источник |
| `fieldId` | Непрозрачная строка | Обязательно; устойчивый ID текущего определения поля |
| `key` | Строка | Обязательно; машинный ключ из схемы источника |
| `label` | Строка | Обязательно; текущая подпись поля |
| `type` | Enum | Обязательно; один из типов таблицы ниже |
| `status` | `set \| unset \| invalid` | Обязательно; состояние текущего значения |
| `value` | JSON-значение или null | Обязательно; типизированное значение только при `set` |
| `updatedAt` | RFC 3339 UTC или null | Обязательно; фактическое время записи значения, если запись существует |
| `options` | Массив вариантов | Обязательно только для `enum`; у других типов отсутствует |
| `reasonCode` | Строка | Обязательно только для `invalid`, без невалидного исходного значения |

Вариант enum содержит `value`, `label` и, если задан в текущей схеме, `color`. Значение поля — именно код `value`, а не отображаемая подпись. Цвет — необязательные метаданные, не команда изменить продуктовый UI.

| `type` | JSON-тип `value` при `set` | Правило |
|---|---|---|
| `string` | string | Сохраняется фактическая строка, включая допустимую пустую |
| `number` | number | Число, не форматированная строка; boolean не является числом |
| `boolean` | boolean | `true` / `false`, не «Да/Нет» и не `0/1` |
| `datetime` | string | Валидированная исходная строка ISO 8601; отсутствующий часовой пояс не выдумывается |
| `enum` | string | Один из текущих кодов `options[].value` |
| `email` | string | Значение, прошедшее штатную проверку CB |
| `phone` | string | Сохранённое нормализованное значение CB |
| `url` | string | Значение, прошедшее штатную проверку CB |

Служебные `capturedAt` / `updatedAt` всегда передаются в UTC. Значение пользовательского `datetime` не переинтерпретируется при экспорте: существующая модель может содержать ISO 8601 без явного смещения.

### Значение отсутствует, пустое или некорректное

| Состояние в CB | Передача |
|---|---|
| Есть валидное значение | `status: set`, исходный типизированный `value`, реальный `updatedAt` |
| Валидные `""`, `0`, `false` | `status: set`; не заменяются на null и не пропускаются |
| Для действующего разрешённого определения нет сохранённой записи | `status: unset`, `value: null`, `updatedAt: null` |
| Значение очищено штатным `setFields(...null...)` | Следующий снимок содержит то же `unset`; старое значение удаляется из рабочего контекста GoCoStack |
| Сохранённая запись не соответствует текущему типу/вариантам/формату | `status: invalid`, `value: null`, фактический `updatedAt`, безопасный `reasonCode` |
| Поле удалено из схемы или больше не разрешено | Его нет в новом `scope/items`; старое разрешение не позволяет продолжить экспорт |

Коды `invalid`: `type`, `option`, `format`, `length`, `schema`. Это безопасная причина, не само невалидное значение. Нельзя сохранять прежнее значение в рабочем контексте только потому, что новое стало `invalid`.

**Ограничение существующей модели:** CB при очистке удаляет запись значения. Без дополнительной истории нельзя достоверно отличить первое отсутствие значения от прежней очистки или сообщить точный `clearedAt`. Контракт не вводит выдуманное состояние «когда-то было очищено». Для интеграции важен актуальный `unset`, который явно сбрасывает прежнее значение.

Удаление определения не гарантирует физическое удаление старой строки значения в CB. Такие строки без действующего определения не экспортируются. Если тип изменён, сохранённое значение повторно проверяется по текущей схеме до экспорта.

Для защиты от смены схемы «A → B → A» сервер хранит монотонную generation WEB-схемы: штатный путь сохранения определений повышает её в той же транзакции при действительном изменении. Generation входит в привязку авторизации/отпечаток вместе с ревизией allowlist и сохраняется в БД; один hash текущего содержимого или наблюдение только при dispatch недостаточны. Существующий runtime_revision источника сейчас обслуживает LLM/SPEECH и не объявляется уже готовой версией WEB-схемы. Реализация добавляет внутренний учёт generation без изменения публичного setFields и без пересоздания значений/ключей.

### Обновления, очередь и восстановление

1. Chatballs формирует снимок для очередного AgentRequest из текущих разрешённых определений и значений контакта. Порядок записей детерминирован: источник, порядок схемы, ID поля.
2. Снимок и состав разрешений замораживаются вместе с request до HTTP. Сетевой повтор сохраняет `snapshotId`, `capturedAt`, значения и общий digest.
3. Изменение только значения появляется в следующем допустимом запросе. Оно не переписывает уже принятый запрос и само не запускает новый автономный ход или webhook.
4. Обновление схемы экспортируемого поля либо состава разрешённых источников/полей изменяет контрольный отпечаток политики внешнего исполнения. Он проверяется до dispatch/применения/доставки вместе с версиями; удаление/отзыв не обходятся старым запросом, курсором или инициативой.
5. Повторное создание поля под прежним ключом получает новый ID и требует нового явного разрешения. Возврат настроек назад не оживляет старую авторизацию.
6. После сотрудника следующий допустимый запрос формирует свежий снимок. Повтор старого запроса не откатывает более новый контекст памяти; GoCoStack учитывает устойчивые ID и порядок ходов.
7. История сообщений не является историей всех изменений кастомных полей. Пагинация истории сохраняет свою границу; актуальный снимок полей передаётся отдельным блоком AgentRequest.
8. Если полный блок нарушает лимит запроса, CB не обрезает поля скрытно и не отправляет частичный `replace`: применяется проверяемая ошибка подготовки контекста и штатная передача сотруднику.
9. Снимки и приёмочные проверки используют тот же защищённый контур хранения и журнал без сырых значений, что и остальные данные запроса.

**Запись из GoCoStack в кастомные поля этим контрактом не разрешена.** AgentResult, callback и инициативное сообщение не принимают patch контакта или определений. Существующий сайт/штатные операции CB остаются источником изменений.
