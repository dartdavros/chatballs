# Известные данные в ручном создании записи

## Проблема и решение владельца

06.11.2026 владелец потребовал исправить подпись ответственного и исключить повторный ввод уже известных имени, email и телефона. Сейчас descriptor._users не учитывает EMAIL, каталог отдаёт схему без начальных значений, ManualLaunch начинает с пустого объекта. Поля на приложенном снимке относятся к прямой операции создания записи. Кадры L2/L4 утверждённого baseline уже показывают данные текущего контакта.

## Сценарии

1. В доступном диалоге с известными контактными данными сотрудник открывает создание лида: имя, email и телефон уже видны в штатных полях.
2. Если часть данных неизвестна, заполнены только известные поля. Название, стадия и ответственный не выводятся догадками.
3. Сотрудник исправляет или очищает значение; preview и запуск используют именно его ввод. Обновление данных формы не восстанавливает очищенное поле.
4. При выборе ответственного отображается доступное полное имя, затем email, а ID служит последним резервом; API получает ID.
5. Другой диалог/операция получает собственные значения; скрытый или чужой контакт не раскрывается. Сценарии сохраняют заданные автором привязки.

## Границы реализации

Контракт адаптера описывает явные привязки начальных полей и типизированные преобразования. Сервер вычисляет их только для разрешённой операции и текущего проверенного диалога, возвращает начальный объект отдельно от TypeSpec. UI использует его при открытии формы и хранит дальнейшие правки локально до штатного preview/подтверждения. Общий механизм не содержит проверок бренда и эвристик по именам полей. Bitrix24 объявляет поля имени/телефона/email для создания лида/контакта и сохраняет собственную вложенную схему CRM. Новые бизнес-записи ради проверки не создаются.

Дизайн сохраняет существующие поля и контролы baseline «Запуск из диалога.dc.html»; новые экраны/блоки/состояния не вводятся. Реальное автозаполнение не подменяется данными демонстрационного макета.

## Архитектурное покрытие

Система, контейнеры и deployment используют существующие view-service-context, view-service-containers и view-service-deployment: штатные internal-ui/backend/PostgreSQL и защищённый выход в Битрикс24, без новых сервисов. Компоненты — view-service-workbench/view-service-backend; код и упорядоченные взаимодействия уточняются отдельными planned-представлениями ручного заполнения. Никакой внутренний уровень Chatballs не исключён. Внешние внутренности Битрикс24 остаются за существующими исключениями модели: Chatballs не владеет исходниками и deployment портала. ADR-0038 регулирует расширяемый контракт без брендов в ядре; ADR-0012 — tenant и права. Planned не объявляется реализованным.

## Вне объёма

Изменение аккаунтов и прав, миграции данных, новый дизайн, угадывание фамилии, названия, стадии или ответственного, автоматическая запись при открытии формы, пересоздание/изменение сохранённых сценариев, общий прогон тестов.

## Открытые вопросы

Нет продуктовых вопросов, блокирующих указанную правку. Точные доступные источники и контракты подтверждаются при реализации адресными тестами и штатной browser-проверкой; отсутствие данных не трактуется как разрешение придумать их.

Контекст, контейнеры и deployment прежние: новых процессов, хранилищ и протоколов нет. Все новые элементы и связи planned до проверенной публикации Skaro. Это исправление данных модели по конкретной диагностике, а не перепланирование завершённых зависимостей.
