# Автоматизация и управляемый обмен T-172

Статус: проект детализации принятой SPEC-0037/ADR-0038. Описание planned;
не является отчётом об исполнении, проверке внешнего сервиса или публикации.

## Границы и дизайн

Общий launch/runner дополняется событиями Chatballs, проверенным webhook,
cursor-опросом при отсутствии webhook, расписанием и внешним API.
Ручной путь, ожидания и вложенные Run сохраняют свои проверки.
Новых обязательных служб, брокера, БД или CRM-мастер-базы нет.
Используются PostgreSQL/RLS, штатные worker и worker-events и inbox/outbox.

Личная приёмка двух baseline уже зафиксирована владельцем 22.10.2026 в R-28.
Источники UI — принятые Сервисы.dc.html, Сценарии.dc.html и Журнал запусков.dc.html
из design/baseline/service-integrations основной копии; устаревшие переходные
макеты не задают новый дизайн. Делегирование в принятом макете означает
«Сценарий выполнит свои шаги с вашими правами администратора».
Миграция не выбирает администратора за пользователя и не включает автоматизацию.
Настройка/результаты обмена и разбор спорных полей используют эти же экраны,
существующие компоненты и ru/en, без нового интерфейса.

## Делегат и единый запуск

Явное разрешение запуска без сотрудника связывается с текущим действующим
OWNER/ADMIN. Сохраняются tenant, делегат и текущая настройка. Копирование,
миграция или один лишь внешний ключ не создают делегирование.
Перед запуском и каждым новым эффектом проверяются текущая организация,
membership/роль, enabled, delegated, разрешённый вид триггера и scope;
Run сохраняет исходную политику, новые права не расширяют старый snapshot.
Отзыв прав/выключение прекращают новые эффекты и ожидания, сохраняя исход
уже отправленного запроса. Вложенные вызовы пересекают права предков.

Все инициаторы проходят общий сервис launch с серверным видом триггера.
Ключ Run — организация, стабильный сценарий и стабильное срабатывание;
ревизия определения не участвует в дедупликации. Снимок, Run, необходимые
checkpoints и outbox сохраняются атомарно. Для события доступен типизированный
event input, контекст строится после проверки видимости делегата.
Входы, файлы, условия, версии контрактов, подтверждения, лимиты и unknown
сохраняют общий протокол исполнителя.

API: Bearer хранится только как хеш в ScenarioExternalKey и ограничен одним
сценарием/trigger. Организация и делегат выводятся сервером. Request не выбирает
actor/grants/tenant или чужой контекст; scope проверяется до чтения данных/Run.
Повтор команды использует обязательный устойчивый ключ запроса.
Перевыпуск отзывает старый ключ; endpoint возвращает фактическое состояние
созданного/прежнего Run, а не обещание завершённого бизнес-эффекта.

## Durable ingress и fan-out

Адаптер проверяет исходные байты, подпись/секрет, схему, event ID, время,
sequence и объявленное replay-окно. Проверенный зашифрованный receipt и outbox
сохраняются до ACK. Дубликат не меняет конверт, конфликт ID/содержимого не
выдаётся за успешное новое событие. Callback и запуск подписчиков используют
один receipt, сохраняя существующее сопоставление ранних ожиданий.

Подходящие подписчики фиксируются устойчивыми delivery checkpoints.
Каждая доставка имеет независимый результат и собственный Run; ошибка одного
не откатывает доставку остальных. Падение после части fan-out возобновляет
оставшиеся доставки, не создаёт новые эффекты завершённым. Изменение ревизии
не меняет идентичность старого срабатывания. Новая подписка не получает
историческое событие как новое. Порции ограничены; остаток получает durable
продолжение. Отказ прав/условий/подключения имеет безопасный наблюдаемый исход.

Доменные факты публикуются через общий hook в исходной транзакции изменения
Chatballs. Отдельный event_type не регистрирует заново старые handlers и четыре
типа правил. Отправка/применение результата не исполняет правила повторно.
Сериализация payload сохраняет tenant/RLS и видимость; raw клиентские данные
не попадают в outbox. Origin/causal metadata передаются через тот же hook.

## Cursor, расписание и справедливость

Для события без webhook используется объявленный адаптером cursor poll.
Ответ адаптера проверяется тем же envelope/schema протоколом. Только транзакция
с durable receipts и outbox двигает cursor. Lease/fencing и проверка исходного
cursor не позволяют просроченному poller перезаписать новое состояние.
Ошибочный ответ и rollback сохраняют прежний cursor.

Каждое подключение имеет своё due/backoff и учитывает pause/Retry-After.
Ограниченные порции и отдельная bounded lane worker-events не задерживают
обработку сообщений и другие подключения. Долгий сетевой I/O выполняется вне
транзакции; ожидание не удерживает поток. Повтор poller идемпотентен.

Расписание использует сохранённый timezone организации и явные поля принятого
определения: дни недели, дата, daily/weekdays/monthly, число 1–28/последний день,
локальное время, misfire skip/once, ambiguous first/second, nonexistent skip/next.
DST fold выбирает ровно одно указанное в определении UTC-время; gap skip
пропускает отсутствующий slot, next переносит его к первому существующему времени.
При misfire once запускается одно последнее пропущенное срабатывание;
skip не воспроизводит пропущенные. Не создаётся очередь всех пропущенных slots.
Slot/cursor следующего расчёта и задание/Run сохраняются атомарно.
Стабильная идентичность slot не включает ревизию сценария.

## Связи и обмен

EntityLink хранит организацию, подключение, виды обеих сущностей и устойчивые
внутренний/внешний IDs. Создание/замена требуют явного подтверждённого выбора
или предусмотренного действия сценария с проверкой прав. Email/телефон и
недоверенные поля клиента не являются доказательством личности.
Снятие/замена связи не меняют внешнюю запись. Активный Run удерживает снимок
старой связи с текущими проверками доступа, новые Run используют новую.

Обмен выполняется только для явно связанных записей и включённых пар.
Исполняются направленные mappings, преобразования, source-of-truth,
выбранные conflict/deletion policies и самостоятельные таблицы статусов
Chatballs→CRM и CRM→Chatballs. Несопоставленное значение не меняет получателя.
Внешние бизнес-данные остаются у сервиса; checkpoints не становятся общей CRM.

Доступность чтения/изменения/удаления определяется контрактом установленного
адаптера и прежними доменными сервисами. Неподдерживаемая операция блокируется
объяснимо, не имитируется. Внешние эффекты проходят общий runner с effect key,
сверкой, retry/unknown, scope и актуальными правами. Native-изменение вызывает
штатный доменный сервис; нет HTTP к себе или универсальной записи в таблицы.

Checkpoint хранит необходимые зашифрованные значения/версии сторон и causal
идентичность. Эхо собственного эффекта не создаёт обратное изменение.
Повтор/перестановка событий не откатывают подтверждённый более новый результат.
Удаление обрабатывается ровно по выбранной политике: сохранение, снятие связи
или явно разрешённая поддерживаемая операция. Неизвестный исход не означает
подтверждённого удаления. Технические бюджеты ограничивают самопорождающиеся цепи.

При manual conflict спорные поля приостанавливаются и доступны OWNER/ADMIN
в существующем журнале «Требуют внимания»: оба значения, время/источник,
выбор каждого поля. Команда решения проверяет права, ревизию связи,
настройку и актуальность обоих значений. Более новое изменение отклоняет
устаревшее решение. Применение создаёт аудируемую команду общего исполнителя;
показываются фактические успех, частичный результат, ошибка, остановка или unknown.
Сохранение выбора не объявляется совершённым эффектом.

## Проверка и архитектурное покрытие

Реализация требует сборку, только затронутые backend-тесты с --reuse-db,
проверки durable ingress/fan-out и падения посреди распределения, scoped API,
cursor rollback/concurrency, DST/misfire/dedup, конфликты/удаление/эхо,
RLS и неизменность четырёх правил; UI проверяется task-local Playwright
в штатном контуре и включает ru/en справку.
Независимые контрактные проверки не заменяют реального внешнего доступа.
Mock API, fake backend, временные HTTP-серверы, seed/смена доступов не создаются.

Контекст, контейнеры, компоненты, код/данные, штатное развёртывание и ordered
dynamic-event/schedule/native-sync покрыты единой C4-моделью, без исключения
уровней. T-173 и полный native-каталог T-174–T-176 не объявляются реализованными.
Никакой planned элемент не становится current от принятия этой детализации.
Перед submit_result — актуальные get_c4_context/review_c4 по точному changeHash.
Отсутствующие реальные проверки фиксируются открытыми, весь этап не закрывается.

## Уточнение модулей T-172 — 03.11.2026

Существующие компоненты и ответственности сохранены. Валидатор
scenarios/synchronization.py остаётся; исполнение разделено на небольшие
synchronization_launch/plan/effects/native/access/support/retention модули
и synchronization_runtime.py, явные связи обслуживает entity_link_views.py.

Обмен строится одним immutable Run: read → plan → fresh read → validate →
условные remote/local effects → verify → finish. Native effect и его result
receipt фиксируются одной транзакцией. Падение отдельного runner commit не
повторяет доменное изменение. Ручное решение возобновляет plan этого Run;
граф не меняется и выбор сам не является эффектом. Оба направления одного
поля используют одно решение; отмена read-only decision не пишет в системы.

EntityDescriptor использует типизированные adapters/synchronization.py и
adapters/references.py. Условная внешняя запись обязана проверять expected
version и поддерживать общий effect-key протокол; отсутствие контракта
блокирует включение соответствующего направления. Bitrix24 объявляет только
read binding и поиск: обычный crm.*.update не выдаётся за CAS. Его исходящий
обмен этим пакетом не объявляется доступным. Native-эффекты вызывают штатные
доменные функции; публичное удаление контакта/переоткрытие закрытого диалога
не выдумываются (ADR-0001, SPEC-0018). Полный каталог T-174–T-176 остаётся planned.

Поиск проходит read operation прежнего runner, и только завершённый Run даёт
кандидатов для явной замены. Ссылка карточки — доверенный локальный callback
адаптера: HTTPS без query/fragment/userinfo. Bitrix24 возвращает origin портала
и путь карточки, не секретный webhook path. Email/телефон не доказывают личность.

Native clocks Contact/Conversation фиксируются в исходной транзакции.
Историческое неизвестное время не выдумывается; latest без времени недоступно.
Backoff due_at и watchdog lease delivery различаются, чтобы возобновление
после паузы не откладывало себя бесконечно. Нормальное опоздание schedule до
60 секунд считается текущим slot; более позднее подчиняется skip/once.
Табличное «не менять» сохраняет получателя; обратное соответствие не выводится.
Неактивные устаревшие baseline checkpoints очищаются по operational retention,
активные Run защищены. Контекст, контейнеры, компоненты, код/данные, deployment
и ordered dynamic-event/schedule/native-sync сохранены, исключений уровней нет.
