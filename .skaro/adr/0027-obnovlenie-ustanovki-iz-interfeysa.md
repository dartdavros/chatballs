## Контекст

Установка обновлялась только из консоли сервера; администратор не узнавал о новых версиях иначе как со страницы релизов, самообслуживание без SSH было невозможно. `backend-app` работает с минимальными правами (ADR-0026), и давать ему управление Docker нельзя.

## Решение

1. **Канал релизов — GitHub Releases** репозитория поставки (`CHATBALLS_UPDATE_REPO`, по умолчанию `dartdavros/chatballs`). Версия зашивается в образ бэкенда (`CHATBALLS_VERSION`; у dev-сборки `dev` обновлений нет). Релиз принимается только с ассетом `compose.yaml` по адресу `…/releases/download/v<версия>/compose.yaml`; версии сравниваются семантически. Проверка — из воркера раз в `CHATBALLS_UPDATE_CHECK_INTERVAL_SECONDS` (15 минут) и по кнопке; результат — в одной строке `UpdateState` вне организаций; ошибка канала ничего не роняет.
2. **Отдельный сервис `updater`** (образ на `docker:cli` с двумя скриптами) — единственный с `/var/run/docker.sock`. Обмен с `backend-app` — файлами в томе `chatballs-updates`: `heartbeat` (каждые 5 с; старше 90 с — «обновление недоступно»), `request.json`, `status.json` (`running`/`done`/`failed` со стадиями), `apply.log`. Updater принимает только цифровую версию, адрес со страницы релизов своего репозитория и `compose.yaml`, где все образы пришпилены `@sha256` из репозитория поставки; проект, каталог и том узнаёт из меток своего контейнера.
3. **Установка в отдельном контейнере** `chatballs-updater-apply` (тот же образ, `docker run -d --rm`, собственная входная точка установки): `config -q` → `pull` → `up -d --wait`. После успеха новый `compose.yaml` копируется в каталог установки. Второй запрос во время установки отклоняется; установка, оборвавшаяся без результата, помечается неудачной.
4. **Интерфейс:** баннер пользователю с правом управления «Платформой» по ADR-0024 «Доступна версия X» со ссылкой «Что нового», кнопкой «Обновить» и подтверждением; баннер переживает перезапуск бэкенда и показывает стадию, итог или причину сбоя. То же и кнопка «Проверить» — в карточке «Обновления» раздела «Платформа». Аудит `updates.install_requested`. Проверять и устанавливать — пользователь с правом управления «Платформой» по ADR-0024. Чтение статуса также сохраняется для пользователей с действующим правом чтения настроек установки.

5. **Связь с Backoffice** — серверный HTTPS check-in с UUIDv4 установки, текущей версией и необязательным `public_url` из существующих настроек. Адрес очищается по правилам SPEC-0005 R-17. Смена адреса сохраняет UUID. Передача `public_url` включается после развёртывания поддержки поля по T-021 в проекте Backoffice. UUID и расписание принадлежат установке, общее состояние хранится в PostgreSQL вне организаций. Первый цикл штатного воркера после смены версии `CHATBALLS_VERSION` резервирует check-in с прежним UUID, даже если суточный срок ещё не наступил. Перезапуск с той же версией соблюдает сохранённое расписание. Выключенная настройка, действующая резервация и срок ожидания после 429 имеют приоритет. Решение опирается на фактически запущенную версию воркера и действует также при обновлении из консоли. Встроенный адрес относится к официальному исходящему API продукта (SPEC-0005 R-15…R-20). Проверка сертификата обязательна. Запросы не следуют перенаправлениям. Backoffice не управляет обновлением и не передаёт адреса релизов.
6. **Одна настройка для внешних обращений** — включена по умолчанию, доступна для изменения пользователю с правом управления «Платформой» по ADR-0024. Она управляет фоновыми и ручными проверками GitHub, check-in, включая передачу настроенного внешнего адреса, и получением публикаций. Решение проверяется в общей серверной логике, включая вызов через каталог действий. Статус уже запущенной установки релиза читается по действующему протоколу.
7. **Независимая периодическая работа** — check-in запускает штатный poller. Резервирование попытки и контроль повторов сохраняются в общей базе. Результат связи и полученные сообщения хранятся отдельно от состояния проверки GitHub. Суточная отметка связи не определяет расписание синхронизации публикаций и время их показа. Рабочая копия той же установки наследует UUID при переносе и восстановлении, отдельный экземпляр получает новый до выхода в Backoffice.

Отклонены: Docker-сокет у `backend-app`; Watchtower и аналоги; проверка версии из браузера напрямую в GitHub.

## Настройка и сообщения в рабочем интерфейсе

Переключатель находится в карточке «Обновления» раздела «Настройки → Платформа» и сохраняется через существующую команду настроек установки. При выключении ручная проверка релизов недоступна, сведения о релизах остаются видны. При ошибке сохранения карточка показывает последнее подтверждённое значение и ошибку.

Сервисные сообщения доступны пользователю с правом управления «Платформой» по ADR-0024 в верхней полосе над рабочей оболочкой по [макету верхнего баннера](../../design/drafts/service-announcement-banner/index.html). Визуальный источник фиксируется в ревизии SHA-256 `4d9394d2a04f4aad25ff1bb3a7baede3e5ac0dd5c8060136a1896d01d4455b64`. При реализации закрепить этот макет в `design/baseline/installation-check-in/service-announcement-banner.dc.html` и привести `design/baseline/installation-check-in/platform-updates.dc.html` в соответствие новому размещению. Полоса использует фон штатного баннера в светлой и тёмной темах. Иконка, полный заголовок и текст и доступная ссылка «Подробнее» со стрелкой образуют центральную группу. Кнопка закрытия находится справа. Полный текст с абзацами переносится по доступной ширине. Макет иллюстрирует оформление одного сообщения, в приложении крестик выводит следующее по порядку Backoffice. После последнего сообщения полоса скрывается.

Состояние сообщений выдаётся отдельным запросом чтения в API установки пользователю с правом управления «Платформой». Сервер Chatballs держит открытое исходящее защищённое соединение с Backoffice. Сразу после успешного сохранения Backoffice отправляет подходящей подключённой установке новую публикацию или изменение. Если окно уже началось, Chatballs показывает сообщение сразу после получения. При подключении и восстановлении связи установка получает полный список с обеими границами каждой публикации. Сервер установки и открытая оболочка применяют `starts_at <= now < ends_at` без перезагрузки или нового обращения к Backoffice на границах. Сохранённые сообщения относятся к текущему включению внешних обращений. Сетевой сбой не продлевает срок показа. При отключении, до первой успешной синхронизации после включения и при отсутствии действующих незакрытых сообщений полоса скрыта. «Подробнее» ведёт по полю `link` публикации. Ссылка скрыта при пустом или недопустимом адресе. Блок списка и его состояния убираются из карточки «Обновления».

## Последствия

- `docker.sock` у `updater` равен root на хосте; поверхность сведена к минимуму. Без сервиса интерфейс показывает «обновление недоступно», CLI-путь остаётся.
- Обновление, перенос и восстановление из копии требуют сохранять идентификатор установки. Штатное клонирование для задач обрабатывается как отдельная установка. Обращения к Backoffice из такого контура при проверке допускаются только по согласованию.
- Новый Compose-сервис и расширение прав воркера не нужны. Пользовательская часть следует утверждённому макету.
- Откат — вручную (`compose.yaml` предыдущего релиза); автоматического отката нет — миграции не возвращаются.
