## Контекст

loader_assets/{runtime,site_fields}.js уже поддерживают очередь setFields и postMessage, useWidgetConsent.ts — начало через согласие. Настройка AI/форма запрещают модель/диалог до начала. SPEC-0037/ADR-0038 задают единые события/Run/grants/native действия. Зависимости T-172/T-174 приняты в зафиксированном владельцем объёме: общий event-runtime и каталог native-действий доступны для подключения события сайта. Ограничения их приёмки по реальным внешним подключениям сохраняются.

## Решение

1. Правило WEB связывает name/schema, публичное приглашение и приватный сценарий той же организации; новые правила выключены. Chatballs.emitEvent({widgetKey,name,eventId,data}) расширяет существующий API отдельной очередью, не меняет слияние setFields и не даёт браузеру выбирать scenario_id/grants.
2. До начала чата приглашение локально; data только в памяти, payload на backend не уходит. sessionStorage хранит только минимальную отметку правила с origin/widgetKey. Одно первое событие не вытесняется, TTL 5 минут; закрытие/reload не восстанавливает data и подавляет новый показ того же правила в сессии вкладки.
3. Принятие проходит действующие согласие и форму. Единый серверный consent из SPEC-0039 хранит актуальную принятую версию WebSession; старый токен/флаг не доказывает согласие. При уже принятом согласии событие допустимо без новой первой реплики.
4. Защищённый webchat ingress валидирует schema, widget/origin/session/consent и создаёт webchat.site_event в общем receipt+outbox до ACK. Дедуп eventId дополнен once-per-rule-per-WebSession. Данные недоверенны и не являются личностью/правом.
5. Fan-out, snapshots, Run, grants, журнал и восстановление — SPEC-0037. Зависимости T-172/T-174 остаются; их объём/порядок не меняются. Native-действие первого ответа вызывает исходные domain services и AI-orchestrator, не второй LLM-цикл или HTTP к себе.
6. Доверенное задание сценария отделено от псевдонимизированного контекста data. Первый клиентский текст/перехват/закрытие атомарно инвалидируют поздний проактивный эффект. Нет фиктивного клиентского сообщения, переоткрытия закрытой истории и повторного первого ответа.
7. Публичный источник имеет только ограниченную область посетителя; не расширяет grants/не подтверждает внешнюю запись. Отсутствие разрешения — честный отказ, не привилегированный технический запуск.
8. Приглашение не создаёт контакт/обращение/Message/unread/звук и не раскрывает панель само. Новые настройки и состояния — только после личной приёмки baseline; технические причины остаются в общем защищённом журнале.

## Варианты и последствия

Запуск AI до согласия отклонён владельцем. Произвольный scenario_id/API-key в браузере создаёт обход полномочий. Свой runner и встроенный DOM/scroll-трекинг не нужны. Выбран локальный показ до согласия и существующий сценарный контур после него; новых обязательных служб нет. Восстановление/dedup должны доказать отсутствие двойного первого ответа. Событие не превращается в маркетинговое сообщение активной переписке.
