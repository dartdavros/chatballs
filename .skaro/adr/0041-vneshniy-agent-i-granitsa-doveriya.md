## Контекст

PDF «Chatballs_Autonomous_Agent», 09.11.2026, описывает самостоятельный сервис заказчика вместо встроенного исполнения AI. Владелец 10.11.2026 выбрал новый контракт, согласованные исходные данные доверенному сервису и инициативные отправки только в открытые диалоги под ИИ.

Реальный код: ai/agent_models.py хранит настройки встроенной модели; identity/operation_modes.py требует provider+model; conversations/ai_turn.py планирует embeddings/LLM; ai_turn_state.py ставит ход в outbox; ai_reply_delivery.py перепроверяет управление при отправке. integrations уже имеет SERVICE/ADAPTER, зашифрованные ServiceConnectionSettings и защищённый транспорт. Повторное использование этих основ не доказывает наличие внешнего runtime.

## Решение

1. Разделить режим исполнения AIAgent на builtin/external. Общие ingress, очередь, управление, tenant isolation, сообщения и delivery остаются. Готовность проверяется по выбранному режиму; external не вызывает промежуточную LLM или retrieval Chatballs.
2. Использовать обычное сервисное подключение с версионированным профилем external_agent_v1, общими credentials и сетью. Протокольные dispatch/status/cancel/capabilities — внутренний API исполнителя, не автоматически доступные инструменты/действия сценариев. Явное внешнее разрешение не наследует AgentActionGrant и делегата.
3. В ai/external_agents/ разделить конфигурацию/контракт/контекст, state, HTTP dispatch, inbox receipt, recovery, authorization, delivery и handoff. Новые конкретные пути — целевые, пока не реализованные. Использовать штатный PostgreSQL/RLS и outbox/worker-events. Не представлять каждый ответ агента искусственным ScenarioRun; не дублировать общий транспорт/шифрование/очередь.
4. Один устойчивый request на одно клиентское сообщение, FIFO без объединения и максимум один активный запрос диалога. Долгий результат освобождает HTTP и воркер. Callback может опередить HTTP-ответ; одна транзакционная обработка всех вариантов результата. Ожидания, immutable snapshot, lease/fencing и ID переживают перезапуск.
5. Два независимых scoped Bearer credential поверх HTTPS. Tenant определяется проверенным credential. Монотонная ревизия внешнего исполнения и authorizationId связывают конкретный режим/агента/подключение/диалог и версию управления; возврат/повторное включение не оживляют старый результат. Проверка действует до фактической передачи каналу.
6. Доверенный сервис заказчика получает согласованные исходные тексты и отдельный allowlist данных. Защита его вызовов собственной LLM и хранения — ответственность заказчика. Это новая явно выбранная граница передачи по SPEC-0041, а не исключение, автоматически применяемое к AI-провайдерам Chatballs. SPEC-0022/ADR-0031 продолжают полностью действовать для встроенных LLM, embeddings и инструментов; карта псевдонимов нигде не сохраняется. Старое aiAccess не разрешает внешний экспорт.
7. Полный обмен поддерживает существующие текст, файлы/изображения, контактные сообщения и запрос контакта по способностям канала, оформленные snapshots через разрешённые шаблоны и составные ответы. Scoped file API переиспользует штатное tenant-хранилище/лимиты, HTML/CSS — общий безопасный renderer, а не произвольный srcDoc. Голос Chatballs сначала расшифровывает, передаёт текст и wasVoice:true, без исходного аудио. Для внешнего режима STT выбирается отдельно от LLM ответов. История доступна постранично в своём согласованном snapshot, включая resync памяти. Номер версии API не обозначает урезанную поставку. Структурированный handoff не распознаётся по текстовому токену встроенного runtime.
8. Инициатива разрешается отдельным флагом внутри текущего открытого диалога под ИИ, при пустой клиентской очереди. Перехват/закрытие/отзыв подавляют инициативу; только сотрудник штатно возвращает управление. Сервис не создаёт и не переоткрывает диалоги.
9. Идемпотентность Chatballs даёт одну запись сообщения. При неизвестном исходе у канала не обещается exactly-once: отдельно transport_accepted/unknown. Отмена сервиса best effort без обещания компенсации его side effects.
10. UI требует отдельного лично принятый baseline с существующими компонентами; выбранные сейчас требования не утверждают layout/тексты. Блокировка дизайна локальна UI, не превращается в задачу по написанию спецификаций.

11. Кастомные поля источников CB передаются отдельно от стандартной карточки: context.customer.customFields — полный mode:replace снимок. Идентичность sourceConnectionId+fieldId сохраняет происхождение и исключает коллизии key. Существующие ContactFieldValue и схема WEB читаются без изменения их штатного протокола записи; статусы set/unset/invalid честно отражают текущее состояние. Null в CB удаляет запись, поэтому clearedAt/история очисток не выдумываются. Снимок request неизменяем; следующий запрос читает свежие значения, schema/allowlist входят в отпечаток текущей внешней политики. Старый кеш не сохраняет отозванное значение в рабочем контексте. Существующий runtime псевдонимизации не ослабляется, обратная запись из сервиса не разрешена.

## Рассмотренные альтернативы

- OpenAI-compatible proxy: не выражает независимые память, callbacks, инициативу, handoff и полномочия; создаёт ложную модель LLM-провайдера.
- HTTP/MCP tool в существующем LLM-loop: требует ненужной промежуточной модели и не передаёт сервису роль самостоятельного исполнителя.
- Отдельные брокер/worker-stack/БД: избыточны для существующих outbox/worker-events.
- Долгое открытое HTTP и карта псевдонимов в памяти до callback: не переживают рестарт и противоречат выбранной границе данных.
- Автоматическая передача старых permissions/полного контакта: нарушает явное назначение и минимизацию.

## Последствия

Новый контракт и устойчивые модели требуют миграций и проверок гонок. Старые агенты остаются builtin. Внешняя недоступность не запускает встроенную LLM автоматически. Приёмка требует реального сервиса. Параметры времени/ограничения предложены в SPEC-0041 и контракте; принятие документа не является результатом локальной проверки или релиза. Все уровни C4 покрыты общей моделью, новые элементы planned.

Для защиты от смены схемы «A → B → A» сервер хранит монотонную generation WEB-схемы: штатный путь сохранения определений повышает её в той же транзакции при действительном изменении. Generation входит в привязку авторизации/отпечаток вместе с ревизией allowlist и сохраняется в БД; один hash текущего содержимого или наблюдение только при dispatch недостаточны. Существующий runtime_revision источника сейчас обслуживает LLM/SPEECH и не объявляется уже готовой версией WEB-схемы. Реализация добавляет внутренний учёт generation без изменения публичного setFields и без пересоздания значений/ключей.
