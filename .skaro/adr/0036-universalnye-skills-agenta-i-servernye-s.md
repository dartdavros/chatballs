## Контекст

Агенты Chatballs уже получают данные систем организации через HTTP- и MCP-инструменты. Пересказ сплошным текстом не позволяет стабильно оформлять повторяющиеся ответы: состав заказа, его статус, подборку или другие сведения.

Нужен универсальный механизм переиспользуемых инструкций с необязательными шаблонами ответа. Владелец согласовал общую библиотеку организации, подключение одного skill нескольким агентам, несколько необязательных шаблонов внутри skill и редактирование HTML/CSS с переменными без визуального конструктора в первой версии.

Текущее поле Message.content_html предназначено для санитизированного входящего email. Публичный API истории веб-виджета не отдаёт его, а компонент сообщения показывает текст. Наличие поля не означает готовность поддержки оформленных исходящих сообщений.

Архитектурные основания:
- ADR-0009: конфигурация агента изменяется без релизов и многошаговой публикации.
- ADR-0012: организация — граница изоляции.
- ADR-0019: Chatballs — контакт-центр, без собственной модели заказов, каталога и продаж.
- ADR-0028: ход AI выполняется асинхронно, ограничен сроком и сохраняет существующие правила доставки.
- ADR-0030 и ADR-0032: результаты внешних инструментов — недоверенные данные; инструменты только читают и включаются агенту явно.
- ADR-0031: единый слой псевдонимизации для всех обращений к модели; карта восстановления существует только в памяти хода.

Встраивание всех skills целиком в промпт увеличивает контекст каждого запроса. Генерация HTML моделью делает оформление непредсказуемым. Произвольные HTML/CSS создают риск исполнения кода, утечки данных и влияния на интерфейс вне сообщения.

## Решение

### 1. Библиотека и подключение
Skill — отдельная сущность организации: стабильный идентификатор, название, краткое описание для выбора, подробная инструкция и ноль или несколько шаблонов ответа. Это инструкции применения и поведения, а не источник фактов для retrieval.

Управляют библиотекой владелец и администратор организации. Skill подключается агенту явно; один skill может использоваться несколькими агентами. Все связи и обращения проверяют tenant-контекст; межорганизационные ссылки запрещены.

Skills не обязательны для создания агента или начала работы. Изменения применяются без публикации и релизов. Для одного хода используется согласованный снимок доступных skills и загружаемого содержимого: редактирование во время хода не должно смешивать инструкцию и шаблон из разных состояний. Последующие ходы используют актуальную конфигурацию.

### 2. Загрузка по необходимости
В исходный контекст модели включается краткий каталог только подключённых skills: идентификаторы, названия и описания. Подробные инструкции и описания шаблонов загружаются по выбору модели через внутреннюю операцию runtime. HTML/CSS шаблона для заполнения в модель передавать не требуется: достаточно назначения и схемы входных данных.

Skills могут задавать порядок работы с существующими инструментами и правила ответа, но не отменяют системные ограничения, язык ответа, правила передачи оператору или проверки доступа. Внешние результаты остаются данными и не могут добавлять либо изменять инструкции skill.

### 3. Права и исполнение
Skill не содержит исполняемых программ и не создаёт новые полномочия. Упоминание HTTP/MCP-инструмента в инструкции не включает его агенту. Вызовы используют уже разрешённые инструменты и существующие ограничения чтения, исходящих адресов и псевдонимизации.

Внутренние операции загрузки skill и подготовки оформленного ответа выполняются в общем runtime хода, с ограничением числа операций, размера данных и времени. Они не получают отдельный неограниченный цикл и не обходят срок хода. Живой и существующий проверочный чат используют один механизм.

### 4. Состав шаблона
Каждый шаблон имеет стабильный идентификатор внутри skill, название, назначение, схему входных данных, HTML, CSS и текстовое представление для каналов без поддержки HTML.

Схема описывает типы, вложенные объекты и списки, обязательные и необязательные значения. Шаблонизация допускает подстановку переменных, перебор списков и условия отображения. Доступ к файловой системе, сети, секретам, произвольным объектам приложения и выполнение кода запрещены. Переменные являются данными, а не фрагментами разметки; вывод экранируется по контексту.

Инструкция skill может определять действия при недостатке данных. Отсутствующие цены, позиции, статусы и сроки не заполняются выдуманными значениями. Skill без шаблонов остаётся полноценной инструкцией для обычного ответа.

### 5. Серверная подготовка ответа
Модель выбирает подключённый skill и его шаблон, передаёт структурированные входные значения. Сервер проверяет доступность, принадлежность шаблона, схему и ограничения размера; восстанавливает известные псевдонимы в значениях; затем формирует HTML и текст по одному набору данных.

Восстановление значений производится до контекстного экранирования и окончательной очистки HTML. Подстановка настоящих значений в уже очищенный HTML запрещена. Неизвестные и искажённые псевдонимы обрабатываются по ADR-0031; потеря обязательного значения делает данные некорректными.

Операция подготовки не отправляет сообщение самостоятельно. Её результат включается в штатный контур окончательного ответа, сохранения и доставки: промежуточные вызовы не порождают сообщения клиенту. Модель не переписывает итоговую разметку.

### 6. Безопасное оформление
HTML, атрибуты, адреса ссылок и CSS ограничены явно заданной политикой допустимых конструкций. Запрещены скрипты, обработчики событий, iframe, формы, исполняемые и опасные адреса, CSS-импорты и внешние загрузки ресурсов из шаблона.

CSS действует только внутри конкретного сообщения и не может менять оформление виджета, соседних сообщений или рабочего места сотрудника. Проверка выполняется на сервере; браузер применяет дополнительную защиту при показе. Предпросмотр использует ту же политику и механизм отображения.

Неподдерживаемые конструкции объясняются администратору при проверке шаблона; сохранённый предпросмотр должен соответствовать доставляемому результату. Очистка и изоляция обязательны независимо от роли автора шаблона.

### 7. Представление и история
Оформленное сообщение содержит текстовую версию и безопасное HTML-представление с необходимым изолированным оформлением. Message.text и Message.content_html используются как единая основа текстового и HTML-содержимого; семантика content_html расширяется на безопасные исходящие ответы. Контракт хранения оформления уточняется в спецификации.

Веб-виджет и лента сотрудника показывают одно сохранённое HTML-содержимое и оформление. Каналы без поддержки HTML получают текстовую версию; полной визуальной совместимости сторонних мессенджеров не предполагается. В контекст следующих ходов используется текст сообщения с повторной псевдонимизацией.

В истории сохраняется готовый снимок сообщения, включая необходимое оформление. Изменение или удаление skill либо шаблона не вызывает повторную сборку старых сообщений. Это снимок коммуникации, а не релиз конфигурации агента.

### 8. Данные и язык
ПДн в инструкциях, примерах, схемах, истории и входных значениях проходят единый слой псевдонимизации при отправке модели. Карта восстановления, исходные ответы HTTP/MCP и отдельные копии входных данных рендера не сохраняются в БД, аудит и логи. Допустимы технические метаданные без содержимого и секретов. Сохраняется только готовое клиентское сообщение по действующим правилам хранения коммуникаций.

Заказы и другие внешние объекты не становятся сущностями Chatballs. Данные в карточке — содержание сообщения, а не собственный коммерческий учёт.

Системные подписи и сообщения об ошибках используют действующую i18n. Для обращённого к клиенту системного текста используется язык организации. Пользовательские инструкции и тексты шаблонов не переводятся автоматически; выбор модели следует существующей настройке языка ответа агента.

### 9. Ошибки и границы первой версии
Недоступный skill, некорректные данные или ошибка шаблона не приводят к отправке сырого HTML, псевдонимов или служебной ошибки. Возможная коррекция ограничена общим бюджетом хода; при невозможности сформировать корректный ответ действуют правила недостатка данных и передачи оператору. В канал без HTML отправляется текстовое представление, а не исходный код шаблона.

В первую версию не входят визуальный конструктор, выполнение кода внутри skills, интерактивные коммерческие действия, изменение внешних данных и собственная модель заказов. UI реализуется только после утверждения baseline.

Отклонены: полный текст всех skills в каждом промпте; генерация разметки моделью вместо сохранённого шаблона; сохранение только ссылки на шаблон с повторной сборкой истории; отдельные несогласованные механизмы рендера для клиента, сотрудника и предпросмотра.

## Последствия

Преимущества:
- Один skill переиспользуется агентами организации и объединяет правила сценария с несколькими вариантами оформления.
- Загрузка по необходимости ограничивает постоянный объём контекста.
- Серверная сборка обеспечивает повторяемое оформление, проверку входных данных и единый результат для клиента и сотрудника.
- История не зависит от дальнейшего редактирования шаблона.
- Сохраняются границы контакт-центра, изоляция организаций и действующие ограничения инструментов.

Стоимость и ограничения:
- Потребуются библиотека и связи skills, внутренние операции runtime, ограниченный шаблонизатор, политика HTML/CSS, расширение контрактов сообщений и общий безопасный механизм отображения.
- Загрузка skills может добавлять обращения к модели и расходовать часть срока хода; для моделей без поддержки вызова инструментов использование этого механизма недоступно, что должно быть явно отражено в проверке совместимости.
- Выбор skill моделью не гарантирует его применение к каждому подходящему запросу. Инструкции и качество выбора требуют проверки сценариями; отдельный детерминированный маршрутизатор этим ADR не вводится.
- Проверка типов не доказывает достоверность значений. Инструкция запрещает выдумывание фактов; проверка реальных сценариев должна учитывать соответствие ответа данным источника.
- Ограниченный HTML/CSS не позволяет использовать произвольный веб-дизайн. Допустимый набор должен быть согласован с макетами до реализации.
- Снимок оформления увеличивает объём истории. Нужны технические ограничения размера сообщения и вложенных списков.
- Общая правка skill влияет на будущие ходы всех подключённых агентов; интерфейс должен сообщать об этом.
- При реализации потребуется спецификация skills и согласованные изменения спецификаций «Агент: конфигурация и ход ответа», «Веб-чат» и «Инструменты агента» в части использования skills и оформленных сообщений. Этот ADR дополняет существующие решения, не заменяя ADR-0009, ADR-0019, ADR-0031 или ADR-0032.
- Макеты библиотеки, редакторов, подключения skills и новых представлений сообщений должны быть утверждены до UI-работ.
