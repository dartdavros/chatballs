## Цель

Добавить оставшиеся публичные административные действия в их собственной области полномочий и закрыть проверяемое соответствие всего продуктового API общему каталогу. Завершённый механизм принимается по всей SPEC-0037, включая ранее реализованные способы запуска.

## Критерии приёмки

- [x] Обязательный gate: реализация начинается только после явно зафиксированной личной приёмки владельцем ОБОИХ результатов baseline; принятие карточки плана/задачи не является приёмкой макета. Основание: SPEC-0037 R-28.
- [x] Каталог включает все публичные продуктовые операции области установки/платформы/обновлений/хранения/настроек и оставшиеся возможности по полному inventory. Они доступны только существующим уполномоченным инициаторам своей области; обычное tenant-подключение/сценарий не получает этих полномочий.
- [x] Полный inventory всех продуктовых API не содержит незакрытых действий; для auth/transport/health/protocol endpoints указана проверяемая отдельная классификация. Нельзя переименовать бизнес-операцию в техническую ради исключения из реестра.
- [x] Обёртки сохраняют штатные доменные проверки, аудит, подтверждения/безопасный повтор и процедуры администрирования; нет универсального SQL/записи в таблицы, HTTP к себе, скрытого сброса доступа или отдельной модели ролей. Наличие действия не авторизует его реальное выполнение без требуемых полномочий/указаний.
- [x] В одном доступном штатном контуре проверены полный пользовательский путь: подключение → готовый/собственный сценарий → сотрудник/ИИ/автоматический инициатор → смешанные внутренние/внешние шаги → журнал/восстановление, по принятому baseline. Отсутствующие реальные внешние доступы честно указаны; заглушки не используются как доказательство.
- [x] Независимый адаптер и отсутствовавший пользовательский сценарий подключаются без правки ядра/общих экранов; проверены registry/схемы/справочники/пресеты/версионность. Конкретные брендовые CRM/Mindbox не изображаются реализованными этим общим механизмом.
- [x] По совокупности результатов и затронутых интеграционных проверок закрыты права/RLS, OAuth/секреты/файлы, дубли/гонки, падение на границе эффекта/фиксации, ветви/ожидания/ранние callback, отмена/неизвестность, синхронизация, 7/30 retention и совместимость старых инструментов/правил; непроверенное явно оставлено blocker, а не отмечено пройденным.
- [x] Пользовательская справка и документация контрактов/расширений/восстановления вместе с проверяемыми примерами описывают фактическую реализацию. Выполнены сборка, только относящиеся к изменениям тесты и browser-проверки; полный прогон без явного указания не запускался.
- [x] C4 review соответствует точному итоговому changeHash и реальным code evidence; planned/current обновляются только по проверенной опубликованной реализации. Готовность функции объявляется только при выполнении всех R-1–R-31 и личной приёмке обоих baseline, а не по наличию одного инфраструктурного результата.

## Заметки

Причина выделения: отдельная область полномочий установки/платформы и завершение coverage всего публичного API после доменных групп. Это реализация административных обёрток с необходимой общей интеграционной проверкой, не отдельная задача «написать план/спеку» или прогон тестов ради количества. Проверки в предыдущих задачах остаются обязательными; здесь проверяется их взаимодействие и полнота, без повторного полного тестового прогона. Реальные production/аккаунтные изменения ради проверки не выполнять. Пути: action_catalog/settings.py и разделённые platform/update/storage wrappers, coverage.py. C4: native/policy, deployment и затронутые dynamics. Основа: SPEC-0037, ADR-0038, docs/service-integrations-c4.md и актуальный get_c4_context. Один backend/штатные PostgreSQL, worker/worker-events, inbox/outbox, tenant/RLS; без новых обязательных служб. Соблюдать AGENTS.md, DRY/KISS/SRP, NO GOD FILES, отдельные model/API/subviews, i18n ru/en. Проверки: сборка для изменений кода и только непосредственно затронутые тесты (backend --reuse-db), UI — браузером в штатном контуре. Без полного прогона, seed, временных API/fake backend и изменения доступов ради проверки. Для новых внешних доступов использовать реальный штатный контур; отсутствие доступа фиксировать как blocker, не выдавать непроверенное за пройденное. Перед submit_result прочитать get_c4_context, сверить реальные изменения со спецификацией/C4; необходимые изменения документации/архитектуры предложить единым propose_c4 и получить принятие, затем review_c4 с точным changeHash, затронутыми ID и доказательствами из кода. После изменения кода/документов повторить review. Planned не объявлять current до проверенной публикации.

## Итог

Реализованы 26 глобальных действий в собственных областях полномочий; общий каталог содержит 301 действие, полная опись 775 API/protocol-входов без незакрытых записей. Сборка, 68 итоговых адресных тестов, доступные browser-проверки и exact C4 review пройдены; реальные внешние проверки по прямому указанию владельца «пропусти, я сам проверю потом» не выполнялись и не отмечаются пройденными.
