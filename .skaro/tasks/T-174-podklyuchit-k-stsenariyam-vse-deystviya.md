## Цель

Реализовать внутренние действия диалогов, контактов, сообщений и обслуживания через штатные доменные сервисы. Сценарии получают полноценные операции Chatballs с исходными правами и бизнес-правилами.

## Критерии приёмки

- [x] Обязательный gate: реализация начинается только после явно зафиксированной личной приёмки владельцем ОБОИХ результатов baseline; принятие карточки плана/задачи не является приёмкой макета. Основание: SPEC-0037 R-28.
- [x] Реестр включает все публичные продуктовые операции диалогов/контактов/меток/сообщений, внутренних комментариев/вложений/голосовых, управления/передачи/участников, звонков, уведомлений, шаблонов ответов и правил обработки, а также отчётов/оценок/анализа качества обслуживания; не ограничен несколькими пресетами.
- [x] Создано проверяемое соответствие каждого продуктового API-входа этой группы зарегистрированному действию; non-product auth/transport endpoints классифицированы с причиной, не скрывают пропущенную бизнес-функцию. Новая функция обязана добавлять action descriptor.
- [x] Обёртки разделены по доменам и вызывают исходные сервисы без HTTP к себе и произвольной записи в таблицы. Сохраняются видимость/RLS, назначения/супервизорские ограничения, внутренняя аудитория, идемпотентность доставки и другие исходные проверки.
- [x] Внутренние/внешние шаги совместимы в одном сценарии, поддерживают типы/файлы/выходы/ссылки/ошибки общего контракта; публичные действия доступны по grants тем же сотрудникам/ИИ/автоматизации, а не через отдельный обход.
- [x] Действия и их параметры отображаются общими схемными контролами принятого редактора/журнала, без нового layout или кнопок вне baseline; публикация доменных событий не дублирует старые правила и не создаёт обратный цикл.
- [x] Затронутые contract/coverage и поведенческие тесты проверяют значимые ограничения доменов и вызов из runner; UI проверен браузером. Каталог действий/пользовательские примеры этой группы актуальны.

## Заметки

Причина выделения: независимо полезный полный набор операций рабочего обслуживания; инвентаризация многочисленных публичных API всех доменов слишком велика для одной задачи вместе с настройками организации и администрированием установки. Все доменные действия этой группы, проверки, UI-метаданные и справка остаются в одной задаче; нет дробления по файлам/слоям. Пути: action_catalog/{registry,coverage,conversations,calls,notifications,reports,...}.py; текущие domain services. C4: native и rel-service-native-*. Основа: SPEC-0037, ADR-0038, docs/service-integrations-c4.md и актуальный get_c4_context. Один backend/штатные PostgreSQL, worker/worker-events, inbox/outbox, tenant/RLS; без новых обязательных служб. Соблюдать AGENTS.md, DRY/KISS/SRP, NO GOD FILES, отдельные model/API/subviews, i18n ru/en. Проверки: сборка для изменений кода и только непосредственно затронутые тесты (backend --reuse-db), UI — браузером в штатном контуре. Без полного прогона, seed, временных API/fake backend и изменения доступов ради проверки. Для новых внешних доступов использовать реальный штатный контур; отсутствие доступа фиксировать как blocker, не выдавать непроверенное за пройденное. Перед submit_result прочитать get_c4_context, сверить реальные изменения со спецификацией/C4; необходимые изменения документации/архитектуры предложить единым propose_c4 и получить принятие, затем review_c4 с точным changeHash, затронутыми ID и доказательствами из кода. После изменения кода/документов повторить review. Planned не объявлять current до проверенной публикации.

Завершены явный делегат native-действий ИИ, аудит, адресные проверки, browser-проверка штатного приложения и C4 review revision 15; весь этап и реальные внешние подключения не объявляются завершёнными.
