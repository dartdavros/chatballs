## Цель

Реализовать общий устойчивый путь эффекта и ручной одношаговый запуск через него. Пользователь получает достоверный результат, сверку/отмену и очистку данных, а не ложный успех после сетевого сбоя.

## Критерии приёмки

- [x] Обязательный gate: реализация начинается только после явно зафиксированной личной приёмки владельцем ОБОИХ результатов baseline; принятие карточки плана/задачи не является приёмкой макета. Основание: SPEC-0037 R-28.
- [x] Прямое действие/одношаговый сценарий сотрудника создаёт атомарный snapshot/Run+outbox; dedup tenant/scenario/trigger не обходится правкой ревизии. Ключ эффекта сохранён до запроса; version mismatch объясним и не подменяет контракт.
- [x] Шаг захватывается коротким lease/attempt/fencing, внешний I/O идёт вне транзакции, результат/следующее задание фиксируются атомарно. Устаревший воркер не перезаписывает результат, подтверждённый эффект не повторяется.
- [x] Стратегии idempotency key/reconcile/безопасного чтения/неизвестного результата реально применяются при потере ответа и падении после отправки. Без доказанной безопасности нет слепого повтора записи или обещания exactly-once.
- [x] Текущие права, scope, состояние подключения/сценария/контекста и точные подтверждения проверяются перед каждым новым эффектом. Отмена прекращает новые эффекты; уже отправленный запрос остаётся на установлении исхода, компенсация — отдельное разрешённое действие.
- [x] Backoff/jitter/Retry-After, постоянные ошибки, паузы/лимиты подключений и bounded worker-порции не блокируют другие сервисы и штатную обработку сообщений/ИИ. Нет второго обязательного брокера/worker-сервиса.
- [x] Ручные действия/параметры/подтверждения и безопасный журнал с поиском/фильтрами/пагинацией/realtime, сверкой/аудируемым намеренным повтором/отменой реализованы по baseline; частичный/неизвестный исход не выдан за успех.
- [x] Минимальные операционные данные шифруются. Настраиваемая OWNER/ADMIN очистка по умолчанию удаляет данные шагов через 7 дней после завершения запуска, безопасный журнал через 30; защищает активные ожидания, очищает операционные файлы без независимого владельца и сохраняет минимальные dedup-ключи на окно replay/reconcile. Payload не дублируется в outbox/логах/журнале, аудит сохраняет свою политику.
- [x] Тесты гонок/lease/stale worker, потери ответа и критической границы внешнего эффекта, прав/отключения/отмены и очистки проходят; выполнены сборка и штатная browser-проверка затронутого UI. Инструкции восстановления и ограничения неизвестного исхода включены в справку.

## Заметки

Причина выделения: опасная граница внешнего эффекта и фиксации требует одного связного bounded-сеанса с ручным управлением/журналом и необходимыми тестами; compose/control-flow сложных сценариев завершает следующая задача на этом же исполнителе, без второго runtime. Контракт путей/продолжений сразу соответствует полному SPEC. Пути: execution/{permissions,approvals,launch,runner,actions,recovery,checkpoints}.py, scenario_state/{runs,steps,journal,retention}.py, штатный events; UI integrations/runs/. C4: policy/runner/state, dynamic-staff/recovery/cancel/retention. Основа: SPEC-0037, ADR-0038, docs/service-integrations-c4.md и актуальный get_c4_context. Один backend/штатные PostgreSQL, worker/worker-events, inbox/outbox, tenant/RLS; без новых обязательных служб. Соблюдать AGENTS.md, DRY/KISS/SRP, NO GOD FILES, отдельные model/API/subviews, i18n ru/en. Проверки: сборка для изменений кода и только непосредственно затронутые тесты (backend --reuse-db), UI — браузером в штатном контуре. Без полного прогона, seed, временных API/fake backend и изменения доступов ради проверки. Для новых внешних доступов использовать реальный штатный контур; отсутствие доступа фиксировать как blocker, не выдавать непроверенное за пройденное. Перед submit_result прочитать get_c4_context, сверить реальные изменения со спецификацией/C4; необходимые изменения документации/архитектуры предложить единым propose_c4 и получить принятие, затем review_c4 с точным changeHash, затронутыми ID и доказательствами из кода. После изменения кода/документов повторить review. Planned не объявлять current до проверенной публикации.

## Итог

Реализован общий устойчивый путь ручного прямого действия и одношагового сервисного сценария: snapshot/outbox, lease/fencing, безопасное восстановление, журнал, отмена, намеренный повтор и очистка 7/30. Оба архитектурных пакета применены, C4 review сохранён для revision 7 и текущего changeHash; код и адресные тесты закоммичены. Реального внешнего подключения нет по ранее зафиксированному решению продолжать без доступа, поэтому полный внешний запуск и заполненные UI-состояния не проверены: критерии 7 и 9 не выполнены, задача и этап не объявляются завершёнными.
