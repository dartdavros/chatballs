## Цель

Реализовать сохранение и редактирование полных определений сценариев с типизированными данными, доступом и всеми видами блоков. Пользователь меняет копию пресета или создаёт отсутствующий сценарий без доработки ядра.

## Критерии приёмки

- [x] Обязательный gate: реализация начинается только после явно зафиксированной личной приёмки владельцем ОБОИХ результатов baseline; принятие карточки плана/задачи не является приёмкой макета. Основание: SPEC-0037 R-28.
- [x] OWNER/ADMIN создают/изменяют/копируют/удаляют/включают сценарий; готовый пресет создаёт редактируемую tenant-копию и не перезаписывает её обновлением адаптера. Сохранение не исполняет действия и не выдаёт права.
- [x] Один версионированный формат содержит все triggers, if/foreach/parallel/call/wait/try и action, параметры, обработку ошибок и делегирование. Ревизия защищает от конкурентной правки; отдельный процесс релизов/публикации сценария не навязан.
- [x] API и UI «Когда → Условия → Шаги» поддерживают каждый блок и их комбинации, справочники и схемы адаптеров; обычный сценарий не требует кода, JSON или рисования графа. Список/редактор и все состояния совпадают с принятым baseline.
- [x] Bindings поддерживают ввод сотрудника/ИИ, константы, разрешённый контекст, событие, предыдущие шаги и элемент перебора; типизированные преобразования и файлы. Ссылки/типы/обязательные значения проверяются до эффекта; произвольный Python/JS/SQL не исполняется.
- [x] Настраиваются все способы запуска, область/делегирование, режим ИИ, точные подтверждения и доступ; tenant/идентичность/секрет не назначаются произвольным пользовательским полем. Вложенный сценарий не может расширить права.
- [x] Настройки межсистемных связей/field mapping/source-of-truth/конфликтов/удаления/causality, расписаний/timezone/misfire представлены форматом и принятым UI без зашитого перечня CRM-сущностей; исполнение подключают зависимые задачи.
- [x] Затронутые тесты покрывают полноту формата/валидатора, копирование пресета, ревизии, типы/ссылки и RLS; UI проверен браузером. Пользовательская справка редактора и примеры актуализированы.

## Заметки

Причина выделения: самостоятельный результат — пользователь может сохранить и проверить свой сценарий любой согласованной структуры; это большой UI/типизированный формат, отдельный от протоколов подключения и работы воркеров. Схемы исполнения согласованы со SPEC/C4 заранее; не вводить второй DSL, редуктор возможностей или фиктивный запуск. Незавершённый общий механизм не объявлять готовой функцией. Пути: integrations/scenarios/, scenario_state/definitions.py/subscriptions.py/grants.py/entity_links.py; UI integrations/scenarios/. C4: scenarios/policy/data и dynamic-setup/blocks/native-sync. Основа: SPEC-0037, ADR-0038, docs/service-integrations-c4.md и актуальный get_c4_context. Один backend/штатные PostgreSQL, worker/worker-events, inbox/outbox, tenant/RLS; без новых обязательных служб. Соблюдать AGENTS.md, DRY/KISS/SRP, NO GOD FILES, отдельные model/API/subviews, i18n ru/en. Проверки: сборка для изменений кода и только непосредственно затронутые тесты (backend --reuse-db), UI — браузером в штатном контуре. Без полного прогона, seed, временных API/fake backend и изменения доступов ради проверки. Для новых внешних доступов использовать реальный штатный контур; отсутствие доступа фиксировать как blocker, не выдавать непроверенное за пройденное. Перед submit_result прочитать get_c4_context, сверить реальные изменения со спецификацией/C4; необходимые изменения документации/архитектуры предложить единым propose_c4 и получить принятие, затем review_c4 с точным changeHash, затронутыми ID и доказательствами из кода. После изменения кода/документов повторить review. Planned не объявлять current до проверенной публикации.
