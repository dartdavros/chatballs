## Цель

Подключить автоматические инициаторы к тому же исполнителю и реализовать управляемую межсистемную синхронизацию. Событие даёт независимые запуски подписчиков без повторения штатных правил.

## Критерии приёмки

- [x] Обязательный gate: реализация начинается только после явно зафиксированной личной приёмки владельцем ОБОИХ результатов baseline; принятие карточки плана/задачи не является приёмкой макета. Основание: SPEC-0037 R-28.
- [x] Работают события Chatballs, webhook внешнего сервиса, cursor-опрос при отсутствии webhook, расписание и аутентифицированный внешний API; все используют общий launch/runner с проверенными делегированными полномочиями и устойчивым trigger key.
- [x] Проверенный конверт+outbox сохраняются до ACK. Fan-out после сбоя доставляет событие каждому подходящему подписчику отдельным Run; ошибка одного не теряет остальных. Ревизия сценария не создаёт дубль старого события.
- [x] Доменные интеграционные события публикуются в исходной транзакции изменений Chatballs через общую точку; существующие outbox handlers и четыре вида правил не перерегистрируются/не исполняются повторно. Формирование данных события не обходит RLS/видимость.
- [x] Поллинг фиксирует cursor только вместе с durable обработанными данными. Schedule учитывает timezone, DST и явную misfire-политику из документа; повтор poller не дублирует slot. Pause/backoff и справедливость сохраняют обслуживание прочих подключений и сообщений.
- [x] EntityLink хранит tenant/connection/kinds/устойчивые IDs; исполняются mappings, source-of-truth, конфликты/удаление и причинность/предотвращение обратных циклов. Email/телефон не доказывает личность и не запускает скрытого слияния; отдельная CRM-мастер-база не создаётся.
- [x] Настройки автоматизации/синхронизации и её результаты связаны с принятым UI редактора/журнала; пользователь видит ошибку, остановку и частичный результат без скрытого запуска/выдачи прав.
- [x] Затронутые тесты покрывают durable ingress/fan-out, сбой посреди распределения, cursor/DST/misfire, scoped API, конфликты/удаление/обратный цикл и совместимость правил. Browser-проверка затронутого UI и справка автоматизации/синхронизации входят в задачу.

## Заметки

Причина выделения: независимо полезная автоматизация и синхронизация поверх полного ручного исполнителя. События/расписания и синхронизация держатся вместе, так как используют одни receipt/cursor/causal-правила; выделять отдельные задачи на таблицы/handlers/тесты не требуется. Пути: automation_events/, scenarios/synchronization.py, scenario_state/subscriptions.py/entity_links.py, доменные hooks. C4: dynamic-event/schedule/native-sync, planned events. Основа: SPEC-0037, ADR-0038, docs/service-integrations-c4.md и актуальный get_c4_context. Один backend/штатные PostgreSQL, worker/worker-events, inbox/outbox, tenant/RLS; без новых обязательных служб. Соблюдать AGENTS.md, DRY/KISS/SRP, NO GOD FILES, отдельные model/API/subviews, i18n ru/en. Проверки: сборка для изменений кода и только непосредственно затронутые тесты (backend --reuse-db), UI — браузером в штатном контуре. Без полного прогона, seed, временных API/fake backend и изменения доступов ради проверки. Для новых внешних доступов использовать реальный штатный контур; отсутствие доступа фиксировать как blocker, не выдавать непроверенное за пройденное. Перед submit_result прочитать get_c4_context, сверить реальные изменения со спецификацией/C4; необходимые изменения документации/архитектуры предложить единым propose_c4 и получить принятие, затем review_c4 с точным changeHash, затронутыми ID и доказательствами из кода. После изменения кода/документов повторить review. Planned не объявлять current до проверенной публикации.
