## Цель

Спроектировать полный административный путь: третья группа, подключение, готовые сценарии и создание своего. Результат — открываемые макеты существующего формата и личная приёмка владельца, до реализации.

## Критерии приёмки

- [x] В design/baseline/service-integrations/*.dc.html используются x-dc/canvas, support.js и существующие токены/темы/акцент; подходящие shared/соседние компоненты переиспользованы, отсутствующие спроектированы как переиспользуемые. Рядом перечислены использованные компоненты и новые необходимые элементы.
- [x] Спроектированы третья группа в существующем разделе, каталог установленных адаптеров, создание/проверка/восстановление доступа, OAuth и другие объявленные способы авторизации, карточка сервиса, несколько подключений одного адаптера, готовые сценарии и создание редактируемой копии.
- [x] Редактор показывает «Когда → Условия → Шаги» и все блоки: действие, ветвление, перебор, параллельные ветви, вложенный сценарий, ожидание времени/события/подтверждения, обработка ошибок. Обычный сценарий не требует кода, JSON или графа.
- [x] Предусмотрены ввод/контекст/события/результаты шагов/перебор, вложенные параметры/списки/даты/справочники/файлы, типизированные преобразования; настройки всех способов запуска, расписания/timezone/misfire, связи сущностей/синхронизация/конфликты/удаление и доступ/делегирование.
- [x] Предусмотрены хранение данных шагов 7 дней и журнала 30 дней по умолчанию после завершения запуска, настройка OWNER/ADMIN; пустые/ошибочные/недоступные/отключённые состояния, отсутствие прав, несовместимая версия, несохранённые/конкурентные правки. В продуктовых текстах нет служебных кодов.
- [x] Макеты просмотрены на 1024/1440 в обеих темах с акцентами существующей системы; административный мобильный UI не добавлен. Есть перечень кадров, позволяющий владельцу проверить все пути/состояния.
- [x] Владелец лично принял все относящиеся макеты и новые компоненты; его явное решение зафиксировано. До решения задача не объявляется принятой/завершённой по одному отчёту агента.

## Заметки

Причина отдельной задачи: самостоятельный результат личной приёмки административного пути; большой редактор и схемные контролы требуют отдельного bounded-сеанса от рабочих действий/журнала. Это задача создания baseline, а не подготовки спецификаций или планирования. Источники: существующие design/baseline/Chatballs Baseline v2/ и platform-expansion/, SPEC-0015, view-service-workbench, view-service-code-ui-connections/scenarios. Приложение/его runtime не реализовывать в этой задаче. Новые решения дизайна предъявить владельцу как baseline, не маскировать под работающую интеграцию. Перед submit_result прочитать get_c4_context, сверить реальные изменения со спецификацией/C4; необходимые изменения документации/архитектуры предложить единым propose_c4 и получить принятие, затем review_c4 с точным changeHash, затронутыми ID и доказательствами из кода. После изменения кода/документов повторить review. Planned не объявлять current до проверенной публикации.
