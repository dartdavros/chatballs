## Цель

Реализовать внутренние операции сотрудников, групп, агентов, знаний, навыков, порталов и подключений. Автоматизация использует те же права и проверки, что штатное управление организацией.

## Критерии приёмки

- [x] Обязательный gate: реализация начинается только после явно зафиксированной личной приёмки владельцем ОБОИХ результатов baseline; принятие карточки плана/задачи не является приёмкой макета. Основание: SPEC-0037 R-28.
- [x] Реестр покрывает все публичные продуктовые действия сотрудников/membership/групп/доступности/приглашений и настроек организации, агентов/навыков/знаний/категорий/импорта/файлов, порталов/статей и сервисных/транспортных/AI-подключений, включая сам механизм сценариев/разрешённое управление им.
- [x] Для всех продуктовых API-возможностей группы есть проверяемая запись inventory/action; API логина/протоколов классифицированы отдельно и сохраняют собственные протоколы. Секреты не становятся обычным возвращаемым полем действия.
- [x] Разделённые обёртки вызывают штатные доменные сервисы и сохраняют tenant/RLS, роли/супервизорские/owner ограничения, права контента и режим организации. Изменение параметров запуска или nested-сценарий не повышают scope.
- [x] Реестр не ограничивает продуктовые операции чтением; запись/удаление доступны по точным полномочиям и выбранной политике подтверждения. Повторы внешних/необратимых эффектов объявлены явно и не выдаются за безопасные автоматически.
- [x] Все схемы/справочники/результаты обслуживаются общим редактором/журналом по baseline; нужные доверенные расширения регистрируются без ветвления ядра по названию действия.
- [x] Тесты inventory/contract и затронутые поведенческие тесты прав/режимов/секретов проходят; UI проверен браузером. Документация этой группы действий и примеры входят в результат; существующие аккаунты/пароли/роли ради проверки не меняются.

## Заметки

Причина выделения: завершённый набор операций управления организацией и контентом — другой большой публичный API-контур, чем переписка. Зависимость от предыдущей задачи позволяет переиспользовать единые registry/coverage без конфликтующих реализаций; задача не создаёт новый движок/ролевая модель. Пути: action_catalog/{identity,ai,knowledge,portals,files,settings,...}.py и штатные сервисы. C4: native, соответствующие domain rel-service-native-*. Основа: SPEC-0037, ADR-0038, docs/service-integrations-c4.md и актуальный get_c4_context. Один backend/штатные PostgreSQL, worker/worker-events, inbox/outbox, tenant/RLS; без новых обязательных служб. Соблюдать AGENTS.md, DRY/KISS/SRP, NO GOD FILES, отдельные model/API/subviews, i18n ru/en. Проверки: сборка для изменений кода и только непосредственно затронутые тесты (backend --reuse-db), UI — браузером в штатном контуре. Без полного прогона, seed, временных API/fake backend и изменения доступов ради проверки. Для новых внешних доступов использовать реальный штатный контур; отсутствие доступа фиксировать как blocker, не выдавать непроверенное за пройденное. Перед submit_result прочитать get_c4_context, сверить реальные изменения со спецификацией/C4; необходимые изменения документации/архитектуры предложить единым propose_c4 и получить принятие, затем review_c4 с точным changeHash, затронутыми ID и доказательствами из кода. После изменения кода/документов повторить review. Planned не объявлять current до проверенной публикации.
